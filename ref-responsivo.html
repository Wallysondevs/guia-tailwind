Responsivo

A Ana montou o cardápio da padaria no notebook e ficou ótimo: quatro colunas, tudo alinhado. Então ela abriu o mesmo arquivo no celular e levou um susto — as quatro colunas viraram quatro faixas de dois centímetros, o título quebrou em três linhas e o botão de encomendar saiu pela direita da tela. Ela não quer duas páginas, uma para cada aparelho. Quer uma página que se ajuste. Esta é a consulta do responsivo no Tailwind v4: os breakpoints de verdade, o que cada prefixo gera no CSS, o jeito mobile-first, as faixas e as armadilhas que fazem o layout pular.

1. Os breakpoints do Tailwind

O Tailwind traz cinco breakpoints com nome e mais o caso "sem prefixo". Todos são mínimos: o prefixo vale daquela largura para cima, e nunca "só naquela largura". md: não quer dizer "tablet"; quer dizer "de 768 px em diante", o que inclui o notebook, o monitor grande e a TV. Essa é a primeira coisa a decorar, porque é a que mais gera confusão em quem vem de outras ferramentas.

PrefixoA partir deEm pixelsOnde costuma valer
(sem prefixo)0qualquer largurao celular: é aqui que se escreve o caso base
sm:40rem640 pxcelular grande, celular deitado
md:48rem768 pxtablet em pé, janela estreita no notebook
lg:64rem1024 pxnotebook comum
xl:80rem1280 pxmonitor de mesa
2xl:96rem1536 pxtela grande, sala de aula, painel

Os valores são em rem, não em pixels, de propósito. rem é relativo ao tamanho de fonte do elemento raiz — normalmente 16 px, mas quem aumenta a letra do navegador por dificuldade de visão muda essa base. Se o breakpoint fosse fixo em pixels, a pessoa com fonte 20 px teria um layout de 640 px numa área que, na prática, é menor. Com rem, tudo cresce junto. A aula Os Breakpoints percorre essa escada com exemplos de layout. A conta que você faz de cabeça é rem × 16; os cinco números que importam são 640, 768, 1024, 1280 e 1536.

Repare também no que não existe: não há um breakpoint para "celular pequeno". O Tailwind parte do princípio de que o caso base já é o celular — 375 px, 360 px, 320 px, tanto faz. Quem precisa tratar a tela minúscula de um jeito especial usa faixa (seção 4) ou uma medida avulsa, e não um prefixo novo. Guarde isso: o layout nasce pequeno e cresce; ele não nasce grande e encolhe.

viewport
A área visível da página, sem as barras do navegador. É a largura que os breakpoints medem.
breakpoint
A largura em que o desenho muda de regra. No Tailwind, cada um tem nome: sm, md, lg, xl, 2xl.
mobile-first
Escrever primeiro o caso do celular, sem prefixo, e acrescentar o resto com md:, lg:.
faixa
Um intervalo com começo e fim, como md:max-lg: — vale entre 768 e 1024 px.
container query
Consulta que mede o espaço do componente, não o da janela. No Tailwind, o pai leva @container e o filho usa @sm:, @md:.

2. O que o prefixo escreve no CSS

Cada classe com prefixo vira uma regra dentro de uma consulta de mídia. No Tailwind v4 a consulta usa a sintaxe moderna de intervalo, @media (width >= 48rem), e não o velho min-width. O efeito é o mesmo; o texto é mais curto e mais legível. Veja o que sai de três classes de uma vez:

@media (width >= 40rem) {
  .sm\:block {
    display: block;
  }
}
@media (width >= 48rem) {
  .md\:block {
    display: block;
  }
}
@media (width >= 64rem) {
  .lg\:block {
    display: block;
  }
}

Três detalhes que esse trecho revela. Primeiro, o nome da classe carrega o prefixo escapado (.md\:block), igual às variantes de estado: o dois-pontos faz parte do nome. Segundo, cada breakpoint é uma regra separada; não há "herança" de md: para lg: — se você quer o mesmo valor nos dois, escreva nos dois. Terceiro, a consulta olha a largura da janela (o viewport), não a largura do elemento. Um cartão de 300 px numa tela de 1400 px continua recebendo as regras de lg:. Para reagir ao tamanho do cartão, existem as container queries da seção 6.

Como a ordem das regras no CSS compilado segue a ordem dos breakpoints (do menor para o maior), o que vem depois vence quando as duas condições valem. Isso é o que faz a escada funcionar: p-2 md:p-4 lg:p-8 termina com 32 px num monitor, porque a regra de lg: é a última. E é também o motivo de a ordem no HTML não importar — md:p-4 p-2 desenha igual, já que o Tailwind ordena as regras por breakpoint na hora de compilar. Você pode escrever na ordem que fizer sentido para quem lê.

3. Mobile-first na prática

A regra de ouro é uma frase: escreva o caso base para o celular e use os prefixos para acrescentar. Nunca escreva o caso base pensando no monitor. Se o cartão tem 16 px de respiro no celular e 32 px no notebook, a classe é p-4 lg:p-8. Se você inverter e escrever p-8 com max-lg:p-4, funciona, mas vive de exceção — e cada tela nova exige outra exceção. A aula Mobile First mostra a mesma escada aplicada a um cartão inteiro, degrau por degrau.

Um jeito de conferir se a escada está certa é ler a lista de classes como uma subida: o primeiro valor é o chão, cada prefixo é um degrau. grid-cols-1 sm:grid-cols-2 lg:grid-cols-4 conta uma história clara: uma coluna no celular, duas a partir de 640, quatro a partir de 1024. Se a leitura não contar história nenhuma — md:p-2 md:p-8 —, o problema está na classe, não no navegador.

A grade do cardápio está com uma coluna em qualquer tela. Esta prévia tem 768 px de largura, então o breakpoint md: já vale: acrescente md:grid-cols-2 para o tablet mostrar dois pães por linha.

O painel vai mostrar grid-template-columns com dois valores — algo como 368px 368px — em vez de um valor só. É a prova de que a regra pegou. Se você reduzir a largura da janela do navegador abaixo de 768 px e clicar em Rodar de novo, o painel volta a mostrar uma coluna: a prévia respeita a intenção do breakpoint, e é por isso que a caixa declara data-largura="768" em vez de depender do tamanho da sua tela.

Uma consequência prática do mobile-first: quase toda página tem mais classes de desktop do que de celular. Isso assusta quem lê o HTML pela primeira vez, mas é o esperado. O caso base é curto porque o celular é simples: uma coluna, tudo empilhado, fonte legível. O desktop é que precisa de instruções extras — quantas colunas, o que fica ao lado do quê. Você está descrevendo o que fazer com o espaço que sobra, e não o que fazer quando ele falta.

4. Faixas, medidas avulsas e outras consultas

Às vezes o caso não é "daqui para cima", e sim "só aqui". O Tailwind atende com as variantes max-*, com as faixas compostas e com medidas avulsas entre colchetes. A tabela abaixo é a lista do que o motor aceita, com o texto exato que ele escreve.

ClasseVira no CSSVale quando
max-sm:block@media (width < 40rem)abaixo de 640 px
max-md:hidden@media (width < 48rem)abaixo de 768 px
md:max-lg:block>= 48rem com < 64rem por dentrosó entre 768 e 1024 px
min-[900px]:grid@media (width >= 900px)uma medida que não está na escada
max-[900px]:grid@media (width < 900px)o mesmo, para baixo
min-md:block@media (width >= 48rem)sinônimo explícito de md:
portrait:block@media (orientation: portrait)tela em pé, celular na mão
landscape:flex@media (orientation: landscape)tela deitada
print:hidden@media printa receita impressa, sem o botão de comprar
motion-reduce:transition-noneprefers-reduced-motion: reducequem pediu menos animação no sistema

A faixa composta merece uma explicação, porque o texto do CSS parece incompleto. O Tailwind aninha as duas consultas em vez de juntá-las com and: sai um @media (width >= 48rem) por fora e um @media (width < 64rem) por dentro. O resultado no navegador é o mesmo de um intervalo — vale só entre 768 e 1024 px —, com um detalhe importante: o limite de baixo é inclusivo e o de cima é exclusivo. Em 768 px vale; em 1024 px já não vale, porque lg: assumiu.

Sobre as medidas avulsas: min-[900px]: existe para o caso de o desenho pedir uma quebra que não está na escada. Use com parcimônia e com um motivo que você saiba explicar — "a barra de navegação quebra em 900" é motivo; "achei 900 bonito" é dívida. A escada de cinco degraus é curta de propósito: quanto menos breakpoints, mais coerente o site parece, e menos combinações você precisa testar. Um site com min-[700px], md: e min-[850px] tem três pontos de quebra em 150 px de diferença, o que ninguém consegue revisar.

A linha do menu é a que mais dá errado, e por um motivo bobo: esconder é fácil, mostrar de novo é que exige o prefixo. hidden sozinho esconde em todas as telas, porque hidden não é "escondido no celular" — é display: none, ponto. Quem quer o menu fora do celular e dentro do desktop escreve hidden md:flex, e as duas classes brigam pela mesma propriedade com breakpoints diferentes. O Tailwind resolve pela ordem no CSS: md:flex vem depois, então vence a partir de 768 px. Esse vai e vem tem aula própria em Esconder e Mostrar.

O painel mostra display: none depois da solução, e isso é o certo: a 375 px o menu está escondido. Para ver o outro lado, mude a largura da caixa para 768 — aí o painel passa a mostrar display: flex. Ter as duas provas, uma em cada largura, é o mínimo antes de dizer que um responsivo está pronto.

A linha da tabela tem outra lição embutida. Não existe classe que faça uma tabela de oito colunas caber num celular sem virar sopa; o que existe é um invólucro com overflow-x-auto para o leitor arrastar de lado. E a linha do rodapé lembra uma coisa que o prefixo não resolve: a ordem dos blocos na tela. Quando o celular precisa mostrar a imagem antes do texto, mude a ordem com order-first e md:order-none em vez de duplicar o HTML.

6. Container queries: o cartão que sabe o próprio tamanho

Existe um caso em que o breakpoint de tela mente. Você tem um cartão de produto que aparece em três lugares: na vitrine (largura toda), na barra lateral (estreito) e dentro de um modal (médio). Numa tela de 1400 px, o cartão da barra lateral recebe todas as regras de lg: — e fica com duas colunas espremidas em 280 px. O certo seria o cartão reagir ao próprio espaço, não ao tamanho da janela. É isso que as container queries fazem.

A mecânica tem duas partes. No pai, você marca @container, que no CSS vira container-type: inline-size. Nos filhos, usa os prefixos com arroba: @sm:, @md:, @lg:. O Tailwind então escreve @container (width >= 24rem) no lugar de @media. Repare que a escala do container é outra: @sm: vale a partir de 24rem (384 px), e não 40rem.

@sm:@container (width >= 24rem)384 pxcartão de vitrine de celular
@md:@container (width >= 28rem)448 pxcartão de vitrine comum
@lg:@container (width >= 32rem)512 pxcartão grande, com foto ao lado

@container (width >= 24rem) {
  .\@sm\:flex {
    display: flex;
  }
}
@container (width >= 28rem) {
  .\@md\:grid {
    display: grid;
  }
}

No HTML, a marcação fica assim: um div com @container e, dentro, o cartão com @sm:flex ou @md:grid-cols-2. A partir daí, o cartão se adapta ao espaço que recebeu — e o mesmo HTML funciona na vitrine, na barra lateral e no modal. Duas armadilhas: o @container precisa estar num ancestral direto ou indireto do filho que usa os prefixos, e o container consultado é o mais próximo; se houver dois aninhados, vale o de dentro. Para desempatar, o Tailwind aceita nome: @container/cartao no pai e @sm/cartao:flex no filho.

Quando usar uma coisa e quando usar a outra? Regra prática: se o componente aparece em mais de um contexto de largura — cartão de produto, bloco de estatística, comentário —, container query. Se é o esqueleto da página — a barra lateral que vira gaveta, as colunas do conteúdo —, breakpoint de tela. Misturar os dois é normal e não tem problema; o que não se deve é tentar resolver componente com breakpoint de tela e ficar criando exceção para cada lugar onde ele aparece.

7. As armadilhas que fazem o layout pular

Comece pela ordem. A escada só sobe: p-2 md:p-4 lg:p-8 funciona; p-8 md:p-4 também "funciona", mas conta a história errada e no monitor deixa o cartão apertado, porque não existe lg: para desfazer. Se você escreveu um valor grande na base, todo breakpoint acima precisa de um valor maior, ou o desenho decresce conforme a tela cresce.

Depois, o hidden sem par. hidden não é cosmético: o elemento sai do fluxo, não ocupa espaço e não é lido por leitor de tela. Se o objetivo é só "não mostrar no celular", o par é hidden md:block (ou md:flex, conforme o display que o elemento precisa). Há uma alternativa que preserva o espaço: invisible, que esconde sem tirar do layout — útil quando o sumiço mudaria o alinhamento dos vizinhos.

Terceiro, a largura de teste. Muita gente revisa o responsivo no DevTools com o modo de aparelho ligado e acha que resolveu, mas o aparelho simulado tem 980 px de viewport se a página não declarar <meta name="viewport" content="width=device-width, initial-scale=1">. Sem essa linha, o celular finge ter 980 px e encolhe a página inteira; nenhum breakpoint do mundo conserta isso. O guia já traz a linha em todas as páginas — se você criar a sua, não esqueça.

Quarto, as alturas. h-screen é 100vh, e no celular vh conta a tela sem as barras do navegador, o que faz a seção passar do limite e criar rolagem. Para ocupar a tela de verdade, h-dvh usa a altura dinâmica do viewport. E uma altura em porcentagem só funciona se o pai tiver altura definida; h-full dentro de um div sem altura não faz nada, e parece que "o Tailwind não funcionou".

Quinto, as imagens. Uma imagem grande dentro de uma coluna de grade estoura a coluna, porque o navegador respeita o tamanho natural do arquivo. O par que resolve é max-w-full h-auto no próprio img; num contexto flex ou grid, some min-w-0 ao contêiner de texto para o conteúdo poder encolher. Não é bug do Tailwind: é o comportamento de min-width: auto no flex, que existe desde sempre.

Sexto, o excesso. Cada breakpoint novo é uma combinação a mais para conferir, e o pior lugar para descobrir um layout quebrado é o tablet de alguém. Três degraus — base, md:, lg: — resolvem a maioria dos sites deste guia. Se você precisa de sm: e xl: também, tudo bem, mas teste as cinco larguras: 375, 640, 768, 1024 e 1280.

8. Como conferir antes de publicar

O teste que vale é o da largura, não o do aparelho. No Chrome ou no Firefox, abra o DevTools (F12), ligue o modo responsivo e arraste a alça devagar, olhando o número que aparece em cima. Os pontos de interesse são exatamente os cinco da tabela da seção 1, mais 375 px. Ao cruzar 768, o layout deve mudar de uma vez, sem tremer e sem sobrar espaço morto — se tremer, há duas regras disputando a mesma propriedade.

Uma dica que economiza tempo: escreva a intenção antes da classe. "No celular, o preço embaixo do nome; no tablet, ao lado." Depois traduza para flex-col md:flex-row. Quando a frase não sai, geralmente o problema é de hierarquia, não de CSS. Já quando a frase sai e a tela não obedece, o suspeito é o min-w-0, a largura fixa em pixels no meio do caminho ou um whitespace-nowrap herdado — os três motivos clássicos de estouro horizontal no celular.

As caixas deste guia fazem esse teste por você, com uma diferença importante: a largura da prévia é declarada na caixa (data-largura) e não depende do tamanho da sua janela. Por isso uma missão de md: fica com 768 px mesmo que você esteja lendo no celular. Quando a missão envolve breakpoint, confira também a etiqueta de largura no canto da barra de botões — ela mostra o número real que o motor usou.

9. Resumo

O Tailwind v4 trabalha com cinco breakpoints mínimos — sm: 40rem, md: 48rem, lg: 64rem, xl: 80rem, 2xl: 96rem, ou 640, 768, 1024, 1280 e 1536 px com a fonte padrão. Cada prefixo gera um @media (width >= …) e vale daquela largura para cima, nunca só nela. A base, sem prefixo, é o celular: o layout nasce pequeno e cresce.

  • Escreva a base para o celular e use os prefixos para acrescentar: p-4 md:p-8 lg:p-12.
  • Para faixas, max-md: vale abaixo de 768; md:max-lg: vale no meio, com as duas consultas aninhadas.
  • Medida avulsa: min-[900px]:. Use pouco e saiba explicar por quê.
  • hidden esconde sempre; o par é hidden md:flex, com o display que o elemento precisa.
  • Componente que aparece em vários lugares pede @container e @sm:; o esqueleto da página pede breakpoint de tela.
  • Teste 375, 640, 768, 1024 e 1280 px — e nunca esqueça a linha do viewport.
  • Altura de tela cheia no celular é h-dvh, não h-screen.

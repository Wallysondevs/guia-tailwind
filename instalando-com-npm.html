Instalando com npm

A Ana decidiu: o site da padaria vai ter uma folha de CSS de verdade, gerada no notebook dela e enviada pronta para o servidor. Ela já conhece a estrada curta, a da tag script no HTML, e já viu o defeito dela na prática: a página abre sem estilo e o desenho aparece meio segundo depois. Agora ela vai instalar o Tailwind como um pacote do projeto — a estrada que exige terminal, mas que entrega um arquivo .css comum. O assunto desta aula é só a instalação: o que o npm baixa, onde os arquivos caem, o que cada linha de comando faz e como provar que deu certo antes de escrever a próxima classe.

Você vai aprender
  • O que é o npm e o que ele baixa quando você pede o Tailwind.
  • Por que a instalação traz dois pacotes e não um.
  • O que são package.json, package-lock.json e a pasta node_modules.
  • Para que serve o -D e a diferença entre dependencies e devDependencies.
  • O comando de instalação linha por linha, sem parte decorada.
  • As três provas de que a instalação funcionou.
  • O que fazer quando o npm reclama de permissão, de versão ou de rede.

1. A cena: a padaria precisa de uma folha própria

A padaria da Ana tem três páginas: a inicial, a de produtos e a de contato. No celular de quem encomenda, o site abre com internet ruim — e é aí que a estrada curta mostra seu preço. O navegador precisa buscar o construtor do Tailwind num servidor de fora, ler o HTML inteiro e só então gerar o CSS. Enquanto isso não termina, a página aparece sem cor, sem espaçamento, com o texto grudado nas bordas. No Wi-Fi da padaria, isso leva quase um segundo. Na fila do pão, ninguém espera.

O que a Ana quer é simples de dizer e exige trabalho para montar: um arquivo .css comum, pequeno, que o navegador baixe como baixa uma foto, e que já venha com todas as classes que as três páginas usam. Sem internet obrigatória, sem geração no aparelho do visitante, sem piscar. Para chegar nisso, alguém precisa gerar esse arquivo antes de publicar — e quem gera é a ferramenta do Tailwind, que mora dentro do projeto.

Como esse arquivo nasce? Por enquanto, guarde a imagem: existe uma entrada (um arquivo de CSS pequeno, escrito por ela) e uma saída (o arquivo grande, escrito pela ferramenta). No meio das duas fica o comando que lê a entrada, percorre o HTML em busca de nomes de classe e escreve a saída. Instalar com npm é o passo que coloca esse comando dentro da pasta do projeto, para que ele possa ser chamado com uma linha.

Vale saber o que muda em relação ao que a Ana já fez nas caixas deste guia. Nas caixas, o motor lê o HTML da prévia e gera o CSS na hora, no seu navegador — ótimo para aprender, impossível de publicar. No projeto dela, o mesmo motor lê arquivos e escreve um arquivo. O resultado visual é idêntico; o que muda é onde e quando o trabalho acontece. Esta aula cuida do "onde": a instalação.

2. O que é o npm, sem mistério

O npm é o gerenciador de pacotes que vem junto com o Node.js. Ele faz três coisas, e só isso: baixa pacotes de um catálogo público chamado registro (registry), guarda esses pacotes dentro do seu projeto e anota, num arquivo de texto, quais pacotes e quais versões o projeto usa. Não é uma loja com janela, não é um programa que fica aberto, não tem botão. É um comando de terminal chamado npm, e você o chama quando precisa.

Pacote, aqui, é uma pasta com arquivos de outra pessoa, publicada para ser reaproveitada. O Tailwind é distribuído assim: você não baixa um instalador do site, você pede ao npm que traga o pacote tailwindcss. O npm conversa com o registro, baixa a versão pedida, descompacta dentro de node_modules/ e registra o que fez. Da segunda vez em diante, ele reaproveita o que já está no cache do seu usuário e a instalação leva segundos.

Duas consequências práticas que economizam muita dor de cabeça. A primeira: a instalação é um passo do projeto, não da máquina. Cada projeto tem o seu node_modules, com as versões que aquele projeto pediu. A segunda: como tudo está anotado em arquivos de texto, outra pessoa (ou você, seis meses depois, em outro notebook) consegue repetir a instalação com um comando e chegar no mesmo resultado. Isso é o que torna o fluxo com npm confiável — e o que a estrada sem build não oferece.

3. Os dois pacotes: motor e comando

Aqui está a primeira surpresa de quem instala a versão 4: não é um pacote, são dois. O motor tailwindcss sabe transformar nomes de classe em CSS, mas não sabe ler argumentos de terminal, nem procurar arquivos, nem escrever arquivos. Quem faz esse trabalho é a interface de linha de comando (CLI), publicada separadamente como @tailwindcss/cli. Um é o cérebro; o outro é a mão que segura a caneta.

Por que separar? Porque o motor é usado por outras ferramentas que não são terminal: o plugin do Vite, o plugin do PostCSS, o construtor que roda no navegador, todos conversam com o mesmo motor. Se o comando de terminal viesse embutido, essas ferramentas carregariam código que nunca usam. A divisão é a mesma ideia de vender liquidificador e copo separados: quem já tem o copo não paga duas vezes.

tailwindcss
O motor. Recebe o CSS de entrada mais uma lista de nomes de classe e devolve o CSS com as regras. Não tem interface: é chamado por outra ferramenta.
@tailwindcss/cli
O comando de terminal. Lê os arquivos do projeto, chama o motor e escreve a folha de saída. É o pacote que dá o binário tailwindcss.
node_modules/
A pasta onde o npm descompacta os pacotes. Você não edita nada dentro dela e não a copia para outro computador: ela é recriada a partir dos arquivos de anotação.
package.json
A caderneta de identidade do projeto: nome, versão, comandos apelidados e a lista de pacotes que ele precisa.
package-lock.json
O mapa exato do que foi instalado, com versão e endereço de cada pacote. É o que garante que outra máquina instale exatamente o mesmo conjunto.

Na prática, você quase nunca digita o nome do motor. Digita o comando da CLI, e a CLI chama o motor. A exceção são projetos com ferramentas de build (Vite, Next, Astro), que chamam o motor direto — e aí a CLI nem é instalada. Como o site da padaria é HTML puro, a dupla completa é o caminho.

4. O package.json: a caderneta do projeto

Todo projeto que usa npm tem um package.json na raiz. É um arquivo de texto, no formato JSON, com pares de nome e valor entre chaves. Você pode abrir no editor e ler: não há nada escondido. Depois da instalação do Tailwind, o da Ana ficou assim:

{
  "name": "padaria",
  "version": "1.0.0",
  "private": true,
  "scripts": {
    "build": "tailwindcss -i src/entrada.css -o dist/estilo.css",
    "dev": "tailwindcss -i src/entrada.css -o dist/estilo.css --watch"
  },
  "devDependencies": {
    "@tailwindcss/cli": "^4.3.5",
    "tailwindcss": "^4.3.5"
  }
}

Leia por partes. name é o nome do projeto, que o npm init -y tirou do nome da pasta. version é a versão do projeto (não do Tailwind). private: true impede que o projeto seja publicado sem querer no registro público: é uma trava de segurança que a Ana acrescentou à mão. scripts são apelidos para comandos compridos: em vez de digitar a linha inteira, você digita npm run build.

E devDependencies é a lista dos pacotes que só servem durante o desenvolvimento. O Tailwind entra aí porque o visitante nunca o recebe: ele recebe apenas o CSS que o Tailwind produziu. A diferença entre dependencies e devDependencies não é decorativa — quando alguém instala o projeto para colocá-lo no ar, pode pular as dependências de desenvolvimento, que é justamente o caso do Tailwind. É por isso que o comando de instalação leva -D.

Repare também no acento circunflexo antes da versão: ^4.3.5. Ele quer dizer "aceito qualquer 4.x a partir de 4.3.5, mas não aceito 5". É o jeito de receber correções de erro sem quebrar o projeto com uma mudança grande. Se você quiser exatamente uma versão, sem surpresas, escreva 4.3.5 puro — o npm respeita. E se escrever ~4.3.5, aceita correções de terceiro dígito e nada mais.

5. O comando de instalação, linha por linha

Com o terminal aberto na pasta do projeto, são quatro linhas. A primeira entra na pasta; as outras três fazem o serviço:

$ cd /home/ana/padaria
$ npm init -y
Wrote to /home/ana/padaria/package.json
$ npm install -D tailwindcss @tailwindcss/cli
added 12 packages in 3s
$ npx @tailwindcss/cli -i src/entrada.css -o dist/estilo.css

npm init -y cria o package.json com as respostas padrão; o -y é o "sim" para todas as perguntas que ele faria. npm install -D baixa os dois pacotes e anota em devDependencies; sem o -D, eles entrariam em dependencies, o que não é errado, mas mente sobre a natureza da ferramenta. npx executa um comando que está dentro de node_modules sem você precisar saber o caminho completo dele.

O -i aponta o arquivo de entrada, que a Ana criou com uma linha só; o -o aponta o arquivo de saída, que ainda não existe — e é a CLI que vai criá-lo. Nada é impresso quando dá certo: um comando que termina em silêncio, no terminal, é um comando bem-sucedido. A aula A CLI do Tailwind destrincha cada opção; aqui basta saber que essa linha é o coração do fluxo.

Existe um atalho que confunde muita gente. Escreva npx @tailwindcss/cli quando estiver digitando no terminal; dentro de um script do package.json, escreva só tailwindcss, sem o npx. Isso funciona porque o npm coloca a pasta node_modules/.bin no caminho de busca de qualquer script que ele executa. É por isso que o script build da Ana começa com tailwindcss e não com o nome completo do pacote.

6. Onde cada arquivo cai

Depois da instalação, a pasta da padaria tem mais coisas do que tinha antes. Vale conhecer cada uma, porque você vai conviver com elas todos os dias e mexer em apenas duas:

Arquivo ou pastaQuem criaPara que serveVocê mexe?
package.jsono npm initidentidade, scripts e lista de pacotessim, com cuidado
package-lock.jsono npm installversões exatas de tudo o que foi baixadonão à mão
node_modules/o npm installo código dos pacotes baixadosnunca
src/entrada.cssvocêo CSS que você escreve, com o @importsim
dist/estilo.cssa CLIo CSS final que o navegador carreganão à mão

Duas pastas com nomes de três letras contam a história toda: src vem de source, fonte; dist vem de distribution, distribuição. Tudo que é fonte mora em src (ou na raiz, junto do HTML); tudo que o navegador recebe mora em dist. Quando você publica o site, o servidor precisa das duas pastas — e pode ignorar node_modules tranquilamente, porque aquele código só serviu para gerar o CSS.

A entrada da Ana é minúscula, e isso é normal:

@import "tailwindcss";

Uma linha. Ela diz "traga o Tailwind para cá". O arquivo de entrada é o painel de controle do projeto: é nele que você declara cores da marca, fontes, e classes compostas. A aula O CSS de Entrada é dedicada a ele. E o HTML liga a folha gerada do jeito mais comum do mundo:

<link rel="stylesheet" href="dist/estilo.css">

Note a ordem: o link aponta para dist/estilo.css, o arquivo que a CLI escreve. Se você apontar para src/entrada.css, o navegador vai receber um arquivo com uma linha de @import e nenhuma classe — e a página fica sem estilo. Esse é o erro número um de quem instala. A folha que se liga é sempre a da saída.

Primeira folha gerada: deixe o cartão com 24 px de respiro por dentro, cantos de 12 px e texto âmbar escuro, mantendo o fundo claro.

<div id="alvo" class="p-4 bg-amber-100">Pão quentinho</div>
padding: 16px
background-color: oklch(0.962 0.059 95.617)

<div id="alvo" class="p-6 bg-amber-100 rounded-xl text-amber-900">Pão quentinho</div>

Essa caixa é o retrato do que a CLI faz depois de instalar: cada nome de classe vira uma regra, e só nasce regra para o nome que existe. p-6 vira padding de 24 px, rounded-xl vira border-radius de 12 px, text-amber-900 vira color. Nenhuma dessas regras vem de um arquivo mágico: todas foram geradas a partir do que está escrito no class.

7. As três provas de que a instalação funcionou

Instalar sem conferir é o caminho mais rápido para uma hora perdida. A Ana usa três provas, nesta ordem, e cada uma responde a uma pergunta diferente. A primeira prova é sobre o pacote; a segunda, sobre o arquivo; a terceira, sobre a página.

Prova 1 — o pacote está lá, e em que versão. O comando npm ls lista o que está instalado e mostra a versão resolvida. Se aparecer a árvore com os dois pacotes, a instalação aconteceu. Se aparecer uma linha com empty ou um aviso de pacote faltando, não aconteceu:

$ npm ls tailwindcss @tailwindcss/cli
padaria@1.0.0 /home/ana/padaria
├── @tailwindcss/cli@4.3.5
└── tailwindcss@4.3.5

Repare que a versão mostrada é a que está no disco, não a que está escrita no package.json. As duas podem divergir: o ^ autoriza o npm a pegar uma versão mais nova dentro do mesmo 4.x. Quando você precisa saber exatamente o que está rodando — e vai precisar, no dia em que um comportamento mudar do nada —, é esse comando que responde.

Prova 2 — o arquivo de saída tem regras. Abra dist/estilo.css no editor. A primeira linha é um comentário com a versão do Tailwind; depois vêm blocos de variáveis e, mais adiante, uma regra para cada classe usada no projeto. Se o arquivo tiver 30 linhas e nenhuma classe, desconfie: ou o @import não está na entrada, ou o caminho do -i está errado, ou o HTML não está na pasta que a ferramenta percorre.

Prova 3 — a página aplica o CSS. Esta é a que importa de verdade. Escreva uma classe no HTML, rode o comando, recarregue com Ctrl + Shift + R e veja se a aparência mudou. Quando não muda, o problema costuma ser uma classe digitada errado — e o Tailwind não avisa nada: ele simplesmente não gera regra para um nome que não conhece.

O cartão está com p-4x, um nome que não existe — o gerador não escreveu nada e o texto encosta na borda. Conserte a classe para 16 px de respiro interno.

<div id="alvo" class="p-4x bg-amber-100">Pão quentinho</div>
background-color: oklch(0.962 0.059 95.617)

<div id="alvo" class="p-4 bg-amber-100">Pão quentinho</div>

Repare no painel: ele mostra o fundo âmbar e nenhuma linha de respiro. É esse o aviso que você recebe — nenhum erro, nenhuma mensagem, só a falta da propriedade. O silêncio é o diagnóstico, e é por isso que a terceira prova é olhar o resultado, e não a beleza do código.

Existe uma quarta conferência, opcional, que ajuda a entender a segunda: pedir à caixa que mostre as regras geradas em vez do CSS computado. É a mesma coisa que abrir o dist/estilo.css e procurar o bloco da classe. Vale a pena fazer uma vez, porque o arquivo que a CLI escreve é exatamente esse tipo de texto:

Agora olhe a folha gerada, e não o resultado: acrescente ao cartão a classe que arredonda os cantos em 8 px e deixe o painel de regras mostrar os dois blocos.

<div id="alvo" class="bg-amber-100">Pão quentinho</div>
.bg-amber-100 {
  background-color: var(--color-amber-100);
}

<div id="alvo" class="bg-amber-100 rounded-lg">Pão quentinho</div>

Cada bloco tem um seletor (a classe), chaves e uma ou duas propriedades. Repare que o valor não é 8px: é var(--radius-lg), uma variável. O Tailwind escreve variáveis para que o mesmo raio possa ser trocado em um lugar só. Você não precisa entender de variáveis agora; precisa saber que o arquivo gerado é legível, e que o valor final aparece no painel de CSS computado ou na aba Computed do navegador.

8. Atualizar, travar e repetir a instalação

Instalar é o começo, não o fim. Três situações vão aparecer: querer a versão mais nova, querer a mesma versão de ontem e recriar tudo do zero. Cada uma tem um comando e uma lógica.

Para atualizar dentro do que o ^ permite, use npm update. Ele olha as faixas do package.json e sobe o que couber. Para ver o que está fora de faixa, existe npm outdated, que lista versão instalada, versão desejada e versão mais nova. Atualizar um projeto que já está no ar pede cuidado: rode o build e confira as páginas antes de publicar, porque uma correção de erro pode mudar um detalhe de aparência.

Para repetir a instalação em outra máquina — o notebook novo, o computador da irmã, o servidor de build —, não copie a pasta node_modules. Ela tem milhares de arquivos, alguns com atalhos que não sobrevivem à cópia, e é específica do sistema. Em vez disso, leve o projeto e rode npm ci (ou npm install). O ci é o comando feito para isso: apaga o node_modules e reinstala exatamente as versões do package-lock.json, sem negociar faixas.

O package-lock.json existe justamente para essa repetição dar certo. Ele guarda a versão resolvida de cada pacote — inclusive as dependências das dependências, que você nunca viu — e um resumo do conteúdo baixado. Sem ele, duas instalações no mesmo dia podem trazer conjuntos diferentes, porque o ^ aceita novidades. Com ele, o conjunto é o mesmo. É um arquivo chato de ler e essencial de manter.

ComandoO que fazQuando usar
npm installlê o package.json e instala o que faltaprimeira vez, ou depois de acrescentar um pacote
npm install -D pacoteinstala e anota em devDependenciesferramentas que só servem no desenvolvimento

Uma última recomendação de organização, que vale para qualquer projeto: chame os comandos pelos scripts. Com build e dev no package.json, você digita npm run build e não precisa lembrar de -i, -o nem do nome dos arquivos. Quem abre o projeto pela primeira vez lê os scripts e entende como ele é montado. É documentação que não desatualiza, porque é o próprio comando.

9. Cenários do dia a dia

Cenário 1: "npm: comando não encontrado"

O terminal não conhece a palavra npm. Na prática, o Node.js não está instalado, ou foi instalado depois que aquela janela do terminal abriu — o instalador mexe no caminho de busca, e janelas antigas não veem a mudança. Feche o terminal, abra de novo e teste node -v. Se continuar igual, instale a versão LTS no site oficial do Node e repita. Desconfie de tutoriais que mandam instalar o Node por gerenciador de pacotes do sistema: costuma dar versão velha demais para a versão 4 do Tailwind, que pede Node 20 ou mais novo.

Cenário 2: "EACCES: permissão negada"

A instalação tentou escrever numa pasta do sistema e o computador disse não. Quase sempre a causa é um sudo npm install -g feito no passado, que deixou arquivos com dono errado. O conserto não é repetir com sudo — isso só espalha o problema —, e sim corrigir o dono da pasta de cache do npm, como a documentação do npm ensina, e instalar sempre dentro do projeto, sem -g. Regra prática: npm install com sudo é sinal de que algo está configurado errado, não de que faltou permissão.

Cenário 3: "aqui funciona, no computador da minha irmã não"

A pasta foi copiada inteira, com node_modules e tudo, e na outra máquina o comando reclama de arquivo faltando ou de binário incompatível. A cura é sempre a mesma: apague node_modules na máquina de destino, rode npm ci e confira com npm ls. O que se transporta é o projeto — HTML, CSS de entrada, package.json e package-lock.json —, nunca a pasta de pacotes. Ela é descartável por desenho: nasce de um comando e morre com um rm -rf.

11. Resumo

Instalar com npm é colocar o motor e o comando do Tailwind dentro da pasta do projeto, com as versões anotadas em dois arquivos de texto. O motor (tailwindcss) transforma nomes de classe em CSS; a CLI (@tailwindcss/cli) lê os arquivos, chama o motor e escreve a folha final. O package.json guarda a lista e os apelidos de comando; o package-lock.json guarda as versões exatas; o node_modules guarda o código baixado, e é a única peça descartável das três.

Depois de instalar, o fluxo é sempre o mesmo: você escreve o CSS de entrada e o HTML, roda npm run build (ou o comando da CLI) e a página carrega o arquivo de dist. As três provas — npm ls, o arquivo com regras e a página com a aparência certa — respondem, nessa ordem, se o pacote chegou, se o build rodou e se o CSS está sendo aplicado. Quando algo falha, o silêncio do Tailwind diante de uma classe desconhecida é a pista mais útil: quase sempre é o nome.

Para lembrar

  • São dois pacotes: tailwindcss (motor) e @tailwindcss/cli (comando).
  • npm install -D anota em devDependencies: ferramenta de desenvolvimento.
  • package.json é a caderneta; package-lock.json é o mapa das versões.
  • node_modules não se edita, não se copia, não se publica.
  • npm ci reinstala exatamente o que o lock diz — o comando de outra máquina.
  • No terminal, npx @tailwindcss/cli; dentro de script, só tailwindcss.
  • -i é a entrada; -o é a saída; a saída é o que se liga na página.
  • O arquivo de saída é escrito pela ferramenta: não edite à mão.
  • Classe que não existe não gera regra e não avisa nada.
  • Terminal em silêncio, depois do build, é sinal de sucesso.

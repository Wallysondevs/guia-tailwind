Plugins

A Ana viu num vídeo uma linha que resolvia a formatação dos textos longos da página de receitas: @plugin "@tailwindcss/typography";. Copiou, colou no CSS, salvou e escreveu class="prose" no artigo. Nada aconteceu — nem a fonte mudou, nem apareceu erro na tela. Ela passou a manhã convencida de que o plugin estava quebrado. Não estava: faltava o pacote, e faltava entender o que é um plugin no Tailwind v4, onde ele mora e o que ele realmente entrega. Nesta aula a Ana instala, declara e confere um plugin de verdade — e descobre que metade das coisas que ela ia buscar num plugin dá para escrever em vinte linhas de CSS, com o @utility que ela mesma inventa.

  • Por que instalar o pacote com npm vem antes de declarar.
  • O que a prévia deste guia consegue — e o que ela não consegue — fazer com plugins.
  • Como criar a sua própria utilidade com @utility.
  • Como empacotar utilidades prontas com @apply dentro dela.
  • Como um plugin entrega um par: a utilidade e a variante.
  • Quando não vale instalar nada e o CSS do projeto resolve.

1. A cena: a linha colada do tutorial

O que a Ana fez foi o que quase todo mundo faz: começou pelo meio. Ela copiou a linha que aparece no topo do tutorial, sem a parte de cima — a instalação do pacote. No Tailwind v4, a linha sozinha não faz nada, e o pior é que ela falha em dois lugares diferentes: no CSS do navegador (onde não há sistema de arquivos para procurar o pacote) e no terminal (onde o erro aparece, mas só se você estiver olhando a saída do build).

Vale separar as duas coisas desde o começo, porque elas vivem em mundos diferentes. Plugin é o pacote: um pedaço de código publicado no npm, escrito por outra pessoa, que o seu projeto instala. @plugin é a linha do CSS que diz ao Tailwind para ler esse pacote e acrescentar o que ele traz. Uma coisa é a dependência; a outra é o aviso. Sem a primeira, a segunda é uma promessa vazia.

E antes de sair instalando: no v4, boa parte do que os plugins do v3 faziam virou CSS do próprio projeto. Cor nova, espaçamento novo, fonte nova, animação nova e variante nova se escrevem em @theme, @utility e @custom-variant, sem pacote nenhum. O plugin continua fazendo sentido para o que é grande demais para copiar: uma tipografia inteira com regras para título, lista, citação e tabela; um conjunto de estilos de formulário para todos os campos nativos. Esta aula mostra os dois caminhos e, principalmente, quando cada um é o certo.

2. O que um plugin acrescenta

Um plugin é um arquivo de código que recebe o Tailwind e mexe nele. Na prática, o que ele pode acrescentar cai em quatro gavetas, e é útil saber qual delas você está procurando antes de instalar qualquer coisa.

A primeira são utilidades novas: classes que não existem no Tailwind, como prose (o artigo inteiro formatado) ou form-input (o campo de formulário padronizado). A segunda são variantes novas: um prefixo que muda a condição de uma classe, como pointer-coarse: para telas de toque. A terceira são valores de tema: cores, fontes ou espaçamentos que passam a existir em bg-, text- e companhia. A quarta é CSS de base: regras que valem para tags, como ajustar a entrelinha de um blockquote.

utilidadesprose, form-inputtipografia, formulários
variantesnome:classecondições de dispositivo ou estado
valores de temabg-nome, font-nomepaletas e fontes de marca
CSS de basenada: muda tags diretoajustes de tipografia e de campo
plugin
Um pacote de código que acrescenta utilidades, variantes, valores de tema ou CSS de base ao Tailwind. Instalado com npm, como qualquer dependência.
@plugin
A linha do CSS de entrada que manda o Tailwind ler um plugin instalado: @plugin "@tailwindcss/typography";.
@utility
A regra do CSS de entrada que cria uma utilidade sua, com o nome que você escolher. É o jeito v4 de fazer, sem pacote, o que os plugins pequenos faziam.
@apply
Dentro de um @utility (ou de uma regra comum), aplica classes do Tailwind como declarações de CSS.
dependência
Um pacote que o seu projeto precisa para funcionar, listado no package.json e instalado em node_modules.
preflight
O CSS de base que o próprio Tailwind traz, zerando margens e tamanhos de título. Um plugin pode acrescentar regras ao lado dele.

Repare que nenhuma dessas gavetas é mágica: são as mesmas quatro coisas que você escreve à mão no @theme, no @utility e no @custom-variant. A diferença é o volume e a manutenção — um plugin de tipografia tem dezenas de regras que você não quer escrever, e alguém as mantém atualizadas para todas as combinações de título, lista e citação.

3. Onde ele mora no v4

No Tailwind v3, plugin era JavaScript de configuração. Você instalava o pacote e depois abria o tailwind.config.js para listar o plugin numa array. Eram dois arquivos, duas sintaxes e uma ordem que ninguém lembrava.

// v3: plugin declarado em JavaScript, dentro da configuração
module.exports = {
  plugins: [require("@tailwindcss/typography")],
};

No v4 o plugin passou a ser declarado no CSS, junto do @import, do @theme e das suas utilidades. O arquivo de configuração JavaScript não existe mais no fluxo normal, e a linha é curta:

@import "tailwindcss";

@plugin "@tailwindcss/typography";

Essa mudança tem uma consequência prática boa: tudo o que muda o Tailwind passa a estar num arquivo só, na ordem em que aparece — primeiro o import, depois os plugins, depois o tema, depois as suas utilidades. Quem abre o projeto vê a lista inteira de influências de uma vez, sem caçar arquivos. A ordem de leitura também serve de documentação: quem lê de cima para baixo sabe o que chega antes de quê, e é essa a ordem que você deve manter quando o projeto crescer.

Um detalhe de nomenclatura que confunde: o nome dentro do @plugin é o nome do pacote no npm, com arroba e barra quando houver. @plugin "@tailwindcss/forms"; aponta para o pacote @tailwindcss/forms. Não é um apelido, não é um caminho relativo: é o identificador exato do pacote instalado.

4. Instalar antes de declarar

Agora a parte que a Ana pulou. Plugin é dependência, e dependência se instala. No terminal, dentro da pasta do projeto, com o npm que você já conhece:

ana@notebook:~/padaria$ npm i -D @tailwindcss/typography
added 1 package, and audited 3 packages in 1s

O -D guarda o pacote em devDependencies, que é onde ficam as ferramentas que só existem durante o desenvolvimento e o build. Faz sentido: o navegador do cliente nunca baixa esse pacote, porque o que chega lá é o CSS já compilado, com as regras do plugin transformadas em CSS comum.

Se a instalação não aconteceu e você declarar o @plugin assim mesmo, o build para com uma mensagem parecida com “não consegui resolver o módulo”. É um erro bom, porque aparece no terminal na hora. O erro ruim é o outro: você instala, declara, e esquece de usar as classes — aí não há mensagem nenhuma, e o CSS fica sem as regras do plugin, porque o Tailwind só escreve o que encontra escrito no HTML.

Depois de instalar, duas conferências de dez segundos. A primeira: o pacote aparece no package.json? A segunda: o build roda sem reclamar? Se as duas respostas forem sim e a classe ainda não fizer nada, o problema é de uso, não de instalação — e a próxima seção explica por quê.

5. O que a prévia desta aula faz

Aqui no guia, as caixas compilam o seu HTML com o Tailwind de verdade, dentro do navegador, sem npm e sem pasta de projeto. Isso significa que elas não conseguem instalar pacotes: um @plugin escrito numa caixa não encontra o módulo e não gera regra nenhuma. Não é um defeito da caixa; é o mesmo comportamento de um projeto em que você esqueceu o npm i.

Por isso as caixas desta aula ensinam o que um plugin faz, escrevendo à mão o que ele entregaria. É a parte transferível do assunto: quando você instalar um plugin de verdade no seu projeto, as classes dele vão se comportar exatamente como as utilidades que você criar aqui. E há um bônus: o que você escrever na caixa é código de projeto, não brinquedo de exemplo — dá para copiar para o seu style.css e usar.

Guarde então a divisão: @plugin aparece nesta aula nos blocos de arquivo, como leitura; @utility aparece nas caixas, como prática. Um é instalação, o outro é autoria, e o v4 aproximou tanto os dois que muita gente hoje resolve com o segundo o que antes pedia o primeiro.

6. @utility: a utilidade que você inventa

O @utility é a peça mais útil desta aula. Ele cria uma classe nova, com o nome que você quiser, que se comporta como qualquer utilidade do Tailwind: aceita variante (hover:, md:), entra na camada certa do CSS e não é copiada para o HTML como estilo solto.

A sintaxe é a de uma regra comum, com o nome no lugar do seletor. Se você escrever @utility moldura { … }, a classe passa a ser moldura. Dentro, valem as propriedades de CSS que você já conhece, incluindo var() para os valores do tema. Na caixa abaixo, o cartão pede uma moldura de 2 px com cantos de 12 px, e a utilidade ainda não existe.

Crie a utilidade moldura: 2 px de borda, na cor var(--color-amber-400), e cantos de 12 px. O cartão deve ganhar a moldura.

<style type="text/tailwindcss">
/* a utilidade moldura ainda não existe */
</style>

<div id="alvo" class="moldura bg-amber-50 p-4">
  <p class="font-semibold">Pão quentinho</p>
  <p class="text-sm text-stone-600">Sai do forno às 6h.</p>
</div>
padding: 16px
background-color: oklch(0.987 0.022 95.277)

<style type="text/tailwindcss">
@utility moldura {
  border-width: 2px;
  border-color: var(--color-amber-400);
  border-radius: 12px;
}
</style>

<div id="alvo" class="moldura bg-amber-50 p-4">
  <p class="font-semibold">Pão quentinho</p>
  <p class="text-sm text-stone-600">Sai do forno às 6h.</p>
</div>

Antes de rodar, o painel mostra respiro e fundo, e a borda fica em 0px — o preflight zera as bordas de todo elemento, então “sem borda” é o estado de partida. Depois, aparecem border-width, border-color e border-radius. Repare que nada disso precisou de variante nem de tema: a utilidade é CSS seu, com nome de classe.

Duas coisas que o @utility faz e que valem a pena conhecer. A primeira: ele funciona com todas as variantes de graça — hover:moldura, md:moldura, dark:moldura passam a existir no momento em que a utilidade existe. A segunda: o nome pode ter hífen (selo-promo), e aí o CSS gerado escapa o hífen como faz com qualquer classe. E atenção à regra de ouro: utilidade não substitui componente. Se o bloco tem estrutura, filhos e estados, o lugar dele é o HTML com classes, não uma utilidade que tenta adivinhar tudo.

7. @utility com @apply: empacotando o que existe

Escrever CSS cru dentro de uma utilidade é chato quando você já tem as classes prontas. O @apply resolve: dentro do @utility, você liga as classes do Tailwind como se estivesse escrevendo CSS, e o compilador expande cada uma nas declarações correspondentes. É assim que nasce um “botão da casa” sem repetir oito classes em vinte lugares do HTML.

Crie a utilidade botao com @apply, juntando rounded-lg, bg-amber-500, px-4, py-2 e text-white. O botão deve ficar arredondado, âmbar e com texto branco.

<style type="text/tailwindcss">
/* a utilidade botao ainda não existe */
</style>

<button id="alvo" class="botao text-sm">
  Encomendar pão
</button>
font-size: 14px
line-height: 20px

<style type="text/tailwindcss">
@utility botao {
  @apply rounded-lg bg-amber-500 px-4 py-2 text-white;
}
</style>

<button id="alvo" class="botao text-sm">
  Encomendar pão
</button>

O CSS gerado mostra o que o @apply fez, e vale ler com atenção porque ele ensina duas coisas:

.botao {
  border-radius: var(--radius-lg);
  background-color: var(--color-amber-500);
  padding-inline: calc(var(--spacing) * 4);
  padding-block: calc(var(--spacing) * 2);
  color: var(--color-white);
}

Primeira: o @apply não copia texto, copia a regra. Onde a classe original dizia var(--color-amber-500), a utilidade também diz — ou seja, o botão continua acompanhando o tema, e trocar o âmbar no tema troca o botão junto. Segunda: px-4 virou padding-inline e py-2 virou padding-block. São as propriedades lógicas do CSS moderno, que respeitam a direção da escrita; o efeito visual é o mesmo, e é por isso que o painel desta caixa mostra padding-inline e padding-block em vez de um padding só.

O limite do @apply é o de sempre: ele serve para juntar o que já existe, não para esconder decisões. Uma utilidade com dez linhas de @apply é um componente fantasiado de classe, e no dia em que precisar de uma variação você vai brigar com ela. Uma a três classes por utilidade é o tamanho saudável; acima disso, use as classes direto no HTML e deixe o leitor ver as decisões.

8. Utilidade e variante: o par de um plugin de bolso

Olhe agora para o que um plugin pequeno costuma entregar: uma utilidade e, às vezes, uma variante que combina com ela. Você já sabe fazer as duas coisas, e juntá-las num arquivo é o que dá o efeito de “plugin caseiro” — sem pacote, sem npm, sem dependência para atualizar.

Na caixa abaixo, a variante promo já está escrita: ela vale para quem tem o atributo data-promo, que é o que o JavaScript do site põe quando o item entra em promoção. Falta a utilidade selo. O HTML já usa promo:selo, e é aí que a combinação aparece: a utilidade dá o formato de etiqueta, a variante decide quando ele vale.

Crie a utilidade selo: cantos totalmente redondos (9999px), fundo var(--color-amber-100) e respiro de 0.25rem 0.75rem. O preço em promoção deve virar uma etiqueta.

<style type="text/tailwindcss">
@custom-variant promo (&:where([data-promo]));

/* falta a utilidade selo */
</style>

<p id="alvo" class="text-amber-900 promo:selo" data-promo>
  Pão do dia, R$ 5
</p>
color: oklch(0.414 0.112 45.904)

<style type="text/tailwindcss">
@custom-variant promo (&:where([data-promo]));

@utility selo {
  border-radius: 9999px;
  background-color: var(--color-amber-100);
  padding: 0.25rem 0.75rem;
}
</style>

<p id="alvo" class="text-amber-900 promo:selo" data-promo>
  Pão do dia, R$ 5
</p>

Quando a utilidade passa a existir, a classe que já estava no HTML ganha a regra dela com a condição da variante em volta. É o mesmo mecanismo de hover:bg-…, só que com dois pedaços que você escreveu. E repare no valor 9999px: dentro de uma utilidade própria, você escreve CSS de verdade, com valores de verdade. Se quiser usar o arredondamento do tema, escreva @apply rounded-full e deixe o tema mandar.

Com as três ferramentas na mão, a decisão fica fácil de resumir:

O que você precisaOnde escreverPor quê
uma cor, fonte ou espaço do projeto@themevira classe e variável, sem pacote
uma classe nova com CSS seu@utilityaceita variante e vive na camada certa
uma condição nova, com nome@custom-variantprefixo reutilizável no HTML
tipografia inteira, formulários completos@plugin + npmvolume grande, mantido por outra pessoa

A régua prática: se você consegue escrever a regra em menos de dez linhas e ela é só sua, escreva. Se o pacote tem dezenas de regras entrelaçadas e uma documentação própria, instale. O que não vale é instalar um plugin de três utilidades e depois passar a tarde tentando sobrescrever o que ele faz — nesse caso, as três linhas de @utility teriam resolvido na primeira tentativa.

9. Cenários do dia a dia

Cenário 1: o plugin declarado que não faz nada

Ela colou @plugin "@tailwindcss/typography";, escreveu prose no artigo e nada mudou. Três suspeitos, na ordem em que se conferem: o pacote não está instalado (falta o npm i -D); o build não rodou de novo (o CSS está velho); ou a classe está escrita em outro lugar que não o HTML que o build lê. O primeiro dá erro no terminal, o segundo dá CSS desatualizado, o terceiro dá silêncio total. Nenhum dos três é bug do plugin.

Cenário 2: dois plugins mexendo na mesma tag

Um plugin de tipografia ajusta a entrelinha do blockquote; um plugin de formulário mexe no input. Enquanto os dois tocam tags diferentes, tudo bem. O problema aparece quando dois plugins escrevem na mesma camada de base: vale a ordem em que os @plugin foram declarados, e aí a ordem do arquivo passa a ser uma decisão de desenho. Se a página ficou estranha só depois de instalar o segundo, é ali que se olha primeiro.

Cenário 3: o plugin que virou CSS do projeto

A Ana usava um plugin pequeno do v3 que criava três utilidades de etiqueta. Na migração para o v4, descobriu que ele não era mais necessário: as três utilidades cabiam em vinte linhas de @utility, sem dependência para atualizar e sem risco de o pacote abandonar o projeto. Ela copiou o comportamento, apagou o pacote e ganhou uma pasta node_modules menor. Nem toda migração precisa de plugin — muitas precisam de menos.

Exercício: a utilidade do selo

O selo de promoção precisa de cantos totalmente redondos. Complete a linha que declara a utilidade, usando o nome que o HTML já espera:

@utility { border-radius: 9999px; }

Dica: é o mesmo nome que aparece na classe promo:selo. Sem o @utility, essa classe não existe no CSS — e o HTML fica com um prefixo que não gera nada.

11. Resumo

Plugin é pacote; @plugin é a linha do CSS que manda o Tailwind lê-lo. No v4 essa linha mora no mesmo arquivo do @import, no lugar do plugins: do tailwind.config.js, e o pacote precisa estar instalado com npm antes. Um plugin pode trazer utilidades, variantes, valores de tema e CSS de base — as mesmas quatro gavetas que você preenche à mão com @theme, @custom-variant e @utility.

Antes de instalar, pergunte o tamanho: menos de dez linhas de regra é @utility; dezenas de regras entrelaçadas e mantidas por outra pessoa é plugin. E lembre que, nas caixas deste guia, o @plugin não tem como funcionar — não há npm dentro da prévia —, mas o @utility funciona igual ao do seu projeto, e o que você escrever ali serve para copiar.

Para lembrar

  • Plugin é pacote instalado com npm; @plugin é a declaração no CSS.
  • No v4 não há plugins: em JavaScript: tudo fica no CSS de entrada.
  • O nome no @plugin é o do pacote, com @ e barra quando houver.
  • Pacote ausente dá erro no build; classe esquecida no HTML não dá erro nenhum.
  • Um plugin pode trazer utilidade, variante, valor de tema e CSS de base.
  • @utility nome { … } cria a classe nome, com variantes de graça.
  • @apply dentro da utilidade expande classes em declarações e mantém as variáveis do tema.
  • Utilidade é para uma ou duas decisões; bloco grande é componente no HTML.
  • Utilidade + variante no mesmo arquivo é o “plugin de bolso”, sem dependência.
  • Regra prática: menos de dez linhas, escreva; dezenas de regras, instale.

Mobile First

A Ana desenhou o cartão do pão olhando para o monitor do balcão: duas colunas, respiro grande, texto de 18 px. Depois “adaptou” para o celular, cortando o que não cabia. O resultado ficou ruim nas duas pontas — apertado no telefone, esparramado no monitor. Nesta aula ela vira o processo de cabeça para baixo e aprende o jeito que o Tailwind foi pensado para ser usado: começar pelo desenho menor, o do celular, e crescer a partir dele. O nome disso é mobile first, e não tem nada de moda passageira: é uma ordem de decisão que deixa o CSS menor e mais fácil de consertar.

Você vai aprender
  • O que “mobile first” quer dizer de verdade (e o que não quer).
  • Por que a classe sem prefixo é a mais importante de todas.
  • Como montar uma escada de respiro e de colunas do menor para o maior.
  • Por que a ordem das classes no HTML não muda nada, e o que muda de fato.
  • Como reconhecer uma escada invertida e consertá-la.
  • O caminho prático para refazer um cartão começando por 375 px.
  • Quando o melhor breakpoint é nenhum: layouts que se adaptam sozinhos.

1. A cena: o cartão que ficou ruim nas duas pontas

O cartão da Ana tinha, no monitor, duas colunas: a foto do pão de um lado, o texto do outro, com 32 px de respiro em volta e o título em 24 px. Bonito. No celular, o mesmo cartão herdava respiro de 32 px, título de 24 px e duas colunas de 160 px cada — o texto cabia em três palavras por linha e o preço saía pela borda. A “adaptação” dela foi apagar coisas no celular, o que quase sempre termina num desenho pobre para quem está no telefone.

O erro não foi de classe, foi de ordem. Ela desenhou o caso mais espaçoso primeiro e tratou o celular como exceção — um lugar onde se corta. O Tailwind, e boa parte do mundo do CSS moderno, faz o contrário: o caso pequeno é a regra, e o caso grande é que recebe acréscimos. A razão é prática. Numa tela estreita não sobra espaço para nada: o que não é essencial simplesmente não cabe. Se você começa por ela, cada elemento que sobrevive já passou pelo teste mais duro. Depois é só dar mais ar e mais colunas conforme o espaço aparece.

Há também uma razão de manutenção. Quando a base é o celular, um componente novo no projeto já nasce funcionando em qualquer tela: ele não tem nada de especial para telas grandes, então aparece igual em todas. Você só acrescenta um degrau quando o conteúdo pede. Na ordem contrária, todo componente novo nasce “de desktop” e precisa de uma correção para o celular — e é sempre a correção que alguém esquece de fazer.

Uma última vantagem, que parece técnica mas aparece no dia a dia: se o CSS falhar em carregar pela metade, ou se o navegador for antigo e ignorar uma media query, o que sobra é o desenho base — uma coluna, texto legível, tudo empilhado. Um site mobile-first degrada bem. Um site desktop-first degrada em duas colunas espremidas numa tela de 400 px.

2. O que “mobile first” quer dizer

O nome engana. “Mobile first” não quer dizer “faça um site para celular” nem “esconda coisas no celular”. Quer dizer que a primeira decisão de cada componente é tomada pensando no menor espaço, e as seguintes são acréscimos para espaços maiores. A tradução mais honesta seria “do menor para o maior”.

No Tailwind, isso aparece na própria sintaxe: a classe sem prefixo vale em todas as larguras, e o prefixo só acrescenta uma condição “a partir daqui”. Não existe, na escala padrão, um prefixo que diga “só no celular” — e isso é de propósito. Se a base vale em todo lugar, você é obrigado a pensar no pequeno primeiro; o grande é sempre um ajuste.

base
A classe sem prefixo (p-3, grid-cols-1). Vale em qualquer largura e é o desenho do celular.
degrau
Cada ponto em que você acrescenta uma mudança: sm:, md:, lg:.
escada
O conjunto dos degraus de um componente, sempre do menor para o maior.
acréscimo
O jeito certo de usar um degrau: só dizer o que muda, sem repetir o que já vale abaixo.
intrínseco
Layout que se adapta sozinho ao espaço, sem breakpoint: flex-wrap, auto-fit, largura em porcentagem.

Há um detalhe do mundo real que vale trazer para cá: o celular mais estreito ainda em uso tem cerca de 320 px, e os mais comuns ficam entre 360 e 430. Se o seu desenho base funciona em 375, provavelmente funciona em 320 com um ou outro ajuste. Comece a testar por 375, que é o número que os inspetores usam como padrão, e depois desça até 320 para ver se nada estoura.

3. A base vale em todo lugar

Antes de qualquer breakpoint, o componente precisa ficar decente sem nenhum prefixo. Isso quer dizer três coisas: uma coluna, respiro modesto e texto em tamanho de leitura normal. No cartão da padaria, a base ficou flex flex-col gap-3 p-3 — empilhado, com 12 px de respiro. É feio no monitor? Um pouco. Mas é correto em qualquer lugar, e é a partir dele que os degraus vão trabalhar.

A base é também o que salva o componente quando alguém usa o site num aparelho esquisito: uma TV, um leitor de ebook, uma janela estreita no meio de dois monitores. Nenhum desses casos tem breakpoint próprio, e todos caem na base. Por isso ela não é “a versão do celular”: é a versão de todo mundo, com os degraus servindo de exceção para quem tem mais espaço.

Na prática, você escreve a base uma vez e nunca mais mexe nela. Cada degrau só acrescenta o que muda. Se o respiro é 12 px no celular e 24 no tablet, você não escreve p-6 na base e md:p-3 — escreve p-3 e md:p-6. A diferença parece cosmética e não é: na primeira versão, o celular herda 24 px e você precisa de outro degrau para corrigir; na segunda, o valor cresce quando há espaço, e não há nada para corrigir.

Uma confusão comum é achar que a base “é aplicada primeiro e depois substituída”. Não é bem isso. Todas as regras que casam valem ao mesmo tempo; o que decide quem pinta por último é a ordem no CSS gerado, e o Tailwind põe a base antes e os degraus depois, em ordem crescente. Você pode pensar como substituição — é uma boa simplificação — mas o mecanismo é ordem.

4. A escada do cartão: p-3, sm:p-6, md:p-8

Com a base pronta, cada degrau responde a uma pergunta: “o que passa a caber aqui?”. A partir de 640 px, o cartão ganha respiro médio. A partir de 768, mais respiro e talvez o texto maior. A partir de 1024, o cartão pode virar duas colunas. Nada disso é obrigatório: você acrescenta degraus só onde o conteúdo pede.

DegrauLarguraO que costuma mudar no cartão
basede 0 pxuma coluna, respiro de 12 px, tudo empilhado
sm:640 pxrespiro de 24 px; o texto ganha um degrau
md:768 pxfoto e texto lado a lado; respiro de 32 px
lg:1024 pxo cartão entra numa grade de três; respiro de 48 px

Na caixa abaixo, o cartão está com o respiro de celular e nada mais. A missão é subir a escada em três degraus. Repare que não há nada para apagar: o p-3 continua valendo em todas as larguras, e cada novo degrau assume a partir do seu ponto. É a escada no sentido literal — cada passo em cima do anterior.

Suba o respiro conforme a tela cresce: mantenha p-3, acrescente sm:p-6, md:p-8 e lg:p-12 ao cartão.

<div id="alvo" class="rounded-xl bg-amber-50 p-3">
  <p class="text-base font-semibold">Pão de queijo</p>
  <p class="text-sm text-stone-600">Assado às 6h, sai quentinho.</p>
</div>

background-color: oklch(0.987 0.022 95.277)
border-radius: 12px

<div id="alvo" class="rounded-xl bg-amber-50 p-3 sm:p-6 md:p-8 lg:p-12">
  <p class="text-base font-semibold">Pão de queijo</p>
  <p class="text-sm text-stone-600">Assado às 6h, sai quentinho.</p>
</div>

Com a solução rodada, o painel mostra o respiro da largura em que você está agora: 12 px abaixo de 640, 24 px entre 640 e 768, 32 px entre 768 e 1024, e 48 px acima disso. Se você arrastar a janela devagar, vai ver os saltos. O valor de partida que está impresso no painel é o do HTML inicial — 12 px, que é o único valor que não depende de janela nenhuma.

Antes de seguir, um teste de sanidade: a escada tem quatro degraus e três prefixos. Se você contar seis classes de respiro num elemento, provavelmente está repetindo valores ou usando dois prefixos para a mesma coisa. Uma propriedade, uma escada. Escadas paralelas — uma para respiro, uma para tamanho de texto — são normais e esperadas; duas escadas para a mesma propriedade, não.

5. O CSS gerado e a ordem que resolve tudo

Aqui está o motivo de a escada funcionar. Quando você escreve p-3 sm:p-6 md:p-8, o Tailwind gera as regras nesta ordem, com a base primeiro e os degraus em ordem crescente:

.p-3 {
  padding: calc(var(--spacing) * 3);
}
@media (width >= 40rem) {
  .sm\:p-6 {
    padding: calc(var(--spacing) * 6);
  }
}
@media (width >= 48rem) {
  .md\:p-8 {
    padding: calc(var(--spacing) * 8);
  }
}

Numa tela de 800 px, as três regras casam ao mesmo tempo: a janela é maior que 0, maior que 640 e maior que 768. Quem decide o valor final é a última que aparece no arquivo — a do md, que está embaixo. É a cascata do CSS fazendo o trabalho, e é por isso que a ordem em que você escreve as classes no atributo não importa: p-3 sm:p-6 md:p-8 e md:p-8 sm:p-6 p-3 geram o mesmo CSS, na mesma ordem.

Isso tem uma consequência que muita gente custa a aceitar: não existe “forçar” um valor colocando a classe por último. Se você quer que o celular tenha 24 px e o desktop 12 px, escrever md:p-3 p-6 não resolve — no desktop, o md:p-3 vai vencer de qualquer jeito, porque ele está mais abaixo no CSS. A única forma de ter um valor menor no desktop é usar um prefixo max-, ou repensar o desenho.

E é justamente aí que nasce a escada invertida, o erro da próxima seção. Quem vem do desktop pensa “no computador é grande, no celular é pequeno” e traduz isso como p-8 md:p-2. O CSS é gerado na ordem certa, mas o desenho fica ao contrário do que se quer: 32 px no celular e 8 px no desktop.

6. A escada invertida e como consertar

O sintoma é fácil de reconhecer: o componente fica apertado na tela grande e folgado na pequena. No cartão da Ana, isso apareceu quando ela copiou um bloco de um modelo pronto e colou no projeto: class="rounded-xl bg-amber-50 p-8 md:p-2". No monitor, 8 px de respiro — o texto quase encostava na borda. No celular, 32 px — metade da tela comido pelo respiro.

Na caixa seguinte, o cartão está assim de propósito. A missão é inverter: 8 px no celular, 24 px a partir de 640 e 32 px a partir de 768. Isso quer dizer trocar a base e montar a escada para cima. A classe p-8 tem de sair; se ela ficar, volta a valer em todas as larguras e a escada perde o sentido.

Conserte a escada invertida: o cartão está com p-8 md:p-2. Deixe p-2 na base, sm:p-6 a partir de 640 e md:p-8 a partir de 768.

<div id="alvo" class="rounded-xl bg-amber-50 p-8 md:p-2">
  <p class="text-base font-semibold">Broa de milho</p>
  <p class="text-sm text-stone-600">Feita com milho da roça.</p>
</div>
padding: 32px
background-color: oklch(0.987 0.022 95.277)
border-radius: 12px

<div id="alvo" class="rounded-xl bg-amber-50 p-2 sm:p-6 md:p-8">
  <p class="text-base font-semibold">Broa de milho</p>
  <p class="text-sm text-stone-600">Feita com milho da roça.</p>
</div>

O painel de partida também depende da janela, e isso aqui ajuda a entender o problema: numa janela larga ele mostra 8 px, porque o md:p-2 já venceu a base — o cartão abre com o respiro de celular num monitor. Estreite a janela para menos de 768 e o valor salta para 32 px, o respiro de monitor num telefone. Depois da correção, a leitura fica intuitiva: 8 px abaixo de 640, 24 px entre 640 e 768, 32 px acima disso. O número final no monitor pode ser o mesmo de antes; o que muda é o caminho até ele.

O que o md:p-2 fazia, para quem quiser ver no CSS: ele gera uma regra dentro do @media (width >= 48rem), que aparece depois da base. O arquivo sai assim:

.p-8 {
  padding: calc(var(--spacing) * 8);
}
@media (width >= 48rem) {
  .md\:p-2 {
    padding: calc(var(--spacing) * 2);
  }
}

No desktop, a regra de baixo vence a de cima e o cartão fica com 8 px. No celular, a media query não vale e sobra o p-8, com 32 px. Ou seja: o CSS está correto, obedecendo a ordem; o desenho é que está ao contrário. Quem escreve max-md: no lugar de md: também consegue o efeito — mas paga o preço de manter uma lógica invertida em todos os componentes.

7. Refazendo o cartão, do celular para fora

O roteiro que a Ana passou a seguir tem quatro passos. Primeiro, abra a página numa largura de 375 px e escreva só a base, sem nenhum prefixo: uma coluna, texto legível, respiro pequeno. Segundo, aumente para 640 e pergunte o que passa a caber — normalmente respiro e um tamanho de texto. Terceiro, vá para 768 e veja se duas colunas fazem sentido. Quarto, vá para 1024 e decida se o cartão entra numa grade.

A regra de ouro é nunca “desfazer” no degrau maior. Se você se pegar escrevendo um valor menor num prefixo, é sinal de que a base está errada: conserte a base, não o degrau. Isso vale para respiro, tamanho de texto, largura e visibilidade. Um componente mobile-first tem uma base simples e degraus que só acrescentam.

Na caixa abaixo, o cartão da padaria está empilhado — foto em cima, texto embaixo, botão no fim. A partir de 640 px, o conteúdo deve ficar em linha e alinhado ao centro, que é como o cartão fica bonito quando há largura sobrando. São dois acréscimos, e o flex-col da base continua lá.

No celular o cartão fica empilhado (já está). A partir de 640 px, ponha foto, texto e botão em linha, alinhados ao centro: acrescente sm:flex-row e sm:items-center.

<div id="alvo" class="flex flex-col gap-3 rounded-xl bg-amber-50 p-3">

Duas coisas para observar na prévia depois de rodar. A primeira: no celular, o botão fica embaixo do texto e ocupa só o necessário — se você quisesse o botão de largura cheia ali, usaria w-full sm:w-auto, outro par clássico de escada. A segunda: o gap-3 não mudou. Espaço entre elementos é uma decisão que costuma valer em todas as larguras; mudar o respiro de dentro do cartão já é suficiente para dar a sensação de folga.

Esse é o padrão que você vai repetir em tudo: empilhar no celular, alinhar em linha quando houver espaço. Cabeçalho, cartão de produto, rodapé, formulário de duas colunas — quase todos começam com flex-col e ganham sm:flex-row ou md:flex-row no degrau em que a linha deixa de espremer o texto.

8. Quando não existe breakpoint no código

Nem todo layout precisa de escada. Alguns se adaptam sozinhos, e são a melhor invenção do CSS para quem não quer manter vinte breakpoints. O flex-wrap é o exemplo mais simples: os itens vão para a linha de baixo quando não cabem, em qualquer largura, sem uma media query sequer. O grid com auto-fit faz o mesmo com colunas, criando e removendo colunas conforme o espaço. Larguras em porcentagem e max-w-* também dispensam breakpoint.

A regra prática: se o layout pode se resolver com fluxo (quebra de linha, colunas automáticas, limite de largura), prefira isso. Breakpoint é para quando a decisão muda de natureza — duas colunas viram três, o menu some, o texto cresce um degrau. Se o que muda é só “cabe ou não cabe”, o navegador sabe resolver melhor do que você.

NecessidadeMobile first (escada)Sem breakpoint
Cartões lado a lado quando há espaçomd:grid-cols-2grid-cols-[repeat(auto-fit,minmax(220px,1fr))]
Botões que não cabem na linhasm:flex-nowrapflex-wrap
Texto que não pode ficar largo demais2xl:max-w-3xlmax-w-prose
Imagem que estoura a colunamd:w-1/2w-full max-w-full
Respiro que acompanha a telap-3 sm:p-6 md:p-8p-[3vw] com moderação

A última linha merece um aviso: valor em vw (porcentagem da largura da janela) é tentador e vira armadilha. Em telas muito estreitas, o texto pode ficar ilegível; em telas muito largas, o respiro fica absurdo. Use quando quiser mesmo que o valor acompanhe a tela de forma contínua, e teste nas duas pontas. Para quase todo o resto, a escada de três ou quatro degraus é mais previsível.

9. Cenários do dia a dia

Cenário 1: o menu que ela esqueceu de olhar

O site estava todo mobile-first, menos o menu, que ela fez antes de aprender. Resultado: no celular, seis links espremidos numa linha, dois deles cortados. A correção foi refazer o menu como escada: base com o botão de abrir e os links escondidos; a partir de 768, os links aparecem em linha e o botão some. Note que a base é o estado mais simples — o menu fechado — e o degrau acrescenta o que só cabe em tela grande. Fazer o contrário, com o menu aberto por padrão, obrigaria a esconder coisas no celular.

Cenário 2: o formulário de duas colunas que virava uma bagunça

O formulário de encomenda tinha nome e telefone lado a lado, com 50% cada. No celular, cada campo ficou com 160 px e o número do telefone era cortado no meio. A correção foi a escada clássica: grid-cols-1 sm:grid-cols-2 gap-3. Duas colunas só quando houver espaço para dois campos inteiros. Detalhe: ela manteve a ordem dos campos igual à ordem de leitura, para quem navega por teclado não pular de um lado para o outro da tela.

Cenário 3: a tabela de preços e o “não dá para empilhar”

Nem todo conteúdo pode virar coluna. A tabela de preços com quatro colunas não faz sentido empilhada, porque o visitante precisa comparar linha com linha. A solução foi manter a tabela como está e dar a ela rolagem horizontal própria, com um aviso discreto. Mobile-first não é uma regra que obriga a empilhar tudo: é uma ordem de decisão que, neste caso, decidiu que a tabela continua tabela — só que rolando dentro do seu espaço.

Exercício: a grade da vitrine

A vitrine já tem grid grid-cols-1 gap-3 na base — uma coluna no celular. Complete com a classe que faz duas colunas a partir de 768 px:

<div class="grid grid-cols-1 gap-3 ">

Dica: o prefixo é o do ponto de 768 px, e a utilidade continua sendo grid-cols-2. Se você escrever grid-cols-2 sozinho, a vitrine fica com duas colunas até no celular.

11. Resumo

Mobile first é uma ordem de decisão, não um tipo de site: a classe sem prefixo desenha o caso menor e vale em todo lugar; os degraus sm:, md:, lg: só acrescentam o que passa a caber quando há espaço. O Tailwind gera o CSS nessa ordem — base primeiro, degraus crescentes — e é por isso que a última regra vence numa tela larga e a ordem do atributo class não muda nada.

A escada invertida (p-8 md:p-2) é o erro clássico de quem desenha no monitor e adapta depois; o remédio é inverter a base e montar os degraus para cima. E nem tudo precisa de breakpoint: flex-wrap, auto-fit e max-w-* resolvem sozinhos o que é só questão de “cabe ou não cabe”.

Para lembrar

  • Base sem prefixo = o desenho do celular, e vale em todas as larguras.
  • Cada degrau só acrescenta o que muda; nunca repita o que já vale abaixo.
  • A ordem das classes no HTML não importa: o CSS gerado é que manda.
  • Se você escreve um valor menor num prefixo, a base está errada.
  • Teste em 375 px primeiro; depois 640, 768 e 1024.
  • Empilhar no celular e virar linha com sm:flex-row é o padrão mais comum.
  • flex-wrap, auto-fit e max-w-prose dispensam breakpoint.
  • vw para respiro é tentador e traiçoeiro: teste nas duas pontas.
  • Nem todo conteúdo pode ser empilhado; tabela pode rolar dentro do próprio espaço.
  • Mobile first degrada bem: se o CSS falhar, sobra uma coluna legível.

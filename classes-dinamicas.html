Classes Dinâmicas

A Ana aprendeu um pouco de JavaScript e montou a vitrine dos pães do dia com um laço: para cada pão da planilha, cria um cartão e escolhe a cor pelo estado dele. No celular funcionou, no notebook funcionou, e no sábado — justo no sábado — os cartões do pão esgotado saíram sem cor nenhuma. Ela conferiu o código três vezes, o nome estava certo, e o Tailwind parecia não ter visto. É que ele não vê: o Tailwind lê texto, não executa o seu programa. Nesta aula a Ana entende por que metade das classes calculadas funciona e metade não, e aprende as três saídas que resolvem isso de vez.

Você vai aprender
  • O que o Tailwind faz quando lê o seu projeto — e o que ele não faz.
  • Por que "bg-" + cor + "-100" nunca vira CSS.
  • A regra de ouro: o nome inteiro tem de estar escrito em algum lugar.
  • O mapa de classes: escolher entre nomes completos em vez de montar pedaços.
  • Estado que muda: atributo no HTML e variante na classe.
  • Valor que muda: variável de CSS em vez de nome de classe.
  • Como forçar classes no build de verdade, e por que isso é o último recurso.
  • Onde procurar quando uma classe aparece na tela e não no CSS.

1. A cena: o cartão que saiu sem cor

A vitrine da Ana tem uma regra de negócio simples: pão fresquinho aparece em âmbar claro; pão que acabou aparece em cinza. A planilha tem uma coluna estado, com dois valores, fresco e esgotado. O código dela, simplificado, fazia isto:

const cores = { fresco: "bg-amber-100", esgotado: "bg-stone-100" };
cartao.className = "p-4 " + cores[pao.estado];

Esse código está correto, e produz class="p-4 bg-amber-100" no navegador. O problema aparece antes: o Tailwind precisa ter escrito a regra .bg-amber-100 no CSS, e para isso ele tem de ter encontrado o texto bg-amber-100 em algum arquivo do projeto. Aqui ele encontrou — o nome está no objeto cores, inteiro, entre aspas. Por isso funcionou por dois meses.

No sábado, ela quis uma terceira cor: pão de queijo, que vende rápido, em verde. Escreveu queijo: "bg-" + "green" + "-100" para “economizar repetição”. O navegador recebeu class="p-4 bg-green-100" corretamente. E o cartão saiu sem cor, porque no projeto inteiro nunca apareceu o texto bg-green-100 — apenas três pedaços que, juntos, formam aquele nome quando o programa roda. E o programa roda no navegador de quem visita; o Tailwind rodou antes, na compilação, e já foi embora.

Essa é a assimetria que causa todos os problemas deste assunto: o Tailwind olha o texto do arquivo, no momento do build; o seu código monta strings no navegador, no momento do uso. São dois momentos diferentes, e nada no primeiro adivinha o que o segundo vai produzir.

2. O que o compilador realmente faz

Vale entender o mecanismo, porque ele explica até os casos esquisitos. O Tailwind não tem uma lista de classes possíveis que ele aplica: ele faz o caminho contrário. Varre os arquivos do projeto procurando palavras que pareçam nomes de classe, e para cada candidato que reconhece, escreve a regra correspondente. É por isso que o CSS gerado é pequeno, e é por isso que classe não usada não existe nele.

Nessa varredura, ele não sabe o que é HTML, o que é JavaScript ou o que é comentário: tudo é texto. Uma classe citada num comentário gera CSS. Uma classe dentro de uma string que nunca é usada também gera. Uma classe montada por concatenação não gera nada, porque o texto que existe no arquivo é "bg-" +, e isso não é um nome de classe.

Daí a regra de ouro desta aula, e ela cabe numa frase: o nome completo da classe tem de estar escrito em algum arquivo que o Tailwind lê. Não importa se ele vai ser usado, nem se está num ramo de código que nunca roda; importa que exista como texto inteiro. Todo o resto é consequência.

Um detalhe que tranquiliza: o Tailwind é generoso com o que aceita como “texto inteiro”. Ele acha nomes em atributos, em strings, em objetos, em listas, em comentários. Então escrever as classes num objeto de mapa, como a Ana fez no começo, é a solução normal — não é gambiarra, é o jeito recomendado. O que não funciona é esconder o nome atrás de uma conta.

varredura
A passada do compilador pelos arquivos do projeto, procurando texto que pareça nome de classe. Acontece no build, antes de qualquer código rodar.
candidato
Cada palavra que a varredura encontra e testa. Se o Tailwind reconhece a palavra como classe, escreve a regra; se não, ignora sem avisar.
nome completo
O nome da classe inteiro, escrito em um só pedaço de texto: bg-green-100. É a única forma que a varredura enxerga.
mapa de classes
Um objeto com uma chave por estado e o nome completo do outro lado. Escolher a chave é seguro; montar o nome não é.
estado
A condição que muda o visual de um bloco — fresco, esgotado, pronto. Quando o conjunto é finito, vira atributo no HTML e variante na classe.
valor livre
O que não cabe numa lista: a cor escolhida pelo cliente, uma medida, um progresso. Vai para uma variável de CSS, não para o nome da classe.

3. A regra de ouro, e o que ela proíbe

Com a regra na mão, fica fácil classificar o que serve e o que não serve. A tabela abaixo mostra formatos comuns de código e o que o compilador vê em cada um.

No seu códigoGera CSS?Por quê
"bg-amber-100"simo nome inteiro está escrito
"bg-" + cor + "-100"nãonunca existe o texto bg-amber-100
`bg-${cor}-100`nãoé a mesma concatenação, com outra sintaxe
pronto ? "bg-green-100" : "bg-amber-100"simos dois nomes aparecem inteiros
"bg-" + (pronto ? "green" : "amber") + "-100"nãoa decisão acontece longe do nome
"p-4 " + mapa[estado]simo mapa guarda nomes completos

Repare na quarta linha: escolher entre duas strings inteiras é seguro, e é o padrão que se usa em todo projeto. O que mata é o pedaço variável no meio do nome. A diferença parece pequena quando você escreve, e é enorme quando o compilador lê.

Vale conhecer a forma mais elegante da mesma ideia, porque ela também ajuda a organizar o código. Em vez de espalhar ifs, você declara um mapa único, com uma chave por estado e o nome completo do outro lado:

const classes = {
  fresco:   "bg-amber-100 text-amber-900",
  esgotado: "bg-stone-100 text-stone-500",
  queijo:   "bg-green-100 text-green-900",
};
cartao.className = "p-4 rounded-xl " + classes[pao.estado];

Três vantagens de uma vez: todos os nomes existem como texto, então o CSS é gerado; o mapa é o único lugar onde a decisão de cor mora, então mudar o visual de “esgotado” é uma linha; e quem lê o arquivo entende as três variações sem abrir o HTML. Se o mapa crescer a ponto de ficar ilegível, é sinal de que o desenho tem estados demais — não de que o mapa está errado.

4. A primeira missão: juntar os pedaços

Na caixa abaixo está o código da Ana antes do sábado, reduzido ao essencial. O elemento carrega as duas partes separadas em atributos data-, como o JavaScript fazia antes de juntar. O Tailwind não encontra o nome completo, então a regra de fundo não existe — e o painel mostra só o respiro e a cor do texto.

O fundo está partido em data-cor e data-tom. Escreva o nome inteiro da classe no atributo class e rode: o cartão deve ficar âmbar claro.

<div id="alvo" class="p-4 text-amber-900" data-cor="bg-amber" data-tom="100">
  <p class="font-semibold">Pão de queijo</p>
  <p class="text-sm">Sai do forno às 6h.</p>
</div>
padding: 16px
color: oklch(0.414 0.112 45.904)

<div id="alvo" class="p-4 text-amber-900 bg-amber-100" data-cor="bg-amber" data-tom="100">
  <p class="font-semibold">Pão de queijo</p>
  <p class="text-sm">Sai do forno às 6h.</p>
</div>

Depois de rodar, o painel ganha a linha do fundo. Nada mudou no Tailwind, nada foi instalado: o que mudou é que agora existe no texto uma classe que ele reconhece. Guarde a sensação, porque é sempre o mesmo conserto — trocar uma conta por um nome.

E se o nome viesse de um lugar onde você não pode escrever? Aí é sinal de que a escolha está no lugar errado. Quem decide se o pão está fresco é a planilha, e isso é dado; a cor de cada estado é desenho, e isso é código seu. O dado pode mudar à vontade sem quebrar nada, desde que o desenho esteja escrito. Na prática: o mapa fica no arquivo, e o JavaScript só escolhe a chave.

5. Quando o estado muda: atributo e variante

Cor por estado é o caso mais comum, e tem um jeito de escrever que dispensa JavaScript para trocar classe: deixe o atributo contar o estado e a classe perguntar sobre ele. O Tailwind tem variantes para atributos data-*, e elas leem o valor do atributo no momento em que o navegador desenha.

Na caixa abaixo, o cartão já tem data-estado="pronto", que é o que o sistema de pedidos grava quando o pão sai do forno. Falta a classe dizer o que fazer com isso. A vantagem aparece no dia seguinte: se o estado virar esperando, é o atributo que muda, e nenhuma classe é remontada — o CSS já tem as duas.

Acrescente ao cartão a classe que pinta o fundo de verde quando data-estado for pronto: data-[estado=pronto]:bg-green-100.

<div id="alvo" class="p-4 text-green-900" data-estado="pronto">
  <p class="font-semibold">Pedido 42</p>
  <p class="text-sm">Pão de queijo, 6 unidades.</p>
</div>
padding: 16px
color: oklch(0.393 0.095 152.535)

<div id="alvo" class="p-4 text-green-900 data-[estado=pronto]:bg-green-100" data-estado="pronto">
  <p class="font-semibold">Pedido 42</p>
  <p class="text-sm">Pão de queijo, 6 unidades.</p>
</div>

O seletor que o Tailwind escreve é literal e não precisa de nenhum código rodando: [data-estado="pronto"]. Isso significa que a mesma classe serve para todos os pedidos, e que a decisão “verde ou cinza” saiu do JavaScript e foi para o CSS — que é justamente onde ela é desenhada.

O CSS gerado mostra a condição escrita por extenso no seletor, e vale ver a forma exata porque ela explica o comportamento:

.data-\[estado\=pronto\]\:bg-green-100[data-estado="pronto"] {
  background-color: var(--color-green-100);
}

Leia como uma frase: “o elemento que tem esta classe e o atributo data-estado igual a pronto recebe o fundo”. Como o navegador reavalia o seletor a cada mudança de atributo, trocar o valor no elemento basta — e o CSS já tem as regras de todos os estados escritos.

Outros estados seguem a mesma receita: data-[estado=esperando]:bg-stone-100, data-[estado=entregue]:bg-amber-50. Todas escritas por inteiro, todas no CSS final. E como o atributo é lido na hora, a troca é instantânea, sem recarregar e sem recompilar. Este é o caminho preferido quando o conjunto de estados é pequeno e conhecido.

6. Quando o valor muda: variável, não classe

Nem todo dinamismo é escolha entre estados. Às vezes é um valor contínuo: a cor que o cliente escolheu no seletor, a altura que veio da medição, o progresso de uma barra. Aí não existe um número finito de classes para escrever, e montar bg-red-500 por concatenação é justamente o que não funciona.

A saída é inverter a lógica: a classe fica fixa e aponta para uma variável de CSS; o valor variável entra na variável. Em vez de mudar o nome da classe, você muda o conteúdo, e o CSS não precisa ser gerado de novo.

Na caixa abaixo, o JavaScript grava a cor escolhida pelo cliente em --cor-do-dia, no style do elemento. Falta a classe usar esse valor.

Aponte o fundo para a variável com bg-(--cor-do-dia) e rode. O cartão deve assumir o verde gravado no style, sem que nenhum nome de cor apareça na classe.

<div id="alvo" class="p-4 text-white" style="--cor-do-dia: #15803d">
  <p class="font-semibold">Cor escolhida pela cliente</p>
  <p class="text-sm">Vale para o bolo de aniversário.</p>
</div>
padding: 16px
color: rgb(255, 255, 255)

<div id="alvo" class="p-4 text-white bg-(--cor-do-dia)" style="--cor-do-dia: #15803d">
  <p class="font-semibold">Cor escolhida pela cliente</p>
  <p class="text-sm">Vale para o bolo de aniversário.</p>
</div>

O CSS gerado é curto e não tem cor nenhuma: ele apenas repassa a variável. É por isso que qualquer valor serve, inclusive os que ainda não existem quando o CSS foi compilado — e é por isso que esse caminho não pede safelist, nem lista de classes, nem recompilação.

.bg-\(--cor-do-dia\) {
  background-color: var(--cor-do-dia);
}

O preço é que a cor deixa de ser “uma classe do Tailwind” e passa a ser um valor em execução: o painel mostra, o navegador desenha, mas ninguém procurando bg- no CSS vai achar aquele verde. Para os casos em que o valor realmente é livre, é uma troca boa. Para os casos em que existem cinco cores possíveis, o mapa do começo da aula é melhor — ele é documentação de si mesmo.

7. A lista forçada, e por que é último recurso

Existe uma terceira saída, que serve para quando você não controla o código que gera as classes: uma biblioteca, um CMS, um campo de texto em que o cliente digita a classe. No projeto com npm, o Tailwind v4 aceita uma declaração que força nomes para dentro do CSS, sem que eles apareçam no HTML:

@import "tailwindcss";

@source inline("bg-green-100 bg-green-900 bg-green-50");

Isso é o que o v3 chamava de safelist, e o efeito é o mesmo: os nomes listados entram no CSS final mesmo sem uso. Duas observações honestas. A primeira: nas caixas deste guia essa linha não tem efeito, porque o motor compila só o HTML da caixa e não tem projeto para varrer — o lugar dela é o seu style.css, no build de verdade. A segunda: use com parcimônia. Cada nome forçado é uma regra que vai para o navegador do cliente sem ninguém usar, e a lista envelhece calada: você troca o verde, esquece de trocar a lista, e o CSS cresce com nomes que não existem mais.

Antes de chegar nela, prefira o mapa. Ele resolve o mesmo problema mantendo o nome escrito em um lugar que se lê. A lista forçada é para o caso em que o nome vem de fora do seu código — e, mesmo aí, vale perguntar se não é melhor receber um estado em vez de uma classe.

8. Onde procurar quando a classe “não existe”

O sintoma é sempre o mesmo: o HTML no navegador mostra a classe, o elemento está sem o estilo, e não há erro em lugar nenhum. A tabela abaixo é a ordem de conferência que resolve quase todos os casos.

SintomaOnde olharConserto
uma classe funciona, a vizinha nãoo texto do arquivo, não o valor finalescrever o nome inteiro
funcionava e parou depois de um refactoro código que monta a stringvoltar ao mapa de nomes completos

a classe aparece no CSS, mas não pintao painel de CSS computadooutra regra está vencendo, ou o valor é inválido

Repare que três das cinco linhas apontam para o mesmo conserto de fundo: trocar geração de nome por nome escrito. Não é teimosia do Tailwind; é o preço de um sistema que gera só o CSS necessário. Quem mantém a lista de todos os nomes possíveis — o que os frameworks de CSS tradicional fazem — paga com arquivos grandes; quem gera sob demanda paga com a regra de escrever o nome inteiro.

A conferência de dez segundos, no seu projeto: procure no CSS gerado pelo nome que não pegou. Se não estiver lá, o problema é de geração, e é esta aula. Se estiver lá, o problema é de disputa, e o inspetor do navegador mostra quem venceu.

9. Cenários do dia a dia

Cenário 1: o mapa que virou três mil linhas

Começou com três estados e uma cor cada. Depois vieram tamanhos, depois variantes de tema, e o mapa passou a ter combinações demais — cada uma escrita à mão, cada uma para manter. O conserto não foi de sintaxe, foi de desenho: o estado virou atributo no HTML, a cor ficou em duas classes com data-[estado=…], e o mapa encolheu. Quando o mapa cresce sozinho, o problema é o número de variações, não o Tailwind.

Cenário 2: a classe certa, o build errado

Em produção, os cartões saíram sem cor, mas no computador da Ana tudo funcionava. A diferença estava no build: o CSS publicado tinha sido gerado antes do último commit, quando o mapa ainda não tinha a chave nova. O sintoma é idêntico ao da concatenação, e a conferência é a mesma — olhar o CSS publicado. Antes de acusar o Tailwind, compare a data do arquivo de CSS com a data do último código que mudou.

Cenário 3: o cliente digita a classe

A padaria quis um campo em que o cliente escolhe a cor da etiqueta de aniversário, digitando o nome da cor. As combinações eram livres, e aí nenhuma das duas saídas normais servia: o mapa não cobre o infinito, e a concatenação não gera CSS. A solução foi o campo gravar um valor de cor numa variável, como na seção 6. Regra geral: entrada livre pede valor, não pede nome de classe.

Exercício: o estado no atributo

O pedido já traz data-estado="pronto" no HTML. Complete o prefixo que faz o fundo ficar verde só nesse estado, usando o atributo como condição:

<div class="" data-estado="pronto">

Dica: é o prefixo, com colchetes, dois-pontos e a classe inteira. O prefixo também pode ser escrito com aspas dentro do colchete — data-[estado="pronto"] —, mas a forma sem aspas é mais curta e dá no mesmo.

11. Resumo

O Tailwind gera CSS a partir do texto que encontra nos arquivos, não do que o seu programa calcula. Por isso uma classe só existe se o nome inteiro estiver escrito em algum lugar lido pelo compilador. Mapa de nomes completos, escolha entre strings inteiras e objetos com uma chave por estado funcionam; concatenação no meio do nome não funciona, e falha em silêncio.

Quando o que muda é um estado finito, use o atributo no HTML e a variante na classe: data-[estado=pronto]:bg-green-100 decide sem JavaScript. Quando o que muda é um valor livre, use uma variável de CSS e a classe bg-(--cor). A lista forçada (@source inline(…)) existe no build de verdade e serve para o que vem de fora do seu código; é o último recurso, não o primeiro.

Para lembrar

  • O Tailwind lê texto; não executa o seu JavaScript.
  • Classe existe no CSS só se o nome inteiro aparece em algum arquivo lido.
  • "bg-" + cor e `bg-${cor}-100` nunca geram CSS.
  • Escolher entre duas strings inteiras é seguro e é o padrão.
  • Mapa com uma chave por estado: um lugar para mudar e todos os nomes visíveis.
  • Estado finito pede atributo + variante: data-[estado=pronto]:….
  • Valor livre pede variável: bg-(--cor) e o valor no style.
  • @source inline(…) força nomes no build de npm; a prévia do guia não o aplica.
  • Nome que vem de CMS ou de campo livre é entrada de dado, não desenho.
  • Se a classe está no CSS e não pinta, o problema é disputa de regra, não geração.

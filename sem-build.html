Sem Build

A cliente da Ana pediu uma coisa simples: "me manda o site por e-mail, eu abro com dois cliques". Sem terminal, sem instalar nada, sem pasta de projeto. A Ana já sabe que o Tailwind precisa de um passo que transforma as classes em CSS — e agora descobre que esse passo pode acontecer no navegador de quem abre a página, e não na máquina dela. É o modo sem build: uma página, um arquivo de script e um bloco de CSS com tipo especial. É também o modo que este guia usa em todas as caixas que você vem clicando.

Você vai aprender
  • O que é "build" e por que dá para viver sem ele.
  • O que o script @tailwindcss/browser faz, linha por linha.
  • Por que a tag de CSS precisa de type="text/tailwindcss".
  • Como declarar tema e componente direto na página.
  • O preço: tamanho, tempo e o piscar da página sem estilo.
  • Como salvar o CSS compilado e ficar com um site estático de verdade.
  • Por que o endereço antigo cdn.tailwindcss.com não serve na versão 4.
  • Quando o modo sem build é a escolha certa — e quando é armadilha.

1. A cena: o site que precisa abrir com dois cliques

A padaria não tem servidor, não tem conta em nuvem e não tem quem entenda de terminal. Tem uma pasta com três páginas HTML e uma cliente que quer ver o resultado hoje, no notebook dela, na frente da Ana. O combinado é mandar um arquivo compactado; ela descompacta, dá dois cliques no index.html e o site abre.

Se o CSS do Tailwind não existir nessa pasta, o que a cliente vê é HTML cru: títulos do tamanho do texto, listas com bolinhas, cartões sem cor. Não é "meio feio" — é irreconhecível. E não há nada que a Ana possa fazer no notebook da cliente: não dá para pedir que ela instale Node e rode npm install para ver um bolo de fubá.

A saída tem nome e é o assunto desta aula. Em vez de compilar o CSS antes, a página carrega um programa que compila na hora, no navegador de quem abriu. A cliente baixa um JavaScript a mais junto com a página, e o Tailwind faz ali, na memória, o mesmo trabalho que faria no computador da Ana. O resultado na tela é idêntico.

Esse guia faz exatamente isso. Cada caixa que você clicou até aqui monta uma página de verdade, carrega o compilador e gera o CSS do seu HTML. Não é uma simulação: é o Tailwind, o mesmo arquivo, rodando no seu navegador. Então você já viu o modo sem build funcionando umas cem vezes — agora vai entender o que estava acontecendo.

2. O que é build (e por que dá para viver sem)

Build é o passo que transforma o que você escreveu no que o navegador entende. No caso do Tailwind, é a tradução de p-4 para padding: calc(var(--spacing) * 4), e de todas as outras classes da página em um arquivo CSS. Esse passo pode acontecer em três momentos diferentes, e a diferença entre eles é a diferença entre os modos de usar a ferramenta:

Antes de publicar, no seu computador — é o modo com build, com Vite ou com a CLI. A página publicada leva um CSS pronto, pequeno e igual para todos. Durante o desenvolvimento, a cada salvamento — também é o modo com build, só que automático. Ou depois de publicada, no navegador de quem visita — é o modo sem build, e é ele que dispensa terminal, Node e instalação.

Repare que a palavra "sem build" não quer dizer "sem compilação". Quer dizer sem um passo de build na sua máquina. A compilação continua existindo; ela só mudou de lugar. Quem paga a conta é o visitante, e é essa troca que você precisa entender antes de escolher.

build
O passo que compila e empacota antes de publicar. Pode ser um comando que você roda ou um servidor que roda sozinho a cada salvamento.
compilador no navegador
O Tailwind empacotado como JavaScript comum, que lê a página e injeta o CSS gerado. É o @tailwindcss/browser.
CDN
Um servidor que entrega arquivos públicos para o mundo. É de lá que vem o script, sem você baixar nada.
CSS estático
Um arquivo .css pronto, guardado na pasta do site. É o que o modo com build produz e o que o navegador só baixa, sem compilar nada.
FOUC
O piscar da página sem estilo, do inglês flash of unstyled content. Acontece quando o CSS chega depois do conteúdo.

3. Caminho 1: o compilador no navegador

Tudo começa com uma linha no <head> da página. É um <script> como outro qualquer, apontando para o pacote oficial:

<script src="https://cdn.jsdelivr.net/npm/@tailwindcss/browser@4"></script>
<style type="text/tailwindcss">
  @theme {
    --color-marca: #b4532a;
  }
</style>

Leia o endereço com calma, porque cada pedaço diz algo. cdn.jsdelivr.net é o CDN — o servidor de arquivos públicos. /npm/ indica que o arquivo vem do registro do npm, o mesmo onde o npm install busca pacotes. @tailwindcss/browser@4 é o nome do pacote com a versão maior fixada em 4: você recebe correções da versão 4, mas não é surpreendido por uma versão 5 no meio de um projeto.

O que esse arquivo faz quando chega? Ele olha o documento inteiro, encontra as classes escritas no HTML, lê os blocos de tema que estiverem nas tags especiais e escreve uma folha de estilo nova dentro do <head>, com o CSS pronto. Tudo isso em menos de um segundo, sem rede depois do primeiro carregamento do script — porque o compilador já está ali, no seu navegador.

A segunda parte do exemplo é a tag de CSS com type="text/tailwindcss". Ela não é CSS comum: o navegador, sozinho, não sabe o que fazer com ela e a ignora. Quem lê é o compilador. É ali que você escreve o @theme, as classes com @apply e qualquer regra que dependa do Tailwind — a mesma coisa que ficaria no arquivo de entrada de um projeto com build.

Junte as duas peças e você tem uma página que se veste sozinha. Nada de arquivo CSS para sincronizar, nada de comando para rodar, nada de pasta dist. Salve, abra, veja.

4. O type que muda tudo

O erro número um de quem começa no modo sem build é esquecer o type. A página tem o script, tem o @theme escrito bonitinho, e nada acontece. O motivo é que uma tag <style> sem tipo é CSS comum: o navegador tenta interpretar o conteúdo, encontra um @theme que não conhece, descarta em silêncio, e segue a vida.

Repare no verbo: descarta em silêncio. Não há mensagem vermelha, não há aviso no console. O CSS inválido simplesmente não vale. É o mesmo comportamento das classes digitadas errado que você viu na primeira aula — e a mesma estratégia resolve: conferir o que o navegador realmente aplicou.

O selo está transparente porque o navegador ignora o bloco de tema. Acrescente o tipo que o compilador procura: type="text/tailwindcss" na tag style.

<style>
@theme {
  --color-marca: #b4532a;
}
</style>

<span id="alvo" class="rounded-full bg-marca px-3 py-1 text-white">Feito hoje</span>
color: rgb(255, 255, 255)
border-radius: 3.35544e+07px
padding-inline: 12px
padding-block: 4px

<style type="text/tailwindcss">
@theme {
  --color-marca: #b4532a;
}
</style>

<span id="alvo" class="rounded-full bg-marca px-3 py-1 text-white">Feito hoje</span>

Vale guardar a diferença entre as duas tags, porque elas parecem iguais e fazem coisas opostas. Uma <style> comum é lida pelo navegador e escrita por você em CSS puro. Uma <style type="text/tailwindcss"> é lida pelo compilador e aceita as construções do Tailwind, como @theme e @apply. Se você colocar @apply numa tag comum, o navegador descarta a regra inteira e o elemento fica sem estilo nenhum — não só sem o @apply.

Existe ainda um terceiro caso: a tag com tipo mas sem o script na página. Aí o compilador não está lá para ler, e o resultado é o mesmo do começo — silêncio. As duas peças andam juntas, sempre: o script traz o compilador, a tag tipada traz o CSS.

5. Tema e componente direto na página

Com a tag tipada no lugar, tudo o que você aprendeu sobre o @theme funciona. A diferença é que o bloco não mora num arquivo src/style.css: ele mora na própria página, entre as tags, muitas vezes no <head>, antes do conteúdo.

O aviso da padaria só tem uma borda. Complete a regra .aviso com @apply rounded-lg bg-amber-100 p-3 text-amber-900.

<style type="text/tailwindcss">
.aviso {
  border: 1px solid #e7e5e4;
}
</style>

<p id="alvo" class="aviso">Assado às 6h</p>
border: 1px solid rgb(231, 229, 228)

<style type="text/tailwindcss">
.aviso {
  @apply rounded-lg bg-amber-100 p-3 text-amber-900;
}
</style>

<p id="alvo" class="aviso">Assado às 6h</p>

O @apply é a ponte entre os dois mundos: ele pega classes do Tailwind e as escreve dentro de uma regra com nome. No modo sem build isso é especialmente útil, porque você não tem um arquivo CSS separado para organizar — então o .aviso resolve o problema de repetir seis classes em cada um dos quatro avisos da página.

Um cuidado que vale desde já: o conteúdo da tag tipada é compilado junto com o resto, então cada regra que você escreve ali custa bytes na página. Não é lugar para colar uma biblioteca de componentes inteira; é lugar para o tema da padaria e três ou quatro classes com nome. Se a lista crescer, é sinal de que chegou a hora do modo com build — e não é vergonha nenhuma.

Outra coisa que funciona sem build: as variantes. md:p-6, hover:bg-amber-200 e dark:bg-stone-900 são geradas na hora como qualquer outra classe. O que muda é que a variante dark: precisa estar declarada na página, porque no v4 ela não vem pronta — o script do guia declara, e no seu site você declara também, com uma linha de @custom-variant. Guarde o nome; ele tem aula própria mais adiante.

6. O preço: o que se perde

Nada é de graça, e o modo sem build cobra em três moedas. A primeira é o tamanho: o compilador é um arquivo grande, da ordem de centenas de quililobytes, e todo visitante o baixa junto com a página. Para uma demonstração, tudo bem. Para a vitrine da padaria, num celular em rede 3G, é peso que não se justifica.

A segunda é o tempo. Com build, o CSS já chega pronto e a página aparece vestida no primeiro desenho da tela. Sem build, o navegador primeiro desenha o HTML cru, depois executa o script, depois gera o CSS, e só então a página se arruma. Esse intervalo é o FOUC, o piscar de que falamos. Em máquinas rápidas é quase invisível; em celular velho, dá tempo de ver o texto saltar de lugar.

A terceira é o controle. Um erro de classe que o compilador não reconhece passa em silêncio, aqui como em qualquer modo, mas no modo sem build você não tem um passo de build para reclamar antes de publicar. Some-se a isso a dependência de rede: se o CDN estiver bloqueado na rede da cliente — e em rede de empresa isso acontece —, a página abre sem estilo nenhum e não há o que fazer do seu lado.

PontoSem build (navegador)Com build (Vite ou CLI)
Quem compilao navegador do visitanteo seu computador, antes de publicar
Peso extracentenas de kB de JavaScriptzero; só o CSS usado
Primeira pinturapode piscar sem estilojá vem vestida
Terminaldispensaobrigatório uma vez
Ideal parademonstração, protótipo, página únicasite publicado, vários arquivos

Vale dizer o que não está na lista: a qualidade do CSS. O compilador do navegador é o mesmo motor do Vite, então o padding: calc(var(--spacing) * 4) que sai de lá é idêntico. Você não está usando uma versão inferior do Tailwind; está usando a mesma, em outro lugar e na hora errada para um site grande.

7. Caminho 2: o CSS compilado e salvo

Existe um meio-termo que resolve o problema da cliente da Ana sem peso nenhum na página: compilar uma vez, salvar o arquivo e publicar o CSS pronto. A página fica com um <link rel="stylesheet"> comum, como qualquer site dos anos 2000 — e ninguém precisa de Node para abrir.

ana@notebook:~/padaria$ npx @tailwindcss/cli -i entrada.css -o site.css --minify

≈ tailwindcss v4.3.5

Done in 240ms

O comando lê o arquivo de entrada (aquele com @import "tailwindcss" e o @theme), varre os arquivos HTML do projeto e escreve o site.css pronto. O npx roda o pacote sem instalar de forma permanente; o --minify tira espaços e quebra de linha. Depois disso, a página só precisa de:

<link rel="stylesheet" href="site.css">

A pasta que vai no e-mail fica com dois arquivos, e nenhum deles é JavaScript de compilador:

ana@notebook:~/entrega$ ls -lh
total 32K
-rw-r--r-- 1 ana ana  18K nov 27 09:41 index.html
-rw-r--r-- 1 ana ana  14K nov 27 09:41 site.css

Pronto: site estático de verdade, sem JavaScript nenhum do Tailwind. A desvantagem é óbvia e não tem jeito: se a Ana criar uma classe nova no HTML, ela precisa rodar o comando de novo. É por isso que quem faz isso todo dia acaba indo para o Vite, que roda o comando sozinho a cada salvamento — mas para uma página que vai ser entregue hoje e não muda mais, o comando avulso resolve.

Esse caminho também é a resposta para quem pergunta "posso usar o Tailwind só com um arquivo CSS pronto que achei na internet?". Pode, desde que o arquivo tenha sido gerado a partir das classes que a sua página usa. Um CSS de exemplo, feito para outra página, vai estar cheio de regras que você não usa e sem as que você usa. O Tailwind não adivinha: ele só gera o que encontra escrito.

8. Teste final: a página num arquivo só

Hora de juntar tudo no formato que a cliente da Ana vai receber: um HTML, uma tag de script e uma tag de CSS tipada, com o tema da padaria dentro. É o teste de verdade do modo sem build, porque não há nada fora do arquivo para dar errado.

A barra do topo e o selo estão sem cor. No bloco @theme, declare --color-marca: #b4532a e --color-marca-clara: #f6e7e0; depois pinte a barra com bg-marca e o selo com bg-marca-clara.

<style type="text/tailwindcss">
@theme {
  --color-trigo: #e7d8b8;
}
</style>

<header id="alvo" class="p-4">
  <span id="selo" class="rounded-full px-3 py-1 text-xs">Feito hoje</span>
</header>
padding: 16px

<style type="text/tailwindcss">
@theme {
  --color-marca: #b4532a;
  --color-marca-clara: #f6e7e0;
}
</style>

<header id="alvo" class="bg-marca p-4">
  <span id="selo" class="rounded-full bg-marca-clara px-3 py-1 text-xs">Feito hoje</span>
</header>

O painel mostra dois elementos ao mesmo tempo quando a missão pede, mas você já sabe ler: cada linha é uma propriedade que mudou de valor em relação a um elemento sem classe. Se a cor da barra aparecer e a do selo não, o problema é só no segundo token — provavelmente um hífen fora do lugar em --color-marca-clara.

Agora a decisão de qual caminho usar, que é o que interessa depois da aula:

Perceba que não existe resposta única, e que trocar de caminho é barato: o @theme é o mesmo, as classes são as mesmas, o @apply é o mesmo. O que muda é quem compila e quando. Quem entende essa frase não fica preso a tutorial nenhum.

9. Cenários do dia a dia

Cenário 1: abriu com dois cliques e a página ficou sem estilo

Duas causas prováveis. A primeira já foi vista: falta o type="text/tailwindcss" na tag de CSS, e o navegador jogou o bloco fora. A segunda é o script carregado como módulo (type="module") apontando para um arquivo local: aberto por file://, o navegador bloqueia o carregamento por segurança, e o compilador nunca chega. Use o script comum, do CDN, ou sirva a pasta por um endereço — o mesmo arquivo funciona nos dois casos, desde que o navegador possa buscá-lo.

Cenário 2: a página pisca antes de ficar bonita

É o FOUC em ação: o HTML aparece primeiro, o CSS gerado chega alguns décimos depois. Para uma demonstração, avise a cliente; para um site publicado, resolva. O jeito definitivo é salvar o CSS com a CLI e linkar o arquivo pronto. Um paliativo honesto é esconder o conteúdo até o CSS chegar, mas isso troca o piscar por uma tela em branco — e tela em branco é pior para quem espera.

Cenário 3: na rede do cliente, o site abre sem estilo

Aconteceu na primeira visita à padaria: a rede do escritório bloqueava o CDN, o script não veio e a página abriu crua, no meio de uma reunião. A lição é não depender de um servidor de terceiros para o visual do site. Baixe o arquivo do compilador e coloque na pasta, ou compile o CSS e publique estático. Em qualquer um dos dois, o site passa a funcionar mesmo sem internet — que é o mínimo que se espera de uma página que abre com dois cliques.

Exercício: o endereço do compilador

<script src="https://cdn.jsdelivr.net/npm/"></script>

Dica: começa com arroba, tem uma barra no meio e termina na versão maior. O tailwindcss sozinho é o compilador do build, não o do navegador.

11. Resumo

Sem build não significa sem compilação: significa compilar no navegador do visitante, na hora de abrir a página. O compilador vem de um <script> apontando para @tailwindcss/browser@4, e o CSS do projeto vai numa tag <style type="text/tailwindcss"> — sem esse tipo, o navegador descarta o bloco em silêncio. Dentro dela funcionam o @theme, o @apply e as variantes.

O preço é peso e tempo: centenas de kilobytes de JavaScript, um piscar antes do estilo aparecer e dependência de um CDN que pode estar bloqueado. Para demonstração, protótipo e página única é imbatível; para site publicado, o caminho é compilar uma vez — com a CLI, salvando um site.css, ou com o Vite, que faz isso a cada salvamento. O CSS gerado é o mesmo nos três caminhos, o que torna a troca barata e a decisão fácil.

Para lembrar

  • "Sem build" é sobre onde a compilação acontece, não sobre existir compilação.
  • Script do CDN no head mais uma tag style type="text/tailwindcss".
  • Tag style sem tipo é CSS comum: o @theme é ignorado sem aviso.
  • Tema, @apply e variantes funcionam dentro da tag tipada.
  • Cada regra escrita na página é peso: tema e poucas classes, nada de biblioteca.
  • O compilador custa centenas de kB e o CSS chega depois do conteúdo (FOUC).
  • Site estático de verdade: compile com a CLI e linke o CSS pronto.
  • O endereço antigo cdn.tailwindcss.com é da versão 3; na 4, use o pacote browser.
  • CDN bloqueado na rede do cliente = página crua; prefira arquivo local para entregar.
  • As caixas deste guia rodam exatamente assim: script mais tag tipada.

O Modo watch

A Ana passou a manhã alternando entre o editor e o terminal: mudava uma classe, salvava, digitava o comando de build, esperava, voltava ao navegador, recarregava. Cinquenta vezes. No fim da manhã ela tinha feito mais exercício de digitação do que de CSS. Existe uma opção que faz esse trabalho por ela: o modo watch, que fica ligado e refaz o build a cada salvamento. Nesta aula ela aprende a ligar, a conviver e — principalmente — a desligar na hora certa.

Você vai aprender
  • O que a opção --watch faz e por que ela não termina sozinha.
  • Quais arquivos disparam uma nova geração e quais não disparam.
  • Como organizar o terminal: um para o watch, outro para os comandos.
  • O que o watch não faz — servidor, recarga automática, correção de erro.
  • O que acontece quando dois watches rodam ao mesmo tempo.
  • Por que desligar antes de gerar a folha de produção.
  • Como descobrir por que "salvei e nada mudou".

1. A cena: cinquenta builds numa manhã

O trabalho de ajustar uma tela é feito de tentativas pequenas: um pixel a mais aqui, uma cor mais escura ali, um texto que muda de lugar. Cada tentativa exige que o CSS gerado acompanhe o HTML — e, sem automação, cada tentativa custa quatro passos manuais. Quatro passos não parecem muito até você fazer cinquenta vezes e perceber que metade da sua atenção foi para o teclado, não para o desenho.

O modo watch existe para transformar quatro passos em um. Você liga o comando uma vez, ele fica em execução e observa os arquivos do projeto. Quando algum muda, ele refaz o build e escreve a saída de novo. Você salva no editor, conta até dois e recarrega o navegador: o CSS já está atualizado. O nome "watch" é literal — o programa está vigiando.

É a primeira vez no guia em que um comando não termina. Todas as ferramentas que vimos até aqui fazem o trabalho e devolvem o cursor; esta fica viva até você mandar parar. Essa diferença é a fonte de quase todos os mal-entendidos da aula, e é o que explica a sensação de terminal travado.

2. Como ligar e como desligar

É a mesma opção que já apareceu na aula da CLI, agora com o papel principal. Basta acrescentar --watch (ou -w) ao comando que você já usa:

$ npx @tailwindcss/cli -i src/entrada.css -o dist/estilo.css --watch
Done in 84ms

Done in 31ms

Done in 27ms

O primeiro Done in 84ms é o build inicial: ele compila tudo antes de começar a vigiar, para que a folha exista desde o primeiro segundo. Os seguintes aparecem a cada salvamento — 31 ms, 27 ms. Repare que o tempo cai: depois do primeiro, o trabalho é incremental, porque a maior parte do CSS anterior continua válida. Você não precisa fazer nada com esses números; eles servem para confirmar que o watch está vivo.

Para desligar, Ctrl + C. O terminal mostra o acento circunflexo com o C e devolve o cursor:

Done in 31ms

^C
$

O atalho vale para praticamente qualquer programa de terminal que fica rodando: vale para o watch do Tailwind, para um servidor local e para qualquer coisa que pareça travada. Se o terminal não responde e o Ctrl + C não resolve, o processo pode estar esperando uma resposta: aperte Enter uma vez e tente de novo.

Existe uma alternativa ao atalho, para quando você fechou a janela sem querer e o processo ficou órfão: fechar a janela do terminal costuma matar tudo o que ela iniciou. Se em vez disso você suspendeu a janela, o processo continua vivo e escrevendo na saída. Na dúvida, abra outro terminal e rode ps aux para ver se há um tailwindcss rodando — é a única forma de saber sem adivinhar.

3. O que dispara uma nova geração

O watch observa as mesmas coisas que o build lê: o CSS de entrada e os arquivos de texto que a varredura alcança. Salvar qualquer um deles dispara uma nova geração. Isso surpreende quem acha que só classe nova conta: mudar uma palavra dentro do HTML também dispara, porque o programa não sabe distinguir uma mudança relevante de uma irrelevante sem reler o arquivo.

Você salvouAcontecePor quê
um HTML da pasta do projetonovo build em milissegundoso arquivo está na varredura
o CSS de entradanovo build, com o tema novoé a fonte das configurações
um arquivo fora da varreduranadao watch nunca ouviu falar dele
uma imagemnadanão é arquivo de texto com classes
um arquivo dentro de node_modulesnadaa pasta é ignorada de propósito

A terceira linha da tabela explica o caso mais frustrante. Se as páginas do site moram fora da pasta em que o comando foi chamado, o watch não as vê — e você salva, salva e nada acontece. A cura é a mesma da aula do CSS de entrada: rodar da raiz do projeto ou acrescentar o caminho com @source "../pasta";. O sintoma, nos dois casos, é um silêncio suspeito: o watch não imprime nada porque não tem nada para fazer.

Para sentir isso, a caixa abaixo faz o papel do salvamento. A mudança é no texto e no respiro: as duas coisas moram no HTML, então as duas chegam ao build na mesma hora. Um watch ligado escreveria a folha nova antes de você soltar a tecla.

A padaria mudou o horário e o cartão precisa de mais respiro: escreva Pão quentinho às 5h e deixe 16 px de espaço interno — as duas mudanças no mesmo arquivo, como num salvamento de verdade.

<div id="alvo" class="p-2 bg-amber-100">Pão quentinho às 6h</div>
padding: 8px
background-color: oklch(0.962 0.059 95.617)

<div id="alvo" class="p-4 bg-amber-100">Pão quentinho às 5h</div>

4. O que o watch não faz

Vale ser explícito, porque a expectativa errada gera meia hora de procura. O watch não abre servidor: ele escreve um arquivo, e quem serve é outra coisa. Não recarrega o navegador sozinho: você continua apertando F5 ou Ctrl + R — o que ele economiza é o comando de build, não o recarregamento. E não corrige erro de sintaxe no seu CSS: se a entrada tiver um erro, ele avisa e continua esperando, com a folha anterior intacta.

Essa última característica é uma proteção, e é bom entender o efeito colateral. Quando dá erro, a saída não é reescrita: o site continua com a última versão boa. Você vê a página bonita, salva, vê a página bonita de novo, e não entende por que a mudança não pegou — porque o build falhou e a mensagem passou no meio dos outros Done in. Por isso é bom ler o terminal de vez em quando, mesmo quando a página parece certa.

watch
O modo de execução que fica observando arquivos e refaz o build quando algum muda.
recompilação incremental
Refazer só a parte do trabalho que mudou. É por isso que o segundo build leva 30 ms e o primeiro leva 80.
servidor de arquivos
Um programa que entrega os arquivos do projeto para o navegador em um endereço local. Não é papel do Tailwind.
recarga automática
Fazer o navegador recarregar sozinho depois de um salvamento. Vem de outras ferramentas, não do watch.
processo
Um programa em execução. O watch é um processo que só termina quando você manda, ou quando a janela do terminal fecha.

Se você quer recarga automática, o caminho moderno é usar uma ferramenta de desenvolvimento que junte as duas coisas — servidor com recarga e compilação de CSS. Existe uma aula própria sobre isso mais adiante, na parte de integração. Enquanto o projeto é HTML puro, o par "watch mais servidor local" resolve bem, com um F5 no meio.

5. Um terminal para cada coisa

A organização que funciona é simples: um terminal fica com o watch, e não é usado para mais nada. Os comandos do dia a dia — ls, npm ls, um build avulso — vão para outro terminal, ou para outra aba. Duas razões: o watch ocupa o prompt, e a saída dele se mistura com a sua, o que confunde a leitura.

Ter o segundo terminal é fácil: o atalho Ctrl + Shift + T abre uma aba nova na maioria dos terminais do Linux, e o menu do aplicativo sempre tem a opção. A partir dali, o fluxo fica: editor de um lado, navegador do outro, watch rodando na aba um, comandos na aba dois. Quando o watch precisa parar, você sabe exatamente onde apertar Ctrl + C.

Uma vantagem discreta do segundo terminal: é nele que você roda o servidor local que entrega as páginas ao navegador, quando não quer abrir o arquivo direto. Dois processos, duas abas, cada um com sua saída. Quando algo parece não funcionar, você sabe onde olhar primeiro — e não precisa desligar o watch para testar um comando avulso.

Vale também dar um apelido ao comando, no package.json. Com um script dev que já inclui --watch, você digita npm run dev e esquece os caminhos. O nome do script não é padronizado, mas a convenção é essa: dev para o modo de trabalho e build para o de produção. Quem abre o projeto pela primeira vez entende o que fazer só de ler os dois nomes.

6. O lado chato: terminal ocupado, build duplicado

Dois watches rodando ao mesmo tempo no mesmo arquivo de saída é uma receita de confusão. Os dois escrevem no mesmo lugar, cada um com a sua cópia do projeto em memória, e o resultado é uma folha que parece certa e errada ao mesmo tempo: uma classe nova aparece, outra desaparece. O sintoma clássico é "o CSS muda sozinho quando eu não fiz nada".

A causa costuma ser uma aba antiga esquecida. Antes de investigar o Tailwind, vale listar os processos e matar o intruso. É mais comum do que parece: você abre um terminal novo porque o antigo parecia travado, liga o watch de novo, e o primeiro continua lá, vivo, escrevendo.

O segundo lado chato é a memória. Cada watch carrega o motor, o catálogo de classes e os arquivos do projeto. Em um notebook modesto, dois ou três watches de projetos diferentes já pesam. Não é motivo para evitar o modo — é motivo para fechar o que não está em uso, do mesmo jeito que se fecham abas do navegador.

Salve e veja o rebuild: o cartão estava com 8 px de respiro e precisa de 24 px. Mude a classe e rode de novo — é exatamente o que o watch faria sozinho a cada salvamento.

<div id="alvo" class="p-2 bg-amber-100">Pão quentinho</div>
padding: 8px
background-color: oklch(0.962 0.059 95.617)

<div id="alvo" class="p-6 bg-amber-100">Pão quentinho</div>

O painel mostra 24 px e a regra padding: calc(var(--spacing) * 6). No seu projeto, o mesmo efeito aparece sem você clicar em nada: o watch percebe o salvamento e reescreve o arquivo. Se o painel demorar a mudar no navegador, o suspeito não é o watch — é o cache da página.

7. Quando desligar (e por que isso importa)

O watch é uma ferramenta de desenvolvimento, e o nome do ambiente está na própria palavra. Ele não tem lugar no build de produção. O motivo não é filosófico: é que ele pode sobrescrever a folha que você acabou de gerar com --minify, no segundo seguinte, ao salvar qualquer arquivo. Você publica achando que está compacta, e o visitante baixa a versão cheia.

A sequência segura, que já apareceu na aula Build de Produção: um Ctrl + C no terminal do watch, depois o build de produção, depois a conferência do tamanho. Três passos, e o último mostra na hora se algo saiu do lugar. Publicar com o watch ligado é apostar que ninguém vai salvar nada até o upload terminar.

AssuntoModo watchBuild de produção
quando rodaenquanto você trabalhauma vez, antes de publicar
termina sozinho?não: fica ligado até o Ctrl + Csim, em silêncio
saídalegível, com espaçoscompacta, com --minify
quem usavocê, no editoro navegador de quem visita
risco de rodar juntosobrescreve a folha compactanão percebe que foi sobrescrito

Existe também o caso do watch que ficou ligado a noite inteira. Não quebra nada, mas consome memória, mantém o terminal ocupado e, se você mexer nos arquivos de manhã sem lembrar que ele está lá, cada salvamento escreve na pasta de saída — inclusive salvamentos de rascunho que você não queria publicar. Um projeto organizado fecha o dia com o terminal limpo.

8. Cenários do dia a dia

Cenário 1: "salvei e a página não mudou"

Quatro suspeitos, na ordem. O watch não está rodando — confira a saída dele depois do salvamento. O arquivo salvo está fora da varredura — a página mora em outra pasta. O build falhou e a folha anterior continua no lugar — leia a mensagem no terminal. Ou o navegador está com a folha em cache — recarregue com Ctrl + Shift + R. Nessa ordem, você resolve a maioria em menos de um minuto.

Cenário 2: "o terminal não aceita mais comandos"

É o esperado: o watch está ocupando o prompt. Não está travado, está trabalhando. Se você precisa daquele terminal para outra coisa, Ctrl + C e o cursor volta; para ter os dois, abra outra aba. Se a tecla não fizer nada, tente Enter e depois Ctrl + C de novo — e, no limite, feche a janela.

Cenário 3: "o CSS muda sozinho"

Quase sempre são dois watches, ou um watch e um build automático, escrevendo no mesmo arquivo. Abra outro terminal, procure os processos do Tailwind e termine os que não deviam estar lá. Depois de eliminar o duplicado, rode um build limpo e compare o resultado: uma folha escrita por dois processos não tem como ser previsível.

9. Uma mudança no CSS de entrada reconstrói tudo

Falta um efeito que muda a forma de trabalhar: o watch não vigia só o HTML. Como o CSS de entrada é a fonte dos valores do projeto, salvá-lo refaz o build inteiro — e o efeito pode alcançar todas as páginas. É a diferença entre mudar um cartão e mudar a escala do site.

Na caixa abaixo, a alteração é na variável de espaçamento. Com ela, cada degrau da escala muda de tamanho: p-4 deixa de valer 16 px e passa a valer 19,2 px, porque a conta é 4 × 0,3 rem. Todos os elementos que usam qualquer classe de espaço acompanham. É o tipo de mudança que você não quer fazer sem conferir todas as páginas depois.

A padaria quer respiros um pouco maiores em todo o site. No CSS de entrada, troque a variável de espaçamento por 0.3rem e veja o p-4 do cartão virar 19,2 px sem tocar no HTML.

<style type="text/tailwindcss">
@theme { --spacing: 0.25rem; }
</style>
<div id="alvo" class="p-4 bg-amber-100">Pão quentinho</div>
padding: 16px
background-color: oklch(0.962 0.059 95.617)

<style type="text/tailwindcss">
@theme { --spacing: 0.3rem; }
</style>
<div id="alvo" class="p-4 bg-amber-100">Pão quentinho</div>

Repare que a regra gerada continua idêntica: padding: calc(var(--spacing) * 4). O que mudou foi o valor da variável. É por isso que o Tailwind escreve contas em vez de números: uma edição na entrada alcança o site inteiro, sem reescrever regra nenhuma. E é por isso que o watch, ao ver o arquivo de entrada mudar, refaz tudo em vez de remendar um pedaço.

O mesmo vale para uma cor da marca, para uma fonte, para um raio. Sempre que a mudança é no @theme, o build inteiro é refeito — e o watch faz isso em milissegundos, enquanto você olha outra coisa. O assunto tem aula própria na parte de configuração; aqui basta saber que o watch cobre essa parte também.

11. Resumo

O modo watch é o mesmo build, rodando em pé. Ele compila uma vez, observa os arquivos do projeto e refaz o trabalho a cada salvamento, com tempo decrescente porque a recompilação é incremental. Enquanto está ligado, o prompt fica ocupado: isso é o desenho, não um defeito. Ctrl + C encerra, e o costume saudável é ter um terminal só para ele.

Ele observa o CSS de entrada e os arquivos que a varredura alcança, e não faz mais nada: não serve site, não recarrega navegador, não corrige erro de sintaxe — quando o build falha, a folha anterior permanece. Como pode sobrescrever a saída, sai de cena antes do build de produção. E, como refaz tudo a partir do CSS de entrada, é o melhor jeito de sentir na hora o efeito de uma variável de tema.

Para lembrar

  • --watch (ou -w) deixa o build rodando e vigilante.
  • O primeiro build é completo; os seguintes são incrementais e mais rápidos.
  • O prompt fica ocupado: é um processo vivo, não um terminal travado.
  • Ctrl + C encerra e devolve o cursor.
  • Um terminal para o watch, outro para os comandos do dia a dia.
  • Salvar HTML, CSS de entrada ou componente dispara um novo build.
  • Arquivo fora da varredura, imagem e node_modules não disparam nada.
  • O watch não serve páginas nem recarrega o navegador por você.
  • Erro no CSS de entrada: ele avisa e mantém a folha anterior.
  • Antes do build de produção, desligue: dois processos na mesma saída é confusão.

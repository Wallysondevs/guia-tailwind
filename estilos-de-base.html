Estilos de Base

A Ana escreveu a página de receitas com títulos, subtítulos, listas de ingredientes e parágrafos de modo de preparo. Ficou tudo igual: o título principal do mesmo tamanho do texto, o subtítulo também, e os parágrafos colados uns nos outros, sem respiro nenhum. Ela não errou o HTML — o <h1> está lá, com a tag certa. O que aconteceu é que o Tailwind, antes de qualquer classe sua, apaga os enfeites que o navegador dava às tags: é o preflight, uma camada de base que existe para o desenho começar do zero. Nesta aula a Ana entende essa camada, aceita o que ela faz e escreve a base do próprio projeto — os padrões que valem para o site inteiro, uma vez só.

  • O que o preflight zera, e por que o <h1> fica do tamanho do texto.
  • Como escrever a base do projeto com @layer base.
  • Por que uma utilidade sempre ganha de uma regra de base.
  • Como usar @apply dentro da base sem perder as variáveis do tema.

  • As armadilhas: !important desnecessário, seletor de classe na base, regra que some.
  • Como conferir uma regra de base quando o painel não mostra nada.

1. A cena: a página em que tudo é do mesmo tamanho

A receita do pão de queijo é simples, e o HTML também: um <h1> com o nome, um <h2> para os ingredientes, um <ul> com a lista e dois <p> para o modo de preparo. Em qualquer página sem CSS, o navegador mostraria o h1 grande e em negrito, o h2 médio e em negrito, a lista com bolinhas e espaço entre os parágrafos. Na página da Ana, tudo isso desapareceu.

Ela abriu o inspetor e viu a resposta: h1 { font-size: inherit; font-weight: inherit; }, vindo de uma regra que ela não escreveu. É o preflight do Tailwind. Ele faz parte da biblioteca desde sempre, chega junto com o @import "tailwindcss"; e tem um objetivo declarado: deixar todos os navegadores desenhando as tags do mesmo jeito, sem os enfeites diferentes que cada um inventou nos anos 1990.

A confusão é justa: você pediu “Tailwind”, não pediu “apagar meus títulos”. Mas pense no que seria o contrário. Sem o preflight, o seu h1 teria 2 em de tamanho, 0,67 em de margem em cima e 0,67 embaixo, e o seu p teria 1 em de margem em cima e embaixo — valores diferentes em cada navegador, e nenhum deles escolhido por você. A primeira classe mt-4 que você escrevesse brigaria com uma margem que veio do navegador e que você não vê no código. O preflight troca esse pacote de surpresas por um começo conhecido: tudo zerado, e o desenho é decisão sua.

2. As quatro camadas, e por que a ordem importa

Antes de entender o preflight, vale ver onde ele mora. O CSS que o Tailwind gera começa declarando a ordem de quatro camadas, e essa única linha resolve metade das discussões de CSS que você vai ter na vida:

@layer theme, base, components, utilities;

@layer theme {
  :root, :host {
    --spacing: 0.25rem;
    --color-amber-100: oklch(0.962 0.059 95.617);
  }
}

Camada, em CSS, é um jeito de agrupar regras e dizer qual grupo vence quando dois disputam a mesma propriedade. A ordem da primeira linha é a sentença: quem vem depois ganha. Então utilities vence components, que vence base, que vence theme. E isso vale independentemente de quantos seletores cada regra tem — o que, em CSS tradicional, seria impensável.

Essa é a razão de o Tailwind poder usar seletores simples nas utilidades: ele não precisa de !important nem de especificidade alta para ganhar da base. Ele ganha porque está numa camada declarada depois. Na prática, você escreve class="text-xl" num h1 que tem font-size na base, e a classe vence sem briga.

Repare também no que a camada theme contém: as variáveis. Ela vem primeiro justamente porque é a fonte dos valores que as outras camadas vão usar. A ordem conta a história do arquivo: os valores, depois os padrões, depois os componentes, depois as utilidades.

3. O preflight: a base que você já usa

Agora o conteúdo da camada base. A primeira regra do preflight é a mais importantes de todas, e explica muita coisa que parece mágica:

@layer base {
  *, ::after, ::before, ::backdrop, ::file-selector-button {
    box-sizing: border-box;
    margin: 0;
    padding: 0;
    border: 0 solid;
  }
}

Leia devagar. O seletor * pega todos os elementos; os outros pegam os pseudo-elementos. Para todos eles, o preflight zera margem, respiro e borda, e troca o cálculo de tamanho para border-box — aquele em que a largura inclui a borda, e não soma a ela. É por isso que a sua primeira p-4 dá exatamente 16 px e não 16 px mais a borda.

O segundo trecho mais famoso do preflight é o dos títulos. É ele que a Ana viu no inspetor, e é o motivo de a página dela parecer texto corrido:

  h1, h2, h3, h4, h5, h6 {
    font-size: inherit;
    font-weight: inherit;
  }

inherit quer dizer “pegue o valor do pai”. Como o pai do h1 é o body, e o body usa o tamanho normal do texto, o título herda esse tamanho. Não é bug: é o Tailwind dizendo “os títulos não têm tamanho até você decidir”. A decisão pode ser sua, no HTML, com classes; ou do projeto inteiro, na base.

Uma coisa importante: o preflight não é obrigatório. Dá para importar só as utilidades e viver sem ele, e há projetos que fazem isso. Mas pense duas vezes: você passa a conviver com os padrões do navegador, e cada classe sua disputa com eles. Para quem está começando, o preflight é aliado, não obstáculo — ele deixa o ponto de partida igual em todo lugar.

4. A base do projeto

Com o preflight entendido, o caminho fica claro. Se os títulos nascem sem tamanho, alguém precisa dar tamanho a eles, e esse alguém é você. Escrever class="text-3xl font-bold" em cada h1 do site funciona e é o que se faz no começo; quando o site tem quarenta páginas, a decisão vira uma regra de base.

Na caixa abaixo, o h1 da padaria está no tamanho do texto, porque o preflight fez o trabalho dele. Sua missão é escrever, no @layer base, o padrão dos títulos de primeiro nível: 30 px, peso 700 e a cor âmbar escura do tema.

Escreva no @layer base uma regra para h1 com font-size: 30px, font-weight: 700 e color: var(--color-amber-900). O título deve ganhar tamanho e peso.

<style type="text/tailwindcss">
/* a base do projeto ainda não tem regra para h1 */
</style>

<h1 id="alvo" class="bg-amber-50 p-4">Padaria da Ana</h1>
padding: 16px
background-color: oklch(0.987 0.022 95.277)

<style type="text/tailwindcss">
@layer base {
  h1 {
    font-size: 30px;
    font-weight: 700;
    color: var(--color-amber-900);
  }
}
</style>

<h1 id="alvo" class="bg-amber-50 p-4">Padaria da Ana</h1>

Depois de rodar, olhe a prévia: o título cresceu e engordou. Agora olhe o painel: ele continua mostrando só o respiro e o fundo, como antes. Isso não é falha. O painel mostra o que as classes mudaram, comparando o elemento com uma cópia sem classes — e a regra que você escreveu vale para as duas cópias, porque ela não pergunta nada sobre classe. Quem confere o resultado é o valor computado, e é por isso que a meta desta caixa olha font-size e font-weight direto.

Guarde essa assimetria, porque ela vale para toda regra de base: a base não aparece no painel de diferenças. Se um dia você escrever uma regra de base e o painel não mudar nada, comece perguntando se ela é mesmo uma regra de base. Na dúvida, o inspetor do navegador, na aba Computed, mostra o valor final e de onde ele veio.

5. Base e utilidade: quem vence

O caso mais comum de confusão é o seguinte: você põe uma cor de link na base, e um dia precisa de um link com outra cor. Quem ganha? A resposta é sempre a mesma, e é a razão de as camadas existirem: a utilidade. Não importa se a regra de base foi escrita depois, não importa quantos seletores ela tem.

Na caixa abaixo, a base pinta todos os links de âmbar escuro, e o link de horários é justamente o que precisa ser verde. Escreva a utilidade nele e veja a base perder a discussão sem precisar de !important.

Acrescente text-green-700 ao link e rode: o texto deve ficar verde, mesmo com a regra de base pintando todos os links de âmbar.

<style type="text/tailwindcss">
@layer base {
  a {
    color: var(--color-amber-700);
    text-underline-offset: 2px;
  }
}
</style>

<a id="alvo" class="underline" href="#">Horários da semana</a>
text-decoration-line: underline

<style type="text/tailwindcss">
@layer base {
  a {
    color: var(--color-amber-700);
    text-underline-offset: 2px;
  }
}
</style>

<a id="alvo" class="underline text-green-700" href="#">Horários da semana</a>

Antes, o painel mostra o sublinhado e nenhuma cor: a cor vem da base, e vale igual para a cópia sem classes, então não aparece como diferença. Depois, aparece a cor verde — porque agora ela vem de uma classe, e só o elemento com a classe a recebe.

Se você já sofreu com CSS antigo, esse comportamento parece bom demais. Em CSS comum, uma regra a { color: … } e uma classe .text-green-700 têm pesos diferentes: a classe (0,1,0) vence a tag (0,0,1), então funcionaria também. O problema apareceria com um seletor de base mais forte, como .conteudo a (0,1,1), que ganharia da classe. Com camadas, isso deixa de existir: a camada decide primeiro, e o peso só é comparado dentro da mesma camada. É por isso que o Tailwind v4 consegue prometer que utilidade vence base, sempre.

6. Base com @apply

Escrever CSS cru dentro da base funciona, mas obriga você a lembrar dos valores: 30 px aqui, 700 ali, a cor em var(). Se a ideia é usar as decisões do tema, o @apply faz o trabalho de traduzir classe em declaração — e mantém as variáveis no lugar dos números, como você viu na aula de plugins.

Na caixa abaixo, o bloco de ingredientes precisa de um padrão para os subtítulos: 24 px, peso 600 e a tinta escura do tema. O h2 não tem classe nenhuma, e é a base que vai resolver.

No @layer base, aplique text-2xl, font-semibold e text-stone-900 ao h2. O subtítulo da receita deve crescer e escurecer.

<style type="text/tailwindcss">
@layer base {
  /* falta o padrão do h2 */
}
</style>

<div id="alvo" class="border border-amber-200 p-4">
  <h2>Ingredientes</h2>
  <p class="text-sm">Farinha, água, sal e paciência.</p>
</div>
padding: 16px
border-width: 1px
border-color: oklch(0.924 0.12 95.746)

<style type="text/tailwindcss">
@layer base {
  h2 {
    @apply text-2xl font-semibold text-stone-900;
  }
}
</style>

<div id="alvo" class="border border-amber-200 p-4">
  <h2>Ingredientes</h2>
  <p class="text-sm">Farinha, água, sal e paciência.</p>
</div>

O @apply na base é o mesmo @apply de qualquer lugar: ele expande a classe nas declarações e mantém os var(). A diferença é o destino — aqui, o CSS entra na camada base, e portanto perde para qualquer utilidade. É exatamente o que você quer de um padrão: valer como ponto de partida e poder ser sobrescrito por quem sabe mais.

Uma ressalva de tamanho: @apply com três ou quatro classes é confortável; com dez, você escreveu um componente e o escondeu numa tag. Se o padrão do h2 já é um bloco com borda, respiro e espaçamento entre linhas, o lugar dele não é a base — é uma classe aplicada no HTML. A base serve para o que é padrão de tag, não para o que é desenho de peça.

7. O que vai em cada camada

Com as quatro camadas na cabeça, a decisão de onde escrever cada regra fica quase automática. A regra de bolso é perguntar “quem deve poder mudar isso depois?”. Se a resposta é “ninguém, é o padrão do site”, é base. Se é “a página decide”, é utilidade no HTML.

Olhe a terceira linha com atenção, porque é a que mais gente erra: uma peça reutilizável não vira regra de base com seletor de classe. @layer base { .cartao { … } } funciona, e é uma armadilha: a classe fica com o peso de uma classe, mas mora numa camada que perde para as utilidades — então o cartão obedece ao HTML em umas propriedades e à base em outras, e ninguém entende a ordem. Se a peça é um componente, escreva as classes no HTML (ou use @utility, que vive na camada certa).

Vale também ter clareza sobre o alcance da base. Ela vale para o documento inteiro, inclusive para o que você não escreveu: uma regra p { margin-bottom: 1rem } atinge parágrafos dentro de cartões, modais e rodapés. Isso é o que se quer num padrão de leitura, e é um problema quando o texto de um componente precisa de outro ritmo. Se você se pegar escrevendo exceções para a base, é sinal de que a regra era grande demais.

8. Armadilhas da base

Três coisas dão errado com uma frequência previsível, e todas têm conserto simples.

A primeira é recorrer ao !important para a classe ganhar da base. Não precisa: a camada utilities já vem depois. Se a sua classe está perdendo, o problema é outro — normalmente uma classe mais específica do mesmo elemento ou uma regra inline no style, que ganha de tudo. Procurar o !important esconde a causa em vez de resolver.

A segunda é escrever a base fora do @layer base. Uma regra de h1 solta no arquivo, sem camada, tem prioridade maior que as camadas — e aí ela passa a ganhar das utilidades, o que derruba a promessa da seção 5. Regra de base sem camada é a causa número um de “coloquei text-lg e não mudou nada”.

A terceira é a base que some. Isso acontece quando o @layer base está num arquivo que o build não lê, ou quando o import do Tailwind mudou de ordem e o seu bloco ficou antes do @layer ser declarado. No projeto com npm, o sintoma é o mesmo de sempre: o CSS publicado está velho. No modo de desenvolvimento, um watch parado deixa tudo como estava.

Há ainda um detalhe de leitura que vale conhecer: o preflight muda de versão em versão do Tailwind, e um projeto que escreve muita base dependendo do que o preflight zera pode sentir a diferença numa atualização. É raro, mas é o tipo de coisa que aparece num sábado. A defesa é simples: escreva na base o que você quer, não o que você acha que o preflight deixou.

9. Cenários do dia a dia

Cenário 1: o título que não obedecia

A Ana escreveu h1 { font-size: 30px } direto no CSS, sem camada, e ficou feliz. Semanas depois, pôs class="text-4xl" num título de página e nada mudou. A regra solta tinha prioridade sobre as camadas, então ganhava até das utilidades. Mover a regra para dentro do @layer base resolveu na hora — e o título voltou a obedecer ao HTML, que é o que se espera de um padrão.

Cenário 2: a lista sem bolinhas que ninguém pediu

A receita mostrou os ingredientes sem marcador, e a Ana estranhou o próprio HTML, que estava certo. O preflight remove o marcador e o recuo das listas de propósito. Para ter as bolinhas de volta, é uma utilidade: list-disc, com pl-5 para o recuo. Quem quer marcador pede marcador — e essa é a mesma lógica que fez o h1 nascer sem tamanho.

Cenário 3: a base que estragou o rodapé

Ela escreveu p { margin-bottom: 1rem } na base e a página de receitas ficou ótima. Três dias depois, o rodapé ganhou um respiro enorme entre a linha de endereço e a de horário, porque as duas são parágrafos. O conserto não foi aumentar a especificidade: foi reconhecer que a regra era grande demais. O ritmo de leitura da receita passou a ser aplicado no bloco da receita, com space-y-4, e a base voltou a cuidar só do que é de todos.

10. Fixando o que ficou

1. Por que o h1 aparece do tamanho do texto no Tailwind?

2. Você tem a { color: … } no @layer base e text-green-700 no elemento. Quem pinta o link?

3. Onde fica uma regra que deve valer para todos os parágrafos do site, mas perder para qualquer classe?

Exercício: o padrão dos títulos

Complete o bloco que coloca a regra dos títulos na camada certa, aquela em que qualquer utilidade ainda pode sobrescrever:

@layer { h1 { font-size: 30px; } }

Dica: é o nome da camada que vem depois de theme e antes de components na primeira linha do CSS gerado. Sem a camada, a regra ganha das utilidades e vira um problema difícil de achar.

11. Resumo

O CSS do Tailwind declara quatro camadas na primeira linha — theme, base, components, utilities — e a ordem decide quem vence. A camada base já vem preenchida com o preflight, que zera margens, bordas e tamanhos de título para o desenho começar igual em todos os navegadores. É por isso que um h1 sem classe parece texto comum: ele herda o tamanho do pai.

O padrão do projeto se escreve em @layer base, com CSS cru ou com @apply, e vale para o documento inteiro. Dali para baixo, toda utilidade ganha — sem !important, sem contar especificidade. Regra de base fora da camada é a exceção que estraga a regra; peça reutilizável não é base; e o painel das caixas não mostra efeito de base, porque ele mede a diferença que as classes fazem.

Para lembrar

  • Quatro camadas, nesta ordem: theme, base, components, utilities.
  • Quem vem depois vence, mesmo com seletor mais fraco.
  • O preflight zera margem, respiro e borda de tudo, e troca para box-sizing: border-box.
  • h1…h6 { font-size: inherit } é o motivo de o título nascer sem tamanho.
  • Padrão do site inteiro vai em @layer base; variação vai em classe no HTML.
  • Dentro da base, @apply mantém as variáveis do tema no lugar dos números.
  • Utilidade ganha de base sem !important: é a camada, não o peso.
  • Regra de base fora do @layer base ganha das utilidades e causa confusão.
  • Peça reutilizável não vira .classe dentro da base; use o HTML ou @utility.
  • O painel das caixas não mostra efeito de base; confira no valor computado.

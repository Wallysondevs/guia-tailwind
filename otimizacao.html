Otimização

O site da Ana está pronto e ela vai mostrar para uma cliente. A cliente abre no celular, no 3G do bairro, e espera. Espera. O pão da vitrine aparece depois de uns quatro segundos, o texto chega antes da cor, e a página fica dando pulinhos enquanto as fontes carregam. A Ana desconfia das fotos — sempre se desconfia das fotos —, mas o culpado é outro: o CSS. Nesta aula ela aprende de onde vem o peso desse arquivo, como medir com números em vez de palpite e as quatro decisões de escrita que mais engordam uma página. Nada de otimização mágica: conta de bytes e escolhas concretas.

Você vai aprender
  • Por que o CSS atrasa o primeiro desenho da página.
  • De onde vem o CSS que o Tailwind gera — e o que não entra nele.
  • Quanto custa cada tipo de classe: valor da escala, valor arbitrário, variante, atalho.
  • Como medir o peso de verdade, no navegador e no terminal, antes de cortar nada.
  • Por que quatro longhands custam mais que p-4.
  • O que a repetição de informação faz com o arquivo.
  • O que o build de produção faz: minificar, comprimir e cachear.
  • O que nunca deve ir para o servidor.

1. A cena: o pão que demora a aparecer

A página da Ana é simples: um cabeçalho, três cartões de pão e um rodapé. As imagens foram reduzidas, as fotos estão em webp, o JavaScript é um arquivo de vinte linhas. Mesmo assim, no celular, a tela fica branca por segundos. Ela abre o painel do navegador, vai na aba Network e ordena por tamanho. O terceiro maior arquivo é saida.css, com setenta e poucos kilobytes.

Setenta kilobytes não é escândalo nenhum, se você compara com uma foto. O problema não é o tamanho absoluto, é o momento em que o arquivo é usado. O navegador não desenha a página antes de baixar e interpretar o CSS: ele precisa saber as regras para decidir onde cada caixa fica. Se o arquivo demora, a tela fica em branco. Isso tem nome — render blocking, bloqueio de desenho — e é a razão pela qual CSS grande dói mais do que imagem grande: a imagem atrasa a imagem, o CSS atrasa tudo.

O segundo detalhe da cena é mais sutil. A Ana não escreveu setenta kilobytes de regras: ela tem três páginas e talvez quarenta classes diferentes. Em algum lugar do projeto entrou coisa que ela não usa, ou a mesma informação foi escrita de cinco jeitos. É isso que a aula vai caçar — com números.

2. O que o navegador baixa antes do primeiro pão

Vale entender a ordem do trabalho do navegador. Ele baixa o HTML, começa a ler, encontra o <link rel="stylesheet"> e para de desenhar até o CSS chegar. Depois aplica as regras e desenha o que já tem. Só então as fontes e as imagens vão chegando. Ou seja: o CSS é o primeiro da fila e o que segura o desenho da página inteira.

Isso muda o que significa “otimizar”. Não é sobre deixar o arquivo bonito, é sobre tirar bytes da frente do primeiro desenho. E existem só três maneiras de tirar bytes dali: mandar menos CSS, mandar o mesmo CSS menor (minificado e comprimido) ou mandar o mesmo CSS uma vez e reaproveitar (cache). As três são assunto desta aula, e a primeira é a que depende de você — é a única que o build não conserta.

Uma armadilha comum de quem está começando: publicar a página com o compilador rodando no navegador. Existe uma build do Tailwind feita para brincar e para prototipar, a que este guia usa nas caixas, e ela compila o CSS no computador do visitante, a cada visita. É ótima para aprender e péssima em produção: o visitante baixa o compilador inteiro para gerar o CSS que você poderia ter gerado em casa. Em produção, o CSS sai pronto do build e a página só o recebe.

3. De onde vem o CSS gerado

Agora a boa notícia, que é a razão pela qual o Tailwind costuma produzir arquivos menores que um CSS escrito à mão. O Tailwind não tem um catálogo gigante para o navegador baixar: ele lê os seus arquivos, encontra as classes escritas e gera regra só para elas. Uma classe que aparece trezentas vezes gera uma regra. Uma classe que aparece uma vez gera uma regra. Uma classe que aparece zero vezes gera nada.

O mesmo vale para o tema. A paleta do Tailwind tem dezenas de famílias de cor e centenas de tons, mas o arquivo não leva a paleta inteira: leva as variáveis que alguma classe usou. Esta é a primeira parte do arquivo gerado por um <div class="bg-amber-100 p-4 rounded-lg">:

@layer theme {
  :root, :host {
    --font-sans: -apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, …;
    --font-mono: ui-monospace, SFMono-Regular, Menlo, Monaco, Consolas, …;
    --color-amber-100: oklch(96.2% 0.059 95.617);
    --spacing: 0.25rem;
    --radius-lg: 0.5rem;
    --default-font-family: var(--font-sans);
    --default-mono-font-family: var(--font-mono);
  }
}

Repare no que não está ali: nenhuma cor que o elemento não usa. Se você trocar bg-amber-100 por bg-red-100, o arquivo troca a variável e não cresce. É por isso que usar a paleta costuma sair mais barato que inventar hexadecimal: bg-[#fef3c7] cria uma regra com um valor solto, enquanto bg-amber-100 aproveita uma variável que outras classes já usam.

E o que é fixo? O reset — a camada base, aquela que zera margens, ajusta títulos e deixa o desenho neutro. Ele vem inteiro, sempre, e custa alguns kilobytes. É o pedágio do Tailwind, e ele não muda com o tamanho do site. Depois dele, tudo é proporcional ao que você escreve.

4. O custo fixo e o custo por classe

Com isso, a conta fica fácil de entender. O arquivo tem uma parte que não depende de você (o reset e algumas variáveis de fonte) e uma parte que cresce com a quantidade de classes diferentes do projeto. Não com a quantidade de elementos: com a quantidade de nomes distintos.

Então o que engorda o arquivo? Quatro coisas, e nenhuma delas é “usar Tailwind”:

O que você fezO que acontece no CSS geradoComo sai mais barato
usou um degrau da escalauma regra apontando para uma variável do temajá é o barato
inventou p-[15px]uma regra nova, com o valor solto dentrop-4 reaproveita o --spacing

repetiu a mesma informaçãouma regra para cada classe repetida, sem ganho visualdeixar uma classe só

Leia a penúltima linha com atenção, porque ela contraria o instinto de quem quer “economizar classes”. Uma variante não duplica o valor: ela embrulha a regra numa condição, @media (width >= 48rem). O peso é o de uma regra, quase sempre pequena. Cortar variantes para “deixar o CSS leve” é economia falsa: você perde a tela funcionando em troca de duzentos bytes.

Já a repetição é economia de verdade. Quando o mesmo elemento carrega p-4 px-4 pt-4, o navegador gera três regras e aplica uma; os outros dois nomes só servem para você ter dúvida sobre qual está ganhando. É o mesmo raciocínio que a aula Estilos de Componente usa para decidir quando dar um nome a uma peça: menos informação repetida, menos arquivo e menos dúvida.

regra
Um seletor e um bloco de declarações: .p-4 { padding: … }. É a unidade de peso do arquivo — cada classe diferente acrescenta pelo menos uma.
custo fixo
A parte do arquivo que independe do seu site: o reset da camada base e as variáveis de fonte. Vem inteira, sempre.
longhand
Uma propriedade por vez: padding-top, padding-left. A classe pt-4 é um longhand escrito de forma curta.
atalho
A classe que age no grupo todo: p-4 mexe nos quatro lados. O CSS dela é uma declaração só.
minificar
Tirar espaços, quebras de linha e comentários do arquivo final, sem mudar o efeito. Feito pelo build.
compressão
gzip ou brotli: o servidor envia o arquivo compactado e o navegador descompacta. Feito pelo servidor, não pelo Tailwind.

5. Missão 1: use a escala em vez de inventar valor

A primeira decisão é a mais comum de todas. A Ana queria um respiro “um tiquinho menor que 16 px” e escreveu p-[15px] nos três cartões da vitrine. Funciona, e cada valor inventado custa uma regra própria. A missão é trocar pelo degrau da escala que corresponde a 16 px:

Os três cartões usam p-[15px], um valor inventado. Troque pela classe da escala que dá 16 px nos três, e clique em Rodar. A meta confere que não sobrou nenhum valor arbitrário e que o respiro ficou em 16 px.

<div class="cartao bg-white p-[15px]">Pão francês</div>
<div class="cartao bg-white p-[15px]">Pão de queijo</div>
<div class="cartao bg-white p-[15px]">Bolo de fubá</div>
padding: 15px
background-color: rgb(255, 255, 255)

<div class="cartao bg-white p-4">Pão francês</div>
<div class="cartao bg-white p-4">Pão de queijo</div>
<div class="cartao bg-white p-4">Bolo de fubá</div>

Depois de rodar, olhe o CSS gerado com calma. Antes, havia uma regra com padding: 15px escrito à mão. Depois, existe padding: calc(var(--spacing) * 4) — a conta, não o resultado. Parece um detalhe de estética de código, e não é: a versão com conta reaproveita a variável --spacing, que já estava no arquivo por causa de outras classes. A versão com 15 px carrega um número que só serve ali.

Há um ganho escondido, e ele vale mais que os bytes: coerência. Quando a Ana decide que o respiro dos cartões é 16 px, ela para de decidir isso em cada cartão. Daqui a um mês, o quarto cartão nasce com p-4 e combina com os outros. O valor arbitrário não é proibido — ele existe para o caso que a escala não cobre, como uma largura que veio de um desenho impresso. Só não pode virar o jeito normal de trabalhar, porque aí você trocou um sistema de degraus por uma coleção de decisões soltas.

6. Missão 2: o atalho no lugar de quatro longhands

A segunda decisão é sobre escrever o mesmo valor por quatro portas. O cartão da Ana tem respiro igual nos quatro lados, mas ela escreveu lado por lado — pt-4 pr-4 pb-4 pl-4. É o que sai de quem veio do CSS antigo, onde se pensava em cada propriedade. Funciona, e custa quatro regras:

.pt-4 { padding-top: calc(var(--spacing) * 4); }
.pr-4 { padding-right: calc(var(--spacing) * 4); }
.pb-4 { padding-bottom: calc(var(--spacing) * 4); }
.pl-4 { padding-left: calc(var(--spacing) * 4); }
.p-4  { padding: calc(var(--spacing) * 4); }

A última linha é o atalho, e ela faz o trabalho das quatro primeiras. No experimento desta aula, trocar as quatro longhands por p-4 num único elemento encolheu o arquivo gerado em cerca de 180 bytes. Parece pouco — e é, num elemento. O problema é que essa repetição aparece em todo canto de um site: cada cartão, cada botão, cada campo. Cento e oitenta bytes por elemento viram dezenas de kilobytes num site inteiro, sem ninguém perceber.

O cartão tem respiro igual nos quatro lados, escrito por quatro longhands. troque as quatro por uma classe só, de 16 px. A meta confere a regra padding: … no CSS gerado e que não sobrou nenhum pt-4.

<div id="alvo" class="rounded-lg bg-amber-50 pt-4 pr-4 pb-4 pl-4">Pão quentinho, saído do forno</div>
background-color: oklch(0.987 0.022 95.277)
border-radius: 8px
padding-top: 16px
padding-right: 16px
padding-bottom: 16px
padding-left: 16px

<div id="alvo" class="rounded-lg bg-amber-50 p-4">Pão quentinho, saído do forno</div>

Vale conhecer os atalhos que existem, porque eles cobrem quase tudo o que a gente escreve: p- é o respiro todo, px- só a horizontal, py- só a vertical, pt-, pr-, pb- e pl- cada lado. O mesmo esquema existe para margem (m-) e para arredondamento (rounded-). E existe o atalho de dois valores de uma vez: size-11 dá largura e altura iguais, no lugar de w-11 h-11.

Só não vale exagerar na direção contrária. Se um cartão precisa de 24 px em cima e 16 px embaixo, o certo é pt-6 pb-4 — duas regras, cada uma dizendo uma verdade. Usar p-4 e depois pt-6 também funciona, mas aí você tem duas regras para a mesma informação vertical, e a de baixo ganha. Menos classes é bom; menos classes dizendo a mesma coisa é o objetivo.

7. Missão 3: não repita informação

A terceira decisão nasce de um hábito inocente: acrescentar a classe que “resolva” em vez de trocar a que já estava. O cartão da Ana tem p-4 e, depois, um px-4 que ela pôs quando tentava acertar o respiro lateral. O resultado visual é idêntico; o arquivo ganha uma regra que não muda nada.

Além do p-4, o cartão carrega px-4 e pt-4, que dizem a mesma coisa que ele. Deixe só a classe que decide o respiro todo e clique em Rodar: o resultado na tela não muda, o CSS gerado diminui.

<div id="alvo" class="rounded-xl bg-white p-4 px-4 pt-4 text-neutral-800">Pão francês, R$ 9,50</div>
padding: 16px
background-color: rgb(255, 255, 255)
color: oklch(0.269 0 none)
border-radius: 12px

<div id="alvo" class="rounded-xl bg-white p-4 text-neutral-800">Pão francês, R$ 9,50</div>

Compare os dois painéis: o CSS computado é padding: 16px nas duas versões. A diferença não aparece na tela; aparece no arquivo e na sua cabeça. Cada classe redundante é uma pergunta que alguém vai fazer daqui a seis meses (“por que tem px-4 se já tem p-4?”), e a resposta é sempre “não sei, foi ficando”. Limpar isso é o tipo de otimização que não tem glamour e tem retorno.

Aproveite a mesma varredura para caçar três primos dessa repetição: a classe que ficou de uma experiência (hover:shadow-2xl num cartão que nunca tem mouse em cima), a que veio copiada de um componente que mudou (text-lg num parágrafo que hoje é text-sm) e a que sobrou de um tema escuro que você abandonou (dark:bg-neutral-900 sem nenhum dark: em volta). Todas geram regra e nenhuma muda o desenho.

8. O arquivo que vai para o servidor

Escrito o CSS, ele ainda passa por duas máquinas antes de chegar ao celular da cliente: o build, que pode minificar (tirar espaços, quebras de linha e comentários), e o servidor, que pode comprimir na hora de enviar (gzip ou brotli) e mandar o navegador guardar o arquivo em cache. Nenhuma das duas é opcional num site público.

EtapaQuanto ajudaQuem faz
gerar só o usadoé o que decide o tamanho: o resto é percentualo Tailwind, lendo seus arquivos
minificartira espaços e comentários; ganho de alguns por cento a um terçoo build, com a opção --minify
comprimir (gzip/brotli)texto de CSS costuma cair para uma fração do tamanhoo servidor
cachea segunda visita não baixa nadaservidor (cabeçalhos) e nome com hash

Duas armadilhas dessa etapa merecem nome. A primeira é publicar a build @tailwindcss/browser: ela compila no navegador do visitante, o que é ótimo para aprender e ruim para entregar — o visitante paga o custo do compilador e do CSS juntos. A segunda é montar nome de classe por código:

const cor = "amber";
elemento.className = "bg-" + cor + "-100";

Isso não funciona, e não é falha de otimização: é a mesma regra da seção 3 vista do avesso. O Tailwind varre o texto dos arquivos; ele vê "bg-", "amber" e "-100", nunca bg-amber-100. A classe não entra no CSS, o elemento fica sem fundo e o arquivo não cresce — o pior dos mundos, porque o defeito aparece só na tela de quem usa. A saída é escrever os nomes inteiros, mesmo que seja num mapa:

const fundo = { ambar: "bg-amber-100", verde: "bg-emerald-100" };
elemento.className = fundo.ambar;

Para medir tudo isso sem abrir o navegador, o terminal resolve. Depois do build, um ls -l na pasta de saída mostra o tamanho do arquivo; um wc -c mostra em bytes. Compare o antes e o depois de cada mudança — e anote os números, porque a memória engana: o que parece “muito menor” costuma ser 3%.

9. Cenários do dia a dia

Cenário 1: o arquivo com 300 KB num site de três páginas

Se o CSS é muito maior do que o site justifica, o problema quase nunca é o Tailwind. As causas prováveis, em ordem: o compilador do navegador ainda está na página; o CSS antigo continua linkado, junto com o novo; existe um arquivo de CSS gerado antigo, commitado por engano; ou o build está varrendo uma pasta que não deveria (uma cópia de segurança com o HTML de outro projeto, uma pasta de exemplos). O caminho é sempre olhar o arquivo gerado e procurar, no texto, uma classe que você reconhece como morta. Se ela está lá, o Tailwind a encontrou em algum lugar — e o trabalho é achar esse arquivo.

Cenário 2: o painel com uma cor diferente em cada cartão

A Ana fez vinte cartões de cor única, cada um com um hexadecimal escolhido no olho: bg-[#f6d9a8], bg-[#f7dca9], bg-[#f5d8a7]. O site ganhou vinte regras quase idênticas e um desenho que parece sujo, porque as cores não combinam de verdade. A troca por três ou quatro tons da paleta resolve as duas coisas de uma vez: menos regras, porque os cartões passam a compartilhar as mesmas variáveis, e um desenho coerente. Cor inventada é o caso mais comum de “o CSS cresceu sem eu mexer em nada”.

Cenário 3: “apaguei metade das páginas e o CSS não encolheu”

A varredura do Tailwind é por texto, não por página visitada. Se você apagou a página mas deixou uma cópia dela em outra pasta, as classes continuam sendo encontradas e as regras continuam no arquivo. O mesmo acontece com classes escritas em comentários de HTML ou em arquivos de teste que ficaram no projeto. Para achar o culpado, procure o nome de uma classe que só existia na página apagada — se ela ainda está no CSS gerado, existe um arquivo com ela em algum lugar do projeto.

Exercício: o cartão da vitrine

Este cartão tem respiro igual nos quatro lados, escrito como quatro longhands. Escreva a classe única que substitui as quatro e dá 16 px de respiro:

<div class="rounded-lg bg-white ">Pão francês</div>

Dica: o atalho do respiro em todos os lados é a letra p com o degrau da escala. 16 px é o quarto degrau, e o CSS que ele gera é padding: calc(var(--spacing) * 4).

11. Resumo

O CSS chega antes do primeiro desenho, então cada byte dele é mais caro que um byte de imagem. O Tailwind ajuda porque gera só o que você usou: nenhuma classe do catálogo entra sem aparecer nos seus arquivos, e nenhuma cor entra na paleta sem ser chamada. O arquivo tem um pedágio fixo (o reset) e um custo variável que depende da quantidade de classes diferentes do projeto.

As quatro decisões que mantêm esse custo baixo são de escrita, não de configuração: usar os degraus da escala em vez de valores inventados (p-4, não p-[15px]); usar atalhos em vez de longhands (p-4, não pt-4 pr-4 pb-4 pl-4); não repetir informação (p-4, não p-4 px-4); e escrever nomes de classe inteiros, para a varredura encontrá-los. Variantes não são o problema: md: e dark: embrulham a regra numa condição, com peso baixo.

Para lembrar

  • CSS bloqueia o desenho: sem ele, a página fica branca.
  • Só entra o CSS das classes escritas nos arquivos — e só as cores usadas.
  • O reset é custo fixo; o resto cresce com o número de classes diferentes.
  • Valor arbitrário cria regra com valor solto; degrau da escala reaproveita a variável.
  • p-4 é uma regra; pt-4 pr-4 pb-4 pl-4 são quatro.
  • size-11 substitui w-11 h-11.
  • Classe que repete a mesma informação gera regra sem mudar nada na tela.
  • Variante é barata; cortar variante é economia falsa.
  • Minificar é do build, comprimir e cachear é do servidor.
  • Nunca publique a build que compila no navegador; nunca monte o nome da classe por pedaços.

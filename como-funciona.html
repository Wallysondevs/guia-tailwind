Como Ele Funciona

A Ana já entendeu que o Tailwind é um catálogo de nomes que viram CSS. A pergunta dela agora é outra, e é bem mais curiosa: "mas quem é que escreve esse CSS?". Ela nunca viu um arquivo com .bg-amber-100 dentro, nunca rodou comando nenhum e, ainda assim, a caixa desta página desenha o cartão colorido quando ela clica em Rodar. Nesta aula ela descobre o caminho inteiro: o Tailwind lê os nomes que estão escritos nos arquivos, gera uma regra para cada nome que conhece, e entrega ao navegador uma folha de estilo comum. Nada de mágica, nada de JavaScript rodando na página.

Você vai aprender
  • Os três passos do caminho: ler, gerar e aplicar.
  • Por que o Tailwind lê texto de arquivo, e não executa o seu código.
  • Por que só o CSS das classes usadas é gerado — e por que isso deixa a página leve.
  • Uma regra serve para todos os elementos que usam a mesma classe.
  • Por que a ordem em que você escreve as classes no HTML não decide nada.
  • O que acontece quando você para de usar uma classe.
  • As camadas do CSS e por que a utilitária vence o estilo padrão do navegador.

1. A cena: o CSS que ninguém escreveu

A Ana abre a página da padaria no navegador e clica com o botão direito, em Inspecionar. Espia a aba Styles esperando encontrar um arquivo chamado estilo.css com as regras que ela conhece. Em vez disso, encontra uma folha com dezenas de regras curtas, todas com nomes que ela reconhece do HTML: .bg-amber-100, .p-6, .rounded-lg. Nenhuma delas foi digitada por ela.

Quem digitou foi um programa. E é aí que a maioria das dúvidas nasce: se eu não escrevi esse CSS, quando ele foi escrito? Ele é escrito quando você salva o HTML e roda o comando que gera o CSS — ou, nas caixas deste guia, quando você clica em Rodar. O programa lê os seus arquivos, encontra os nomes de classe e produz o CSS correspondente. Esse produto é o que o navegador recebe. O navegador nunca soube o que é Tailwind: para ele, é uma folha de estilo como qualquer outra.

Entender esse caminho não é curiosidade de programador. Quase todo problema de "a classe não funciona" nasce em um dos três passos, e saber qual é o passo poupa horas. Se o nome não está escrito em lugar nenhum que o programa leia, o CSS não existe. Se existe, mas está velho, a página mostra o desenho antigo. Vamos passo a passo.

2. O caminho em três passos

O caminho é sempre o mesmo, do começo ao fim:

  • Ler. O Tailwind percorre os arquivos do projeto e anota todo nome de classe que encontra no texto.
  • Gerar. Para cada nome que ele conhece, escreve a regra de CSS correspondente — uma vez por nome, não uma vez por uso.
  • Aplicar. O navegador carrega essa folha e desenha os elementos que têm aquelas classes, exatamente como faria com qualquer CSS.

Repare no que não está na lista: nenhum passo pergunta "qual é o estilo do cartão?". O Tailwind não tem ideia do que seja um cartão. Ele só vê nomes soltos — p-6, bg-amber-100 — e devolve as regras desses nomes. Quem monta o desenho é você, juntando os nomes. É por isso que duas páginas com as mesmas classes ficam iguais e duas páginas com classes diferentes podem não ter nada em comum.

gerador
O programa que faz os dois primeiros passos: lê os arquivos e escreve a folha. Não desenha nada e não avalia a sua página.
arquivo-fonte
Qualquer arquivo que ele percorre procurando nomes: o HTML, o JavaScript, o CSS de entrada. Fora dessa lista, nada é visto.
regra
Um seletor e as declarações dele. .p-2 com padding é uma regra; três elementos usando p-2 continuam gerando uma regra só.
folha gerada
O arquivo de CSS que sai do gerador e é ligado na página. É o que o navegador carrega — e o que fica velho quando o comando não roda.
camada
Um grupo de regras com prioridade definida: theme, base, components e utilities, nesta ordem.

Nas caixas deste guia, o passo de ler e gerar acontece dentro do navegador, para você ver o resultado na hora. No projeto de verdade, ele acontece num comando que você roda no terminal e que pode ficar vigiando os arquivos enquanto você trabalha. A aula de instalação mostra esse comando; o que importa agora é que o resultado é o mesmo: um arquivo de CSS com as regras dos nomes usados.

3. Passo 1: ele lê texto, não executa o seu código

Essa é a parte que mais confunde, então vale dizer com todas as letras: o Tailwind não abre a sua página no navegador, não espera o JavaScript rodar e não olha o que apareceu na tela. Ele lê os arquivos como texto, procurando padrões que pareçam nome de classe. É rápido justamente por isso — ele não precisa entender a sua aplicação, só o texto dela.

Na versão 4 ele também descobre sozinho onde procurar: percorre a pasta do projeto, ignora o que está listado no .gitignore (como node_modules) e ignora arquivos binários, como imagens. Você não precisa entregar uma lista de arquivos, como se fazia em versões antigas. O preço dessa comodidade é justamente o que vimos acima: se o arquivo está fora da pasta do projeto — um rascunho em outra pasta, uma página copiada para a área de trabalho — ele fica invisível para o gerador, e nenhuma classe dele vira CSS.

A consequência é direta: o que não está escrito, não existe. Se a classe é montada em pedaços, o programa vê os pedaços, não o resultado:

<div class="p-{{ tamanho }}">Pão quentinho</div>

Nesse exemplo, o leitor anota p- e tamanho — e nenhum dos dois é uma classe do catálogo. O CSS do respiro não é gerado, e no navegador a classe final, p-6, existe no HTML mas não tem regra nenhuma. O silêncio é total: nem erro, nem aviso. A solução é escrever as classes por inteiro e escolher entre elas na hora de montar a página.

Guarde a linha do comentário: ela explica por que às vezes o CSS tem uma regra que ninguém usa. Não é bug. O programa é burro de propósito — compara letras, não adivinha intenção. E é essa simplicidade que faz ele ser rápido o bastante para rodar a cada salvamento.

4. Passo 2: uma regra por nome, não por uso

Agora a parte elegante. Suponha que a Ana use rounded-lg em três fichas de pão. O Tailwind não escreve três regras: escreve uma, com o seletor .rounded-lg, que serve a qualquer elemento que tenha essa classe. É o mesmo princípio do CSS de sempre — a classe é um nome compartilhado — só que agora você não precisa inventar o nome nem manter a regra em outro arquivo.

As três fichas de pão precisam do mesmo canto arredondado. A primeira já tem rounded-lg; aplique a mesma classe nas outras duas e clique em Verificar.

<div id="alvo" class="bg-amber-100 p-2 rounded-lg">Pão francês</div>
<div class="bg-amber-100 p-2">Pão de queijo</div>
<div class="bg-amber-100 p-2">Bolo de cenoura</div>
padding: 8px
background-color: oklch(0.962 0.059 95.617)
border-radius: 8px

<div id="alvo" class="bg-amber-100 p-2 rounded-lg">Pão francês</div>
<div class="bg-amber-100 p-2 rounded-lg">Pão de queijo</div>
<div class="bg-amber-100 p-2 rounded-lg">Bolo de cenoura</div>

Depois de rodar, repare no tamanho do que foi gerado: uma regra de canto arredondado, uma de fundo, uma de respiro — não importa se cada uma aparece em uma ficha ou em cinquenta. É por isso que uma página cheia de utilitárias não pesa o que parece. O CSS cresce com o número de nomes diferentes, e não com o número de elementos.

Essa contagem vale também para o seu projeto: se você usar quarenta nomes, o arquivo terá umas quarenta regras curtas, mais o pequeno conjunto de variáveis e o reset. Uma biblioteca de componentes tradicional costuma entregar a folha inteira, com todos os componentes, mesmo os que a página não usa. A diferença é grande, e é a razão de o Tailwind ter ficado popular em sites com muitas páginas.

5. Passo 3: o navegador recebe CSS comum

Nada de especial chega ao navegador. O que chega é uma folha de estilo com esta cara:

.bg-amber-100 {
  background-color: var(--color-amber-100);
}
.rounded-lg {
  border-radius: var(--radius-lg);
}
.p-2 {
  padding: calc(var(--spacing) * 2);
}

São três regras, cada uma com uma propriedade, e um punhado de variáveis no topo do arquivo (--color-amber-100, --radius-lg, --spacing). O navegador resolve as contas e desenha. Quando você lê o painel da caixa e vê border-radius: 8px, está vendo o resultado dessa conta — não o texto que o Tailwind escreveu.

Isso explica duas coisas que assustam quem começa. Primeiro, as cores que aparecem como oklch(0.962 0.059 95.617) no painel: é o âmbar claro escrito do jeito que o navegador gosta, e não um erro. Segundo, o painel só mostrar o que mudou: ele compara o elemento com uma cópia sem classe, então propriedades que já eram iguais não aparecem. Se o painel está vazio, nenhuma classe daquele elemento gerou diferença — informação útil, não defeito.

6. A ordem que decide é a do CSS, não a sua

Chegamos ao ponto que mais causa discussão. Todas as utilitárias têm o mesmo peso: são seletores de uma classe só. Quando duas classes mexem na mesma propriedade, o navegador não olha qual você escreveu por último no HTML — olha qual regra aparece por último na folha gerada. E a ordem da folha é decidida pelo Tailwind, seguindo uma sequência interna dele.

A ficha deveria ter cantos de 8 px. A Ana escreveu rounded-sm primeiro e rounded-lg depois, achando que a última venceria. Deixe só a classe que dá o canto certo.

<div id="alvo" class="bg-amber-100 p-2 rounded-sm rounded-lg">Pão quentinho</div>
padding: 8px
background-color: oklch(0.962 0.059 95.617)
border-radius: 4px

<div id="alvo" class="bg-amber-100 p-2 rounded-lg">Pão quentinho</div>

O painel mostra border-radius: 4px antes, mesmo com rounded-lg escrito por último. Quem venceu foi a regra de rounded-sm, porque o Tailwind gerou os cantos pequenos depois dos grandes. Isso não é capricho: a ordem interna existe para que combinações previsíveis funcionem — borda depois de fundo, por exemplo. O efeito colateral é que você não controla nada pela posição no atributo.

A regra prática que resolve é simples: uma propriedade, uma classe. Se o canto precisa ser 8 px, escreva só rounded-lg. Quando quiser variar por tamanho de tela ou por estado do mouse, use as variações próprias para isso — md:rounded-xl, hover:rounded-none — que têm assunto próprio mais adiante. Empilhar duas classes da mesma família é apostar na sorte.

E não dá para deduzir a ordem interna de cabeça. Estes três casos mostram por que a aposta é ruim: em cada linha, a segunda classe foi gerada antes ou depois da primeira, e o resultado não segue a ordem em que você digitou.

Duas classes no mesmo elementoO que aconteceConclusão
p-2 e p-6vale 24 px, em qualquer ordemp-6 é gerado depois
rounded-sm e rounded-lgvale 4 px, mesmo com rounded-lg por últimorounded-sm é gerado depois
text-sm e text-2xlvale 14 px, mesmo com text-2xl por últimoa ordem não é "do menor para o maior"

Se você guardar uma coisa desta seção, guarde esta: não existe posição no atributo que garanta vitória. A conversa sobre quem vence é sempre sobre a folha gerada, e a única forma de não depender dela é não ter duas classes disputando a mesma propriedade.

7. A folha encolhe quando você para de usar

O terceiro passo tem uma consequência que a Ana vai adorar: o CSS acompanha o uso. Se ela apaga uma classe do HTML e roda o comando de novo, a regra daquela classe simplesmente não é gerada. Nada de arquivo morto acumulando, nada de limpeza manual no fim do projeto.

A ficha do pão passou a usar o fundo da página, sem cor própria. Apague a classe de fundo e deixe o respiro: o painel deve perder a linha do background-color.

<div id="alvo" class="bg-amber-100 p-4">Pão quentinho</div>
padding: 16px
background-color: oklch(0.962 0.059 95.617)

<div id="alvo" class="p-4">Pão quentinho</div>

Compare o painel antes e depois: a linha do fundo sumiu, a do respiro ficou. No projeto, o mesmo acontece com a folha inteira — a regra deixa de existir porque nenhum arquivo pede mais por ela. É essa característica que faz o CSS de um site grande ficar em dezenas de kilobytes em vez de centenas.

Vale notar o outro lado: como o CSS é gerado a partir do texto, ele também não sabe se a classe é útil. Uma classe escrita num comentário, num trecho de exemplo ou numa página que você nem usa mais gera regra do mesmo jeito. Não é problema de desempenho — são bytes — mas é bom saber por que às vezes aparece uma regra órfã na inspeção.

8. As camadas: por que a utilitária ganha do padrão

Falta explicar por que p-4 funciona mesmo quando o navegador já tem uma opinião sobre espaçamento. A resposta está nas camadas do CSS. A versão 4 organiza a folha em quatro camadas, nesta ordem:

@layer theme, base, components, utilities;

A camada theme guarda as variáveis (cores, espaços, fontes). A base traz o pequeno reset que zera margens e deixa o desenho neutro. components é onde ficam estilos de conjunto, se você criar algum. utilities é a última — e, no CSS, quem vem depois ganha quando o peso é o mesmo. Resultado: a sua utilitária sempre vence o reset e os estilos de conjunto, sem precisar de !important nem de seletor comprido.

É por isso que m-0 realmente zera a margem que o navegador dava ao parágrafo, e por que p-6 não briga com nada. Você não precisa decorar as quatro camadas. Precisa saber que existe uma ordem pensada e que a utilitária fica no fim: quando algo não pega, o suspeito raramente é a camada — quase sempre é o nome errado ou o CSS velho.

9. Cenários do dia a dia

Cenário 1: "mudei o HTML e a página não mudou"

Três suspeitos, nesta ordem. O comando que gera o CSS não está rodando (ou não foi executado depois do salvamento) — o arquivo está velho. O navegador guardou a folha antiga no cache — recarregue com Ctrl + Shift + R. Ou você editou um arquivo que o Tailwind não lê, como uma cópia fora da pasta do projeto. Nas caixas do guia, o equivalente é não ter clicado em Rodar depois de editar.

Cenário 2: "a classe está no HTML e mesmo assim não aparece"

Se o nome está escrito e o CSS não existe, desconfie do nome: uma letra trocada, um hífen no lugar do traço, maiúscula onde devia ser minúscula. O Tailwind não corrige e não avisa. A conferência rápida é comparar com a solução da caixa, letra por letra, e olhar o painel: se a propriedade não aparece, a regra não foi gerada. O segundo suspeito é o tal nome montado em pedaços, que nunca chega inteiro ao leitor de arquivos.

Cenário 3: "o cartão mudou de tamanho sozinho quando eu reordenei as classes"

Sintoma clássico de duas classes da mesma família no mesmo elemento. Reordenar não muda nada por si; o que muda é que, ao editar, uma delas saiu sem querer. A cura é a mesma de sempre: uma propriedade, uma classe. Se precisar de valores diferentes por tela, use as variações (p-4 md:p-8) em vez de empilhar.

Exercício: da regra para a classe

O CSS gerado tem a regra abaixo. Escreva no HTML a classe que a produziu:

<p class="">Pão quentinho às 6h</p>

Dica: a propriedade é text-align, o valor é center. A família do texto é text e o valor entra depois de um hífen, sem espaço.

11. Resumo

O Tailwind é um gerador de CSS em três passos. Ele lê os arquivos do projeto como texto e anota os nomes de classe; para cada nome que conhece, escreve uma regra — uma só, mesmo que a classe apareça em cinquenta elementos; e entrega essa folha ao navegador, que não sabe nem se importa de onde ela veio.

Como a leitura é textual, o nome precisa estar escrito por inteiro em algum arquivo que o programa percorra. Como a geração é sob demanda, a folha tem exatamente o tamanho do uso — e encolhe quando você deixa de usar uma classe. E como todas as utilitárias têm o mesmo peso, quem decide a briga entre duas classes da mesma propriedade é a ordem da folha gerada, e não a ordem do seu HTML. A saída continua sendo a mesma: uma propriedade, uma classe.

Para lembrar

  • O caminho é ler, gerar e aplicar — nessa ordem, sempre.
  • A leitura é de texto: ele não executa o seu código nem olha a tela.
  • Classe montada em pedaços não existe para o gerador.
  • Classe desconhecida é ignorada em silêncio: sem erro, sem aviso.
  • Uma regra serve a todos os elementos que usam a mesma classe.
  • O CSS cresce com o número de nomes diferentes, não de elementos.
  • A folha encolhe quando você apaga a classe do HTML.
  • Entre duas classes da mesma propriedade, vence a última regra gerada.
  • Utilitárias ficam na última camada, por isso vencem o reset do navegador.
  • Nada de Tailwind chega ao navegador: ele recebe CSS comum.

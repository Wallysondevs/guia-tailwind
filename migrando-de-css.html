Migrando de CSS Antigo

O site da Ana tem três anos e um arquivo chamado estilo.css com quase três mil linhas, escrito por ela mesma, uma regra por vez, na época em que ela estava aprendendo. O site funciona. Mexer nele dá medo. Agora que ela aprendeu Tailwind, quer migrar — e o primeiro impulso é o pior de todos: apagar o arquivo inteiro e reescrever tudo num fim de semana. Nesta aula ela faz o contrário do impulso: migra uma peça por vez, com os dois CSS convivendo, traduz regra por regra e só apaga o antigo quando não sobra nada apontando para ele. É mais devagar no começo e muito mais rápido no fim.

Você vai aprender
  • Por que os dois CSS podem viver juntos — e o que isso cobra em troca.
  • A ordem que funciona: inventário, tradução, remoção.
  • A tabela de tradução: de font-weight: bold para font-bold.
  • A ponte com @apply: mudar o CSS sem tocar no HTML.
  • O segundo passo: o HTML assume as classes e a regra antiga é apagada.
  • Por que o CSS sem camada vence as utilitárias, e como evitar a briga.
  • O que fazer com style="" inline e com !important.
  • O que não se migra, e como conferir que nada quebrou.

1. A cena: o arquivo de 2.874 linhas

O estilo.css da Ana começou pequeno. Uma regra para o corpo, outra para o menu, outra para o cartão. Três anos depois, ele tem 2.874 linhas, das quais ela reconhece umas duzentas. Tem .botao, .botao2, .botao-novo e .botao-novo-2. Tem três resets diferentes, um deles copiado de um tutorial e nunca entendido. Tem !important em quatro lugares, que ela pôs numa tarde de desespero e nunca tirou.

$ wc -l estilo.css
2874 estilo.css

Esse arquivo não é um fracasso: é o retrato de três anos de aprendizado. O problema não é o passado, é o futuro — cada mudança nova é uma aposta, porque ninguém sabe quais das 2.874 linhas dependem daquela que você vai mexer. Migrar para Tailwind resolve isso, desde que a migração não vire uma aposta ainda maior.

A tentação do “fim de semana de reescrita” falha por um motivo prático: você não tem como saber o que o CSS antigo faz até apagá-lo. Aquele margin-top: -2px na linha 1.402 está lá por um motivo que a Ana não lembra, e apagar tudo de uma vez descobre cinco defeitos ao mesmo tempo, sem saber qual deles veio de onde. Migração boa é migração com rede.

2. Os dois CSS podem viver juntos

A primeira boa notícia: o navegador não tem opinião sobre de onde vem o CSS. Duas folhas de estilo convivem sem conflito de tecnologia — o Tailwind gera um arquivo .css como qualquer outro, e o antigo continua sendo um arquivo .css. Você pode ter os dois no <head> e migrar no seu ritmo:

<link rel="stylesheet" href="estilo-antigo.css">
<link rel="stylesheet" href="saida.css">

O que os dois dividem é o espaço: as mesmas propriedades, os mesmos elementos. Enquanto a página tiver as duas folhas, existe o risco de uma regra do arquivo antigo e uma classe do Tailwind quererem a mesma coisa — e aí vence quem o navegador decidir. É por isso que a migração precisa de ordem, e não só de coragem.

A segunda boa notícia é que esse estado é temporário e mensurável. Dá para migrar página por página: a página de encomendas passa a usar só Tailwind, a vitrine continua no CSS antigo, e o site inteiro funciona durante todo o processo. O que você não pode é deixar o estado intermediário virar permanente: dois CSS carregados em todas as páginas é o dobro de peso, o dobro de confusão e a garantia de que daqui a um ano ninguém sabe qual dos dois manda. A aula Otimização mostra a conta do peso; aqui a conta é de dívida.

CSS sem camada
Regra escrita sem @layer, como todo CSS antigo. Ela ganha das regras que estão dentro de camadas.
@layer base
A primeira camada do Tailwind, onde ficam os estilos de base. Colocar ali o CSS antigo faz com que ele perca para as utilitárias.
ponte
O uso do @apply durante a migração: a regra antiga é traduzida, o HTML fica intacto.
style inline
O atributo style="" no elemento. Vence folhas de estilo e camadas; só perde para !important.
regressão
O que funcionava e parou de funcionar depois da mudança. Migração se mede por ausência de regressão.
!important
Marca de prioridade máxima numa declaração. Herança comum do CSS antigo e a maior pedra no caminho da migração.

3. A ordem que funciona: inventário, tradução, remoção

Três etapas, sempre nesta ordem.

Inventário. Antes de traduzir qualquer coisa, descubra o que existe. Abra o arquivo antigo e conte quantas regras de cada tipo: layout (largura, grid, flex), tipografia (tamanho, peso, cor), componentes (botão, cartão, selo), estados (:hover, :focus), mídia (@media) e as regras de reset do começo. Esse mapa diz por onde começar — e o melhor lugar para começar é sempre o mais repetido.

Tradução. Regra por regra, descubra a classe equivalente. A tabela abaixo é o começo; vale manter a sua ao lado do arquivo, porque você vai consultá-la dezenas de vezes:

CSS antigoTailwindObservação
padding: 16pxp-4a escala é de 4 em 4 px
border-radius: 8pxrounded-lgo valor computado confirma
font-weight: 700font-bold600 é font-semibold
display: flex; gap: 16pxflex gap-4uma classe por propriedade
background: #fef3c7bg-amber-100troque o hexadecimal pela paleta
color: #b4532atext-amber-700o tom mais próximo, não o exato
@media (min-width: 768px)md:na frente da classe
.botao:hoverhover: ou regra própriadepende de onde você está migrando

Remoção. Só depois que a página inteira não usa mais uma regra, ela sai do arquivo antigo. Remover antes de traduzir é como trocar o piso com os móveis dentro. E remover é o passo que as pessoas esquecem: sem ele, você acaba com dois sistemas para sempre, que é pior do que o começo.

Uma dica de ordem dentro da ordem: comece pelos tokens, não pelos componentes. Se o arquivo antigo tem color: #b4532a repetido em vinte regras, o primeiro trabalho é descobrir qual tom da paleta substitui aquele marrom, e usar sempre o mesmo. Assim, cada componente que você migra depois já nasce coerente, e a paleta deixa de ser uma coleção de acidentes.

4. Missão 1: a ponte com @apply

Aqui está o truque que torna a migração segura. Em vez de trocar o HTML e o CSS ao mesmo tempo, troque só o CSS, mantendo o nome da classe. O HTML continua com class="botao"; o que muda é o conteúdo da regra:

/* antes */
.botao {
  background: #b4532a;
  padding: 6px 10px;
  border: 0;
}

/* depois */
.botao {
  @apply rounded-lg bg-amber-600 px-4 py-2 text-white;
}

Como nada no HTML mudou, não há risco de esquecer um lugar. Tudo o que tinha class="botao" continua com a aparência nova, e você confere numa página de cada vez. Esse é o uso mais honesto do @apply: ponte de migração, não destino final.

A regra antiga do botão usa hexadecimal e respiro de 6 px por 10 px. Traduza-a para utilitárias dentro do @apply, mantendo o seletor .botao e o HTML intactos: fundo bg-amber-600, respiro px-4 py-2, cantos rounded-lg e texto branco.

<style type="text/tailwindcss">
.botao { background: #b4532a; padding: 6px 10px; border: 0; }
</style>
<button id="alvo" class="botao">Comprar pão</button>
padding: 6px 10px
background: rgb(180, 83, 42) none repeat scroll 0% 0% / auto padding-box border-box

<style type="text/tailwindcss">
.botao { @apply rounded-lg bg-amber-600 px-4 py-2 text-white; }
</style>
<button id="alvo" class="botao">Comprar pão</button>

O painel depois da tradução mostra padding-inline: 16px e padding-block: 8px — a mesma medida que você escreveria em CSS, só que escrita em degraus da escala. E o hexadecimal #b4532a virou bg-amber-600, que é o degrau mais próximo do marrom original. Essa troca de hex por degrau é uma decisão, não uma obrigação: você aceita um tom ligeiramente diferente em troca de coerência com o resto do site. Na maioria dos casos, é a melhor troca da migração.

Se a regra antiga tiver dez propriedades, traduza as dez de uma vez, mesmo que o @apply fique comprido. Nesta etapa, comprido e fiel é melhor que curto e diferente: você quer ver o mesmo desenho na tela, com o CSS do Tailwind por baixo. Enxugar vem depois.

5. Missão 2: o HTML assume as classes

Passada a ponte, o segundo passo é real: as classes vão para o HTML e a regra antiga morre. Aqui o número de lugares importa — se .botao aparece em três páginas, são três edições, e é exatamente por isso que a ponte veio antes: com ela, você já sabe que a tradução está certa.

Agora tire o .botao do CSS e ponha as utilitárias no próprio botão. A meta confere o respiro de 16 px e que não sobrou nenhum elemento com a classe botao.

<style type="text/tailwindcss">
.botao { background: #b4532a; padding: 6px 10px; border: 0; }
</style>
<button id="alvo" class="botao">Comprar pão</button>
padding: 6px 10px
background: rgb(180, 83, 42) none repeat scroll 0% 0% / auto padding-box border-box

<button id="alvo" class="rounded-lg bg-amber-600 px-4 py-2 text-white">Comprar pão</button>

Depois de rodar, o CSS antigo sumiu do exemplo e o botão continua igual — é isso que “migração sem regressão” quer dizer. Com a regra fora do arquivo, o .botao deixa de existir para sempre e ninguém pode reutilizá-lo por engano.

Aqui vale uma decisão consciente: nem todo botão precisa de utilitárias no HTML. Se aquele botão aparece em vinte páginas, criar um componente com @apply (aula Estilos de Componente) é o destino certo. A diferença entre a ponte e o componente é a intenção: na ponte, a regra está ali para ser apagada; no componente, ela está ali para ficar, porque é o lugar onde o desenho mora.

6. O cuidado da camada: por que o CSS antigo vence

Esta é a parte que pega todo mundo de surpresa, e a única que pode fazer a migração “não funcionar”. As utilitárias do Tailwind moram numa camada de CSS (@layer utilities). O CSS antigo, escrito à mão, não está em camada nenhuma. E o CSS tem uma regra pouco intuitiva: o que está fora de camada vence o que está dentro, quando a especificidade é parecida.

Na prática: você acrescenta bg-amber-100 num cartão que ainda tem .cartao { background: #fde68a } no arquivo antigo, e o cartão continua amarelo. Não é bug; é a ordem do navegador. Duas saídas, e as duas são legítimas:

1. Migre a regra, não conviva com ela. Enquanto o elemento tem classe antiga, ele não deve receber utilitária da mesma propriedade. Esse é o caminho normal da migração: uma peça de cada vez.

2. Coloque o CSS antigo dentro de uma camada. Envolver o arquivo antigo (ou as regras que ficaram) em @layer base faz com que ele perca para as utilitárias, e você pode migrar com tranquilidade, ajustando uma coisa de cada vez:

@layer base {
  .cartao { background: #fde68a; padding: 8px; }
}

Depois disso, um bg-amber-100 no HTML ganha do .cartao antigo, e você consegue ver o que a migração está fazendo. O preço é que as regras antigas passam a perder também para as utilitárias de outras partes da página — o que, em migração, é exatamente o que você quer: o novo manda, o velho cede.

.botao {
  border-radius: var(--radius-lg);
  background-color: var(--color-amber-600);
  padding-inline: calc(var(--spacing) * 4);
  padding-block: calc(var(--spacing) * 2);
  color: var(--color-white);
}

Esse é o CSS que a ponte produziu na missão 1. Repare que ele não tem nenhum hexadecimal: todas as cores e medidas passaram a vir das variáveis do tema. É esse detalhe que faz a migração valer a pena no fim — o site deixa de ter dezenove marrons diferentes e passa a ter um.

7. Missão 3: o style="" inline

Existe um terceiro tipo de CSS antigo, mais teimoso que a folha de estilo: style="…" escrito direto no elemento. Ele vence qualquer folha — inclusive as utilitárias, inclusive as camadas — porque é o que o navegador considera mais específico. Enquanto ele estiver ali, nenhuma classe de fundo vai conseguir mudar aquele fundo.

Este cartão carrega o respiro e o fundo no atributo style, e enquanto eles estiverem ali nenhuma classe ganha nessas duas propriedades (o rounded-lg, que o style não define, funciona normalmente). Apague o style e escreva as mesmas decisões em classes: 24 px de respiro (p-6) e fundo âmbar claro (bg-amber-100). A meta confere o respiro, o fundo no CSS gerado e que não sobrou nenhum style.

<div id="alvo" class="rounded-lg" style="padding:24px;background:#fef3c7">Pão quentinho</div>
border-radius: 8px

<div id="alvo" class="rounded-lg bg-amber-100 p-6">Pão quentinho</div>

Repare no detalhe da meta: conta:[style]=0. Só as classes não bastavam, porque o atributo continuaria vencendo e a tela não mudaria. Isso ilustra o motivo pelo qual migração de style inline é sempre em duas etapas — apagar e depois escrever — e nunca “acrescentar a classe e ver depois”.

O mesmo raciocínio vale para o !important do arquivo antigo. Uma declaração color: #6b7280 !important ganha de text-amber-900, mesmo com a camada a favor do Tailwind. O Tailwind aceita text-amber-900! (no v4 o ponto de exclamação vai no fim da classe), e essa é uma saída de emergência útil em migração — mas cada !important novo é uma pergunta a menos que o próximo desenvolvedor consegue responder. A regra: use o ! para desbloquear uma tela hoje, e anote para tirar.

8. O que não se migra (e como não quebrar nada)

Nem tudo deve virar classe. Cinco coisas costumam ficar onde estão, com motivos diferentes:

Peça do CSS antigoMigrar?Por quê
reset e normalizaçãonãoo Tailwind já traz o dele na camada base
terceiros (biblioteca, plugin)nãovocê não é dono do arquivo e ele muda sozinho
@keyframes longostalvezvale quando viram @theme; senão, deixe em CSS
estilos de impressãodependea variante print: cobre o simples; o resto fica
font-facesima fonte vira uma variável do tema

Ao lado do “o que migrar”, o “como conferir”. Uma migração sem conferência é uma aposta. Três checagens simples resolvem a maior parte:

Print de tela antes e depois. Tire uma captura da página antes de migrar e outra depois. O olho humano pega diferença de 2 px em duas imagens lado a lado, e não pega olhando a mesma página duas vezes em dias diferentes.

Uma página por vez. Migre a vitrine, confira, publique. Depois a lista de pães, confira, publique. Se algo quebrar, você sabe exatamente de onde veio. A pressa de migrar tudo junto é a maior fonte de defeito silencioso.

Procure o nome que morreu. Antes de apagar uma regra do arquivo antigo, procure o nome da classe em todos os arquivos do projeto. Se aparecer em algum HTML que você esqueceu, você descobriu o problema antes do cliente. No terminal, um grep pelo nome resolve:

$ grep -rn "botao-antigo" --include=*.html .
encomendas.html:24:    <button class="botao-antigo">Comprar</button>

Uma armadilha dessa busca: ela acha texto, não uso. Comentário de HTML também aparece, e código comentado não precisa de migração — mas também não precisa de classe. Aproveite a varredura para apagar o que está comentado e não volta nunca mais.

9. Cenários do dia a dia

Cenário 1: a migração que nunca termina

Dois anos depois, o site ainda tem as duas folhas de estilo: metade das páginas em Tailwind, metade no CSS antigo, e cada página nova copia classes antigas porque é mais rápido. O sintoma é conhecido: a migração parou no meio e virou o estado permanente. O antídoto é uma regra de trabalho, não de CSS: nenhuma página nova usa o CSS antigo. A partir do dia em que você começa, tudo o que é novo é utilitária; o antigo só pode encolher.

Cenário 2: a classe nova não faz efeito nenhum

Você pôs bg-white no cartão, salvou, e nada. Nove entre dez vezes, o cartão ainda tem uma regra do CSS antigo mandando no fundo, ou um style="" esquecido no HTML, ou um !important herdado. O caminho de diagnóstico está na aula Depurar o CSS: o painel Styles do navegador mostra a regra vencedora, com o arquivo de onde ela veio. A resposta “veio de estilo-antigo.css, linha 402” é o fim da discussão.

Cenário 3: o site ficou 2 px diferente (e ninguém sabe onde)

Ao trocar margin: 7px por m-2 (8 px), a Ana ganhou 1 px de respiro e a grade desalinhou no terceiro cartão. Migração sempre tem esse tipo de arredondamento, porque a escala do Tailwind é discreta. A saída não é fugir da escala: é aceitar o degrau mais próximo e ajustar o desenho como um todo, em vez de manter um valor solto só para não mexer num pixel. Se algum valor realmente não puder mudar, existe a válvula dos colchetes — m-[7px] —, para ser usada com motivo escrito.

11. Resumo

Migrar de CSS antigo não é reescrever: é substituir por partes, com os dois CSS convivendo e cada página funcionando durante o processo. A ordem é inventário, tradução e remoção. A ponte com @apply deixa o HTML intacto enquanto você confere a tradução; depois as classes vão para o HTML e a regra antiga é apagada. style="" inline e !important vencem qualquer utilitária e precisam sair — cada um a seu tempo.

A armadilha técnica do caminho é a camada: CSS sem camada ganha das utilitárias, então ou você migra a regra, ou coloca o arquivo antigo em @layer base para ele ceder. E o cuidado final é o que separa migração de aposta: uma página por vez, print de tela antes e depois, e uma busca pelo nome da classe em todos os arquivos antes de apagá-la.

Para lembrar

  • Os dois CSS convivem: o navegador não liga para a origem das regras.
  • Ordem: inventário, tradução, remoção. Nunca remover antes de traduzir.
  • Comece pelo que se repete: botão, cartão, preço.
  • A ponte é .botao { @apply … } com o HTML intacto.
  • Depois, as utilitárias vão para o HTML e a regra antiga morre.
  • CSS sem camada vence utilitária; @layer base faz o antigo ceder.
  • style="" inline vence tudo: apague antes de tentar sobrescrever.
  • Hexadecimal vira degrau da paleta: aceite o tom mais próximo.
  • Nada de página nova com CSS antigo — senão a migração nunca termina.
  • Confira com print de tela e grep pelo nome antes de apagar.

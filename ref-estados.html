Estados e Variantes

A Ana já sabe dar respiro, cor e borda ao cartão da padaria. O problema agora é outro: o botão de encomendar está bonito, mas parece morto — o mouse passa por cima e nada muda, e quem navega com a tecla Tab não enxerga onde está o foco. Ela viu num site que dá para escrever hover junto com a classe, separado por dois-pontos, e quando abriu o CSS que o navegador mostrou encontrou um nome estranho, com uma barra invertida no meio. Esta página é a consulta dela — e a sua: cada variante de estado, o CSS que o Tailwind v4 escreve de verdade, quando usar e o que não funciona.

1. O que é uma variante

Uma variante é uma condição colada na frente de uma classe, separada por dois-pontos. A classe continua sendo a mesma de sempre; o que muda é quando ela vale. bg-amber-600 pinta o fundo sempre. hover:bg-amber-600 pinta o fundo só enquanto o ponteiro está em cima do elemento. O Tailwind lê esse prefixo, monta um seletor com a condição e gera uma regra nova, com um nome de classe novo.

O detalhe que assusta no começo é o escape. O nome da classe no HTML tem dois-pontos (hover:bg-amber-600), e dois-pontos não pode aparecer cru num seletor CSS, porque ali ele significa outra coisa. Então o Tailwind escreve uma barra invertida antes: .hover\:bg-amber-600. Essa barra não é erro de digitação nem coisa de programador experiente: é só o jeito de dizer ao navegador "esse dois-pontos faz parte do nome". Você nunca digita essa barra no HTML — ela nasce no CSS gerado, e é por isso que ela aparece tanto nas saídas desta página.

Vale guardar uma consequência prática dessa mecânica: a variante só existe se a classe inteira estiver escrita no HTML. O Tailwind não adivinha combinações. Se você escrever class="bg-amber-600" e tentar ligar o hover por JavaScript juntando pedaços de texto ("hover:" + "bg-amber-600"), a regra pode nunca ser gerada. A variante é resolvida na hora de compilar, não na hora do clique. Isso volta na seção 8, porque é a causa de metade dos "meu hover não funciona" que aparecem nos fóruns.

variante
O prefixo com dois-pontos: hover:, md:, dark:, group-hover:. Diz em que condição a classe vale.
pseudo-classe
Um estado que o próprio navegador controla, escrito com dois-pontos no CSS: :hover, :focus, :checked, :first-child.
prefixo
O que vem antes dos dois-pontos. Pode ser uma condição de tela (md:), de tema (dark:) ou de estado (disabled:).
grupo
O pai marcado com group, que serve de gatilho para os filhos usarem group-hover: e parentes.
par
O irmão marcado com peer, usado quando quem muda de estado é um campo de formulário e quem reage é o texto ao lado.

Repare que uma variante não é um "modo". Ela não desliga a classe base: as duas convivem, e o navegador decide qual aplicar em cada momento. É por isso que class="bg-amber-500 hover:bg-amber-600" funciona — o âmbar 500 é o repouso, o 600 é o estado. Uma dica de leitura que ajuda muito: leia a classe da direita para a esquerda. Primeiro "fundo âmbar 600", depois "quando o mouse estiver em cima".

2. Ponteiro e teclado

As variantes de interação são as primeiras que todo mundo usa, e as que mais confundem, porque duas delas parecem iguais. focus: pega qualquer foco, inclusive o que nasce de um clique do mouse. focus-visible: pega só o foco que o navegador considera "de teclado", ou seja, quando a pessoa chegou ali com Tab. Na prática: use focus-visible: para o anel de destaque e focus: quando o campo precisa mudar de aparência de qualquer jeito, como um input que ganha borda âmbar ao ser clicado. A aula O focus mostra o mesmo raciocínio aplicado a um formulário inteiro.

Outra mudança do Tailwind v4 que pega muita gente: hover: não vira mais um :hover solto. Ele vem embrulhado numa consulta de mídia, @media (hover: hover). Isso significa que, num celular ou num tablet sem mouse, a regra de hover simplesmente não existe — o navegador não tem como "passar o mouse". O efeito é intencional: evita que um toque deixe o botão preso no estado escuro até o próximo toque. Se você quer que o toque também dê retorno visual, use active:.

Quando o Tailwind encontra hover:bg-amber-600 e focus-visible:ring-2 no mesmo botão, ele gera duas regras separadas. Vale ver o texto exato, porque ele explica duas coisas de uma vez: o escape do dois-pontos e o fato de o ring ser uma sombra, não uma borda.

@media (hover: hover) {
  .hover\:bg-amber-600:hover {
    background-color: var(--color-amber-600);
  }
}
.focus-visible\:ring-2:focus-visible {
  --tw-ring-shadow: var(--tw-ring-inset, ) 0 0 0 calc(2px + var(--tw-ring-offset-width)) var(--tw-ring-color, currentcolor);
  box-shadow: var(--tw-inset-shadow), var(--tw-inset-ring-shadow), var(--tw-ring-offset-shadow), var(--tw-ring-shadow), var(--tw-shadow);
}

Duas leituras úteis. Primeiro: a cor vem de uma variável (--color-amber-600), não de um hexadecimal, então trocar a paleta depois é trocar a variável. Segundo: o anel é montado com box-shadow e variáveis próprias — se você tentar "consertar" o anel com border, o layout vai pular 2 px, porque borda ocupa espaço e sombra não. É por isso que o guia insiste no ring para foco.

O botão de encomendar está morto: nada acontece quando o mouse passa e não há sinal de foco. Acrescente o escurecimento no hover (hover:bg-amber-600) e o anel de 2 px para quem usa teclado (focus-visible:ring-2).

<button id="alvo" class="rounded-lg bg-amber-500 p-3 text-white">Encomendar pão</button>
padding: 12px
background-color: oklch(0.769 0.188 70.08)
color: rgb(255, 255, 255)
border-radius: 8px

<button id="alvo" class="rounded-lg bg-amber-500 p-3 text-white hover:bg-amber-600 focus-visible:ring-2">Encomendar pão</button>

Clique em Rodar e depois em Verificar. O painel vai continuar mostrando o mesmo respiro e a mesma cor de repouso, porque o estado não está ligado — nenhum mouse está em cima do botão. O que muda está no CSS gerado, e é justamente por isso que a missão confere com rule: e não com css:. Para ver o efeito com os olhos, passe o mouse na prévia e aperte Tab até o botão.

3. Estados de formulário

Aqui mora a maior economia de JavaScript do Tailwind. O navegador já sabe se um campo está preenchido, inválido, desabilitado ou marcado; as variantes só dão nomes a esses fatos. A tabela abaixo é a lista completa do que o motor gera hoje, com o seletor real de cada uma.

user-valid::user-valida mesma ideia do lado positivo

A diferença entre invalid: e user-invalid: é a que mais estraga formulário bonito. :invalid é verdadeiro desde o primeiro desenho da tela: um campo obrigatório vazio já é inválido. Se você pintar de vermelho com invalid:, o formulário inteiro nasce vermelho e a pessoa se sente culpada antes de digitar. :user-invalid só aparece depois que houve interação de verdade — é o que você quer em quase todos os casos. O suporte é bom nos navegadores atuais, e quando falta, o pior que acontece é o destaque não aparecer; nada quebra.

Um lembrete que vale para todas as variantes desta seção: elas dependem do estado real do elemento. disabled: só pega button, input, select, textarea, fieldset e option. Num div, o atributo disabled não existe e a regra nunca casa. Para um bloco que "parece desabilitado", use um atributo que você mesmo controla — data-bloqueado com data-bloqueado:opacity-50 — ou o par aria-disabled="true" com aria-disabled:opacity-50. A segunda opção é melhor, porque o leitor de tela entende o atributo.

4. Posição na lista: first, last, odd e even

Estas variantes não dependem de quem está olhando, e sim do lugar do elemento entre os irmãos. São as que mais economizam marcação: em vez de dar uma classe diferente ao primeiro item do cardápio, você diz "todo primeiro filho não tem borda em cima". O seletor gerado é literal — dá para ler e conferir.

not-first::not(:first-child)borda em cima de todos, menos no primeiro

O ponto que derruba iniciante é o significado de "filho". first: quer dizer "primeiro filho do pai", não "primeiro item da minha lista". Se entre os filhos houver um título h3 antes do primeiro li, o li deixa de ser o primeiro filho e a classe não faz efeito nenhum. É aí que entra first-of-type:: ele conta só os elementos do mesmo tipo, então o primeiro li volta a ser o primeiro. Escolher entre um e outro é observar o HTML em volta, não a lista em si.

A lista do cardápio está toda branca e os olhos se perdem. Ponha fundo bg-amber-50 nos itens ímpares e bg-white nos pares, usando as variantes — sem classe em cada item.

O painel desta caixa descreve o primeiro item — ele é ímpar, então ganha o âmbar claro da solução. A missão confere duas coisas: que a classe existe uma vez e que o seletor gerado é :nth-child(odd). Note que a classe foi repetida nos quatro itens; parece redundante, mas é assim que o Tailwind funciona. O que se ganha é não inventar nome de classe e não manter uma regra em outro arquivo.

5. group: o estado do pai

O caso clássico: um cartão de produto onde a foto cresce, o título muda de cor e a sombra aumenta quando o mouse passa em qualquer lugar do cartão. Sem variante de grupo, você teria de repetir hover: em cada filho — e o efeito só aconteceria quando o mouse estivesse exatamente sobre aquele pedaço. A solução é marcar o pai com group e escrever group-hover: nos filhos.

<a href="#" class="group block rounded-xl bg-white p-4 hover:shadow-lg">
  <h3 class="text-amber-700 group-hover:text-amber-900">Pão do dia</h3>
  <p class="text-sm text-stone-600">Sai do forno às 6h30.</p>
</a>

A classe group sozinha não gera CSS nenhum: ela é uma etiqueta. O que gera CSS é o group-hover: nos filhos, e o seletor que o Tailwind escreve usa :is() e :where() em volta do nome. Duas consequências: primeiro, o group precisa ser ancestral de verdade — irmão não serve; segundo, a condição vale para qualquer descendente, inclusive netos. Se você tem dois grupos aninhados, o group-hover: do neto reage ao hover dos dois, o que costuma surpreender.

Por isso o Tailwind v4 permite batizar o grupo: group/cartao no pai e group-hover/cartao:text-amber-900 no filho. O trecho depois da barra é só um nome, e ele existe para desempatar grupos aninhados. É a mesma ideia do peer nomeado, que aparece na próxima seção. Fora isso, o comportamento é idêntico e o CSS gerado fica um pouco mais longo, com o nome dentro do :where().

Vale conhecer a família inteira, porque todos seguem a mesma gramática. group-focus: quando o pai recebe foco, group-focus-within: quando qualquer coisa dentro do pai foca, group-active: durante o clique, group-has-[:checked]: quando o pai tem um filho marcado. E há uma armadilha de acessibilidade: um efeito que só aparece no group-hover: fica invisível para quem usa teclado. Se a informação for importante, some group-focus-within: ao mesmo elemento, com o mesmo efeito.

6. peer: o estado do vizinho

peer resolve o problema oposto: quem muda de estado é um campo de formulário e quem reage é o texto ao lado. O exemplo mais útil é o aviso de erro. O campo recebe peer, o aviso recebe peer-invalid:block, e o aviso aparece sozinho quando o valor não passa na regra — sem uma linha de JavaScript.

<label class="block">
  <span class="text-sm font-medium">Telefone</span>
  <input type="tel" required class="peer mt-1 w-full rounded-md border p-2">
  <span class="hidden text-sm text-red-600 peer-invalid:block">Precisamos de um telefone.</span>
</label>

A condição do peer é o que mais confunde: ele só enxerga irmãos que vêm antes dele no HTML. O seletor gerado usa ~, o combinador de irmãos seguintes, e não existe combinador para trás. Se o aviso estiver acima do campo na marcação, nada acontece. A correção é mover o campo para cima do aviso (ou usar flex com order, mas a marcação é mais simples).

:is(:where(.group):hover .group-hover\:text-amber-700) {
  color: var(--color-amber-700);
}
:is(:where(.peer):checked ~ .peer-checked\:text-amber-700) {
  color: var(--color-amber-700);
}

Leia os dois seletores com calma, porque eles explicam por que grupo e par se comportam de jeitos diferentes. No primeiro, o estado é do ancestral e o alvo é o descendente: qualquer coisa dentro do .group serve. No segundo, o estado é do irmão anterior e o alvo é o que vem depois do ~. O :where() existe para não somar especificidade — detalhe que importa quando você mistura classes do Tailwind com CSS escrito à mão, assunto de Tailwind x CSS.

O peer aceita os mesmos estados do formulário: peer-checked:, peer-focus:, peer-disabled:, peer-placeholder-shown:, peer-invalid:. E aceita nomes: peer/email no campo e peer-invalid/email:block no aviso, para quando há vários campos no mesmo formulário. Sem o nome, todos os peer-* da página reagem a todos os peer, o que quase nunca é o que você quer num formulário de contato com cinco campos.

7. aria-, data-, has- e supports-

Nem todo estado vem do navegador. Muitos vêm do seu próprio HTML ou do JavaScript que abre um menu. Para esses casos o Tailwind tem variantes que leem atributos. A vantagem sobre criar uma classe nova é que o estado continua visível no HTML: quem lê a marcação vê data-aberto e entende o que está acontecendo — o mesmo não se pode dizer de classe-misteriosa-2.

Três observações que economizam tentativa e erro. O has- precisa dos colchetes mesmo quando o que vai dentro é uma pseudo-classe — has-[:checked], com dois-pontos dentro. O seletor que sai tem um espaço sobrando em :has( > img), o que é inofensivo mas explica por que às vezes a comparação de texto assusta. E supports- aceita a declaração inteira com dois-pontos: supports-[display:grid]: vira @supports (display:grid), sem espaço, exatamente como você escreveu.

Sobre aria-: o Tailwind considera que o atributo vale quando é "true". Se o seu componente escreve aria-expanded="false", a variante não pega — que é o desejado. Já as variantes data- com valor precisam da forma data-[chave=valor], e o valor é comparado como texto, com aspas no CSS gerado. Um data-state="aberto" no HTML e data-[state=aberto]: na classe combinam; um erro de acento ou de maiúscula não.

8. Combinar variantes e o que não funciona

Variantes se empilham da esquerda para a direita, e todas precisam ser verdadeiras ao mesmo tempo. md:hover:bg-amber-600 quer dizer "a partir de 768 px e com o mouse em cima". A ordem em que você escreve importa no sentido de aninhamento: o que está mais à esquerda é a condição de fora. Trocar a ordem de md: e hover: gera o mesmo efeito na prática, porque as duas são independentes; mas empilhar duas condições que dependem uma da outra, como dark:group-hover:, produz um seletor que só casa quando o tema e o hover valem juntos.

O CSS gerado para um caso composto mostra o aninhamento. Vale lembrar que o escape vale para cada dois-pontos, um por vez: md:hover:bg-amber-600 vira .md\:hover\:bg-amber-600:hover, dentro de uma consulta de largura. Se você digitar a classe com um espaço no lugar do dois-pontos, são duas classes diferentes e nenhuma delas existe.

A lista de conferência rápida, do que vale ao que nunca casa:

  • md:hover:bg-amber-600 — largura a partir de 768 px e mouse em cima: vale.
  • dark:focus:ring-2 — tema escuro e foco: vale, e o seletor gerado é :where(.dark, .dark *) mais :focus.
  • hover:focus:underline — hover e foco ao mesmo tempo: vale, mas os dois estados juntos são raros, então o efeito quase nunca aparece.
  • group-hover:peer-checked:block — pai com hover e irmão marcado: vale, e é um dos seletores mais difíceis de depurar que existem.
  • md:md:block — a mesma condição duas vezes: funciona, com regra duplicada no CSS.
  • hover :bg-amber-600 — espaço antes dos dois-pontos: são duas classes que não existem, e nada é gerado.
  • hover:bg-amber600 — nome de cor incompleto: nada é gerado, sem aviso nenhum.
  • disabled:opacity-50 num div — :disabled num elemento que não aceita o atributo: nunca casa.
  • peer-checked:block escrito acima do campo, no HTML — o ~ só olha para frente: nunca casa.
  • group-hover:text-amber-700 sem nenhum ancestral com group: nunca casa.

Sobre prioridade, o Tailwind não inventa camadas por estado: ele apenas gera regras na ordem em que aparecem no CSS compilado. Duas variantes que mexem na mesma propriedade e valem ao mesmo tempo — focus:bg-amber-100 hover:bg-amber-200 num botão com mouse em cima e foco — resolvem pelo que veio depois na folha, e não pelo que veio depois no HTML. A saída é não disputar: use uma variante por propriedade, ou aceite que o foco ganhe e escreva o hover pensando nisso.

Três coisas que as variantes não fazem, para você não perder tempo. Primeiro, elas não sobrevivem a nomes montados em JavaScript: hover:bg-amber-600 precisa estar escrito por inteiro em algum arquivo que o compilador leia. Segundo, elas não substituem o ! quando você precisa vencer uma regra mais forte — em v4 o importante vai no fim, bg-amber-100!, e o ! na frente é sintaxe antiga e não funciona. Terceiro, elas não atravessam o atributo style="": um style="color: red" vence qualquer hover:text-amber-700, porque estilo inline ganha de folha de estilo, sempre.

9. Resumo

Variante é condição: o prefixo antes dos dois-pontos diz quando a classe vale, e o Tailwind gera uma regra nova com o nome escapado (.hover\:bg-amber-600). No v4, hover: vem dentro de @media (hover: hover), então no toque ele não existe; para retorno no celular, use active:. Para foco, prefira focus-visible: no anel e focus: quando o campo precisa mudar sempre.

Os estados de formulário vêm prontos do navegador e economizam JavaScript: disabled:, checked:, required:, invalid:, user-invalid:, placeholder-shown:, read-only:. Use user-invalid: no aviso de erro e invalid: só quando quiser o vermelho desde o início. Lembre que disabled: depende de um elemento de formulário de verdade.

  • first:, last:, odd:, even: olham a posição entre os filhos; first-of-type: ignora os irmãos de outro tipo.
  • group-* reage ao pai marcado com group; peer-* reage ao irmão anterior marcado com peer.
  • O seletor do grupo é :is(:where(.group):hover …); o do par é :is(:where(.peer):checked ~ …). Ler o CSS gerado esclarece quase todo bug.
  • aria-*, data-*, has-* e supports-* leem o que o seu HTML ou o seu JavaScript escreve — e são a melhor alternativa a classes inventadas.
  • Variantes se empilham; a classe completa precisa existir no HTML compilado, senão nada é gerado.
  • ring é sombra, não borda; ! vai no fim da classe no v4.

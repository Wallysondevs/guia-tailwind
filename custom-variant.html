Custom Variants

A Ana tem doze botões no site e, em todos, o mesmo comportamento: o fundo muda quando o mouse passa e também quando o botão está com o foco do teclado. Como não existia um prefixo que dissesse “mouse ou teclado”, ela escreveu a condição à mão, em colchetes, doze vezes: [&:is(:hover,:focus)]:bg-amber-200. Funciona — e é ilegível. Um dia ela errou uma vírgula em um dos doze e passou vinte minutos procurando. Nesta aula ela aprende a dar nome a uma condição: escreve @custom-variant uma vez no CSS e passa a usar hocus: no HTML, como qualquer outro prefixo.

Você vai aprender
  • O que é uma variante e o que o prefixo dela faz com o seletor.
  • O papel do & dentro do @custom-variant.
  • Como juntar duas condições num nome só, com a vírgula.
  • Por que quase sempre vale escrever :where() em volta da condição.
  • O que é especificidade e como ela decide quem vence.
  • Como criar uma variante que é uma media query, e não um seletor.
  • Quando usar a variante própria, a arbitrária e a que já vem pronta.
  • O que conferir quando a variante nova não faz nada.

1. A cena: a condição escrita doze vezes

O botão de encomenda da Ana precisa reagir de dois jeitos: com o mouse em cima e com o foco do teclado. Ela já sabia que existem hover: e focus:, e que dá para empilhar prefixos. Mas empilhar significa “as duas coisas ao mesmo tempo”, e não é isso: o botão nunca está com mouse e teclado juntos. Então ela foi para a variante arbitrária, aquela em que você escreve o seletor entre colchetes:

<button class="[&:is(:hover,:focus)]:bg-amber-200 rounded-lg bg-amber-100 p-3">
  Encomendar
</button>

Funciona, e o CSS gerado está correto. O problema é de manutenção, não de mecanismo. Aquele prefixo tem colchetes, dois-pontos, parênteses e uma vírgula; para ler em voz alta, é um trava-língua. Em doze botões, ele aparece doze vezes, e cada cópia é uma chance de errar um caractere — o que aconteceu, como sempre acontece. E se amanhã ela quiser que o estado inclua também :active? São doze edições idênticas.

É para isso que existe @custom-variant: um lugar no CSS onde você registra um nome e diz qual condição ele representa. Depois disso, o nome vira prefixo como qualquer outro. Você troca dezoito caracteres ilegíveis por cinco legíveis, ganha um lugar único para mudar a regra e passa a ler o HTML sem parar para decifrar colchetes.

2. O que é uma variante, por dentro

Antes de escrever a primeira, vale desmontar a ideia. Uma variante é um envelope: ela não muda o que a classe faz, muda quando aquilo vale. Em hover:bg-amber-200, o pedaço bg-amber-200 continua sendo “fundo âmbar”; o hover: diz que a regra só se aplica em um estado do elemento.

O Tailwind escreve esse envelope como seletor de CSS. hover:bg-amber-200 vira .hover\:bg-amber-200:hover { … } — e aquele \: no meio do nome não é enfeite: é a barra invertida escapando os dois-pontos, porque dois-pontos não pode aparecer cru dentro de um nome de classe. Toda variante funciona assim: pega o seletor da classe e acrescenta uma condição.

O que o @custom-variant faz é dizer qual condição acrescentar. A forma é sempre a mesma: o nome da variante, um parênteses e a condição escrita em CSS. Dentro da condição, o caractere & é o elemento que tem a classe. Se você escreve (&:focus), está dizendo “o elemento com a classe, quando estiver em foco”. Se escreve (& > li), está dizendo “os filhos diretos desse elemento”.

variante
O prefixo antes dos dois-pontos que muda a condição de uma classe: hover:, md:, dark:. Ela não troca a utilidade, só quando ela vale.
@custom-variant
A linha do CSS de entrada que registra um nome de variante e a condição dele. Uma vez registrado, o nome vale em qualquer HTML do projeto.
&
Dentro da condição, representa o elemento que carrega a classe. É o mesmo & do CSS aninhado, e é o que permite escrever &:hover ou & > li.
:where()
Um invólucro que aplica a condição com especificidade zero. Serve para a sua variante não roubar a disputa de quem deve vencer no CSS.
especificidade
O peso de um seletor na hora de decidir qual regra vale quando duas mexem na mesma propriedade. Quanto mais “específico”, mais forte.
variante arbitrária
A condição escrita na hora, entre colchetes, direto na classe: [&:hover]:bg-amber-200. Serve para o caso isolado; não tem nome nem lugar único.

Repare que a variante não é um atalho de digitação: é uma peça do projeto. Ela mora no CSS de entrada, junto do tema, e vale para todas as páginas. Quando você muda a condição ali, todos os usos acompanham — é essa a diferença que justifica o nome.

3. O primeiro nome: hocus

Hora de escrever. O nome escolhido é hocus, uma brincadeira antiga de quem faz componente: hover mais focus, as duas condições que, para quem usa o teclado, devem ser a mesma coisa. A linha é esta:

@custom-variant hocus (&:hover, &:focus);

A vírgula dentro dos parênteses separa as duas condições: o Tailwind gera uma regra para cada uma, com o mesmo corpo. O HTML fica curto e honesto: hocus:bg-amber-200. E o CSS gerado mostra o envelope em ação.

Na caixa abaixo, o botão existe e a variante ainda não. Sua missão é registrar hocus e usar o prefixo no botão. O painel desta caixa mostra as regras geradas, e não o CSS computado, porque o que interessa aqui é justamente o seletor.

Escreva @custom-variant hocus (&:hover, &:focus); no bloco <style> e acrescente hocus:bg-amber-200 ao botão. O painel deve mostrar a regra com as duas condições.

<style type="text/tailwindcss">
/* nenhuma variante própria ainda */
</style>

<button id="alvo" class="rounded-lg bg-amber-100 p-3 text-amber-900">
  Encomendar pão
</button>
.rounded-lg {
  border-radius: var(--radius-lg);
}
.bg-amber-100 {
  background-color: var(--color-amber-100);
}
.p-3 {
  padding: calc(var(--spacing) * 3);
}
.text-amber-900 {
  color: var(--color-amber-900);
}

<style type="text/tailwindcss">
@custom-variant hocus (&:hover, &:focus);
</style>

<button id="alvo" class="rounded-lg bg-amber-100 p-3 text-amber-900 hocus:bg-amber-200">
  Encomendar pão
</button>

Depois de rodar, o painel mostra uma regra só, com dois seletores separados por vírgula. Repare na barra invertida antes dos dois-pontos do nome da classe: ela está ali para o navegador não achar que hocus termina naquele ponto. Repare também que não existe nada parecido com .hocus { } — a variante não cria regra própria; ela só muda o envelope das classes que a usam.

Uma consequência prática que vale dizer em voz alta: variante sem uso não gera CSS. Se você registrar hocus e não escrever hocus: em lugar nenhum, o arquivo final não muda um byte. É o mesmo comportamento das utilidades — o Tailwind só escreve o que encontra escrito no HTML. E é por isso que a variante nova “não faz nada” quando você esquece de usá-la: ela existe no CSS de entrada, mas ninguém pediu.

4. Duas condições, um nome

A vírgula é o único detalhe de sintaxe que costuma morder. Ela não significa “e sim”; significa “ou”: as duas condições produzem a mesma declaração, e o navegador aplica a que casar. Se você quisesse “mouse e teclado ao mesmo tempo”, escreveria sem vírgula, (&:hover:focus) — que quase nunca é o que se quer, porque ninguém usa os dois juntos.

Esse é o motivo de hocus ser tão comum em bibliotecas de componente: é a condição dupla que deixa o botão bonito para quem usa mouse e visível para quem usa teclado, sem duplicar classes. E é também o caso em que a variante arbitrária fica feia: [&:is(:hover,:focus)] é a mesma ideia, escrita de um jeito que ninguém lê em voz alta sem parar.

Com a variante registrada, o CSS gerado sai assim, e vale olhar com calma porque ele explica o resto da aula:

.hocus\:bg-amber-200:hover,
.hocus\:bg-amber-200:focus {
  background-color: var(--color-amber-200);
}

Duas coisas para levar. Primeira: o corpo é o mesmo das outras classes — a cor continua vindo de uma variável do tema, e nada foi duplicado à mão. Segunda: a condição foi acrescentada ao seletor da classe, não trocada. Isso significa que a variante pode ser empilhada com outras, e dark:hocus:bg-amber-200 funciona como você espera: no tema escuro e com mouse ou foco. A ordem dos prefixos nesse caso é livre, mas escrever sempre na mesma ordem — tema, tamanho de tela, estado — deixa o HTML previsível.

5. Especificidade: por que :where() aparece tanto

Agora a parte que separa quem só copia a receita de quem entende. Toda regra de CSS tem um peso, e quando duas regras mexem na mesma propriedade do mesmo elemento, vence a de peso maior — não a última que você escreveu. Seletor de id pesa mais que classe, classe pesa mais que tag, e assim por diante.

Uma variante que acrescenta :hover ao seletor deixa a regra mais pesada que a classe simples. Isso costuma ser bom, mas cria um problema sutil: a sua variante pode passar a ganhar de coisas que deveriam vencê-la, e você fica sem ferramenta para sobrescrever, a não ser com !important — que é o sinal de que o desenho das camadas está errado.

O :where() resolve isso embrulhando a condição numa camada de peso zero. A condição continua valendo, mas não soma força ao seletor. Por isso a receita que você vai ver em todo lugar é &:where([data-destaque]) em vez de &[data-destaque]: as duas funcionam, e a primeira deixa o CSS fácil de sobrescrever depois.

Na caixa abaixo, o preço está marcado com o atributo data-destaque — um jeito de o JavaScript dizer “este item está em promoção” sem trocar classe. A variante destaque: precisa existir para o prefixo funcionar. Sua missão é escrever a linha, com :where().

Registre a variante destaque com a condição &:where([data-destaque]). O preço marcado deve ganhar fundo âmbar claro.

<style type="text/tailwindcss">
/* a variante destaque ainda não existe */
</style>

<p id="alvo" class="p-2 text-amber-900 destaque:bg-amber-100" data-destaque>
  Pão de queijo, R$ 6
</p>
padding: 8px
color: oklch(0.414 0.112 45.904)

<style type="text/tailwindcss">
@custom-variant destaque (&:where([data-destaque]));
</style>

<p id="alvo" class="p-2 text-amber-900 destaque:bg-amber-100" data-destaque>
  Pão de queijo, R$ 6
</p>

Antes de rodar, o painel mostra o respiro e a cor do texto, e nenhum fundo: a classe destaque:bg-amber-100 está no HTML, mas o prefixo não existe no CSS, então não há regra para ela. Depois de registrar a variante, o fundo aparece. É o mesmo silêncio de sempre — classe sem CSS não avisa nada.

O CSS gerado para essa variante tem a condição depois do nome da classe, e o :where() aparece literalmente no seletor — não é uma convenção de leitura, é CSS de verdade:

.destaque\:bg-amber-100:where([data-destaque]) {
  background-color: var(--color-amber-100);
}

Se você tirar o :where() e escrever &[data-destaque], o seletor vira .destaque\:bg-amber-100[data-destaque] e o fundo aparece igual. A diferença só se revela no dia em que outra regra disputa a mesma propriedade: aí a versão com atributo “cru” ganha por ter mais peso, e você fica sem argumento para sobrescrever.

Vale conhecer o atalho que dispensa variante própria neste caso específico: para atributos data-* simples, o Tailwind já aceita o nome do atributo como prefixo. data-destaque no HTML combina com data-destaque:bg-amber-100 na classe, sem @custom-variant nenhum. A variante própria vale quando a condição é composta — atributo mais estado, dois atributos, filho de algo — ou quando você quer um nome curto e estável que não dependa do nome do atributo.

6. Variante que não é seletor: a media query

Até aqui as condições foram seletores: estados do elemento, atributos, posição na árvore. Mas uma variante também pode ser uma media query — e aí ela pergunta algo sobre o ambiente, não sobre o elemento. É o mesmo mecanismo dos breakpoints, com um nome escolhido por você.

Dois exemplos que aparecem em projeto de verdade. O primeiro, acessibilidade: quem marcou no sistema “reduzir movimento” não quer animação. O segundo, impressão: a página precisa de outro respiro no papel. Os dois se escrevem assim, sem nenhum seletor:

@custom-variant sem-movimento (@media (prefers-reduced-motion: reduce));
@custom-variant papel (@media print);

Na caixa abaixo, a condição é a largura da janela, porque é a única que dá para testar na prévia. A variante apertado está registrada com um limite pequeno demais, e por isso o fundo não aparece na janela de 375 px. Sua missão é corrigir o número.

A prévia tem 375 px. Mude o limite de 20rem para 30rem e rode: em telas apertadas o cartão deve ganhar fundo âmbar claro.

<style type="text/tailwindcss">
@custom-variant apertado (@media (width < 20rem));
</style>

<div id="alvo" class="border border-amber-300 p-4 apertado:bg-amber-100">
  <p class="font-semibold">Encomendas</p>
  <p class="text-sm">Retire no balcão até as 18h.</p>
</div>
padding: 16px
border-width: 1px
border-color: oklch(0.879 0.169 91.605)

<style type="text/tailwindcss">
@custom-variant apertado (@media (width < 30rem));
</style>

<div id="alvo" class="border border-amber-300 p-4 apertado:bg-amber-100">
  <p class="font-semibold">Encomendas</p>
  <p class="text-sm">Retire no balcão até as 18h.</p>
</div>

O CSS gerado é uma media query comum embrulhando a classe, exatamente como o Tailwind faz com sm: e companhia. A diferença é que o número e o nome são seus, e que o nome não vem de uma variável --breakpoint-*: ele mora no @custom-variant. Por isso, essa variante não ganha um par max-apertado automático; se você quiser os dois lados, escreva as duas linhas.

Se a condição que você quer já existe como breakpoint, use o breakpoint. Criar uma variante de largura quando balc: faria o mesmo serviço é sinal de que o projeto está com duas réguas de tamanho — e duas réguas é sempre uma a mais do que se consegue lembrar.

7. Pronta, arbitrária ou própria?

Toda condição que você imaginar cabe em uma destas três caixas, e escolher a caixa certa é a decisão do dia a dia.

A pronta é a primeira tentativa: hover, focus, disabled, data-*, os breakpoints, dark. O Tailwind traz dezenas, e a documentação lista todas. Use antes de inventar.

A arbitrária é a segunda: a condição escrita na hora, entre colchetes. Ótima para o caso isolado — um seletor de filho numa tabela, um [&:nth-child(3)] para acertar uma borda. Ruim quando repete, porque não tem nome, não tem lugar único e não tem como mudar em bloco.

A própria é a terceira: um nome no @custom-variant. Vale quando a condição aparece em três lugares ou mais, quando o nome dela é uma palavra que o time já usa, ou quando você quer poder mudar a condição sem tocar no HTML.

SituaçãoO que usarPor quê
mouse e teclado no mesmo botão@custom-variant hocus (&:hover, &:focus)a condição se repete e ganha nome curto

terceiro filho de uma lista[&:nth-child(3)]:border-tcaso isolado, não vale nome

tema escuro por classe@custom-variant dark (&:where(.dark, .dark *))a receita oficial, já pronta no projeto

Duas armadilhas de nomenclatura. Não batize uma variante com o nome de uma que já existe: @custom-variant hover (…) não “melhora” o hover:, ela o substitui, e o resto do site passa a obedecer à sua condição. E não use o nome de uma utilidade, como flex ou grid: o prefixo e a classe ficam iguais na leitura e ninguém entende o HTML depois.

8. Quando a variante nova não faz nada

O sintoma é sempre o mesmo: você escreveu minha-variante:bg-amber-100, salvou, e o fundo não apareceu. Não há mensagem de erro. A lista de conferência é curta e resolve quase todos os casos.

  • O @custom-variant está no arquivo compilado? Ele precisa estar no CSS de entrada, junto do @import "tailwindcss";. Num projeto com build, um arquivo CSS solto não é lido por ninguém.
  • O nome está igual? hocus e Hocus são coisas diferentes, e variante com hífen (sem-movimento) só combina com o prefixo escrito do mesmo jeito.
  • Falta o &? A condição precisa dizer onde ela se encaixa: sem o &, o que você escreveu vira um seletor de descendente, e a regra passa a procurar aquele atributo num filho. O elemento com a classe não é pintado.
  • Falta a condição real? No caso do atributo, o HTML precisa ter data-destaque de verdade. Variante que pergunta algo que ninguém responde nunca casa.
  • O CSS foi recompilado? No modo com npm, o processo de build tem de estar rodando; se ele parou, o CSS fica velho e a variante nova não chega no navegador.

Há ainda o caso do “não faz nada porque outra regra venceu”. Aí o painel do navegador resolve: na aba Styles, a declaração riscada mostra quem ganhou. Se o vencedor é uma variante sua sem :where(), você já sabe o conserto.

9. Cenários do dia a dia

Cenário 1: a variante que nasceu grande demais

A Ana criou @custom-variant promo (&:where([data-promo], .promo)) e passou a usar promo: em tudo: preço, selo, botão e até no rodapé. Seis meses depois, queria mudar só o comportamento do preço e descobriu que a condição era uma só para o site inteiro. O conserto foi criar uma segunda variante, mais específica, e migrar o preço. Variante é contrato: nasce pequena, e cresce quando a repetição justifica.

Cenário 2: o botão que só funcionava com mouse

Ela usou hover:bg-amber-200 no botão de encomenda e testou no mouse: perfeito. No teclado, o foco aparecia na borda e o fundo não mudava, então o botão parecia desligado. Trocar para hocus: resolveu os dois casos com uma classe. O detalhe que fica: quem navega por teclado depende de focus, e quem usa leitor de tela depende de focus-visible; a variante própria é o lugar onde o time decide o que vale para os dois.

Cenário 3: duas variantes com o mesmo peso

Num cartão, ela tinha destaque:border-amber-500 e hover:border-amber-700. No mouse, a borda não mudava: as duas regras tinham o mesmo peso, e vencia a que o Tailwind escreveu por último. A solução foi de desenho, não de força: a variante própria ganhou :where() e passou a ser mais fraca que o hover:, que é o estado mais urgente. Sem :where(), o conserto seria !important — e aí o próximo caso seria pior.

Dica: são o :where(, o seletor de atributo entre colchetes e o fechamento. Sem o :where, a regra funciona igual, mas fica mais forte do que devia.

11. Resumo

Variante é envelope: ela não troca o que a classe faz, troca quando vale. @custom-variant registra um nome para uma condição escrita em CSS, e o & dentro dela é o elemento que carrega a classe. Uma vírgula junta duas condições no mesmo nome — é assim que nasce hocus: — e o CSS gerado mostra o seletor com a condição acrescentada, sem criar regra própria.

A condição pode ser um seletor ou uma media query, e quase sempre vale embrulhá-la em :where() para ela não somar especificidade. Use a variante pronta quando existir, a arbitrária para o caso isolado e a própria quando a condição se repete ou merece um nome. E lembre que variante sem uso não gera CSS: se o prefixo novo não faz nada, comece conferindo se o @custom-variant está no arquivo compilado e se o nome está escrito igual.

Para lembrar

  • Variante muda o quando, não o que: o corpo da regra continua igual.
  • @custom-variant nome (condição); registra o prefixo nome:.
  • & é o elemento que tem a classe; & > li são os filhos diretos.
  • Vírgula = “ou”; &:hover, &:focus gera duas regras com o mesmo corpo.
  • :where() zera a especificidade e evita briga com quem deveria vencer.
  • A condição pode ser media query: (@media (prefers-reduced-motion: reduce)).
  • Atributo data-* simples já tem prefixo pronto, sem variante própria.
  • Não reuse nome de variante existente nem de utilidade no batismo.
  • Variante registrada e não usada não aparece no CSS final.
  • Prefixo que não faz nada: arquivo não compilado, nome diferente ou falta de &.

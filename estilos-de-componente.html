Estilos de Componente

A Ana tem um botão que ela considera perfeito. Levou uma tarde para acertar o âmbar, o respiro e o arredondamento, e agora cola aquele botão em três páginas do site da padaria. Enquanto nada muda, tudo bem. Mas chega o dia em que o âmbar precisa ficar um tom mais escuro — e a Ana descobre que tem o mesmo botão escrito em três arquivos, com três cópias da mesma lista de classes. Nesta aula ela faz o que gente experiente faz nesse momento: dá um nome ao botão e escreve o estilo uma vez só, usando @apply dentro de um componente. É o primeiro passo para o HTML parar de repetir o que já foi decidido.

Você vai aprender
  • O que é um componente neste guia (e por que não tem nada a ver com JavaScript).
  • Onde a sua classe mora: no <style type="text/tailwindcss"> da página ou no arquivo de entrada do projeto.
  • Como o @apply copia as declarações de uma utilitária para dentro da sua classe.
  • Por que a classe precisa ficar dentro de @layer components.
  • Como colocar :hover e :focus-visible no componente.
  • O critério dos três usos: quando vale criar a classe e quando é desperdício.
  • A diferença entre @layer components e @utility.

1. A cena: o botão que mora em três páginas

O site da Ana tem três páginas: a vitrine, a lista de pães e a página de encomendas. Em todas elas existe um botão amarelo com o texto “Comprar”. O HTML de cada um é este aqui, copiado e colado com carinho:

<button class="rounded-lg bg-amber-500 px-4 py-2 font-semibold text-amber-950">Comprar</button>

Cinco classes, todas úteis, nenhuma errada. O problema não é a qualidade do botão — é a quantidade de lugares onde a mesma decisão está escrita. Quando o âmbar precisa mudar, a Ana abre três arquivos, procura a linha, troca bg-amber-500 por bg-amber-600 e reza para não ter esquecido nenhum. Semana passada ela esqueceu: a página de encomendas ficou com o botão antigo por quatro dias, e ninguém percebeu, porque ninguém abre as três páginas lado a lado.

Existe uma saída que não é “voltar ao CSS antigo” e não é “aceitar a repetição”. A saída é transformar esse conjunto de classes em uma peça com nome: uma classe de componente. O HTML fica assim:

<button class="botao">Comprar</button>

E o desenho do botão passa a viver em um lugar só. Se amanhã o âmbar mudar, muda ali — e as três páginas acompanham. O que você vai aprender nesta aula é justamente escrever esse “um lugar”, com as ferramentas do Tailwind, sem perder as vantagens das utilitárias.

2. O que é um componente (e o que não é)

Antes de escrever código, vale desmontar uma confusão. Em muitos lugares, “componente” quer dizer uma peça de programa — um arquivo JavaScript que desenha um pedaço da tela. Aqui não. Neste guia, componente é só isto: um conjunto de estilos que se repete e que ganha um nome. Pode ser um botão, um cartão, um selo de “novo”, um preço. A pergunta que define se algo é componente não é “que tecnologia usa?”, é “aparece mais de uma vez?”.

No Tailwind existem três jeitos de desenhar a mesma peça, e a escolha entre eles é o coração desta aula:

  • Utilitárias no HTML. É o que a Ana fez. Cada elemento carrega a lista completa de classes. Vantagem: nada para nomear, nada para sincronizar, e o HTML mostra exatamente o que acontece. Desvantagem: a mesma lista se repete, e mudar o desenho é editar em vários lugares.
  • Classe de componente com @apply. Você escreve .botao { @apply … } uma vez e usa class="botao" em todo lugar. Vantagem: um lugar só para mudar. Desvantagem: você precisou inventar um nome, e nomes mentem — daqui a três meses ninguém lembra o que .cartao2 faz.
  • Utilitária própria com @utility. Um degrau além: você cria uma utilitária nova, que aceita variantes (md:selo, hover:selo). Serve para o valor que falta no catálogo, não para juntar cinco utilitárias existentes.

Não existe resposta certa universal. Existe um critério econômico, que a gente vai usar até o fim do guia: se a peça aparece uma vez, escreva utilitárias; se aparece três vezes ou mais, dê um nome. Uma vez só, a classe é trabalho sem retorno. Três vezes, cada mudança futura custa três edições e uma chance de esquecimento.

Se você escrever class="botao md:botao", o md:botao não gera nada — o Tailwind não sabe o que é uma variante de uma classe que não é utilitária. Isso vai voltar na seção 8.

3. Onde a classe mora: o <style type="text/tailwindcss">

Nos exemplos deste guia, a classe de componente mora dentro da própria página, em um bloco <style> com um tipo especial:

<style type="text/tailwindcss">
@layer components {
  .botao {
    @apply rounded-lg bg-amber-500 px-4 py-2;
  }
}
</style>

O atributo type="text/tailwindcss" é a chave. Sem ele, o navegador trata o bloco como CSS comum — e CSS comum não conhece @apply. O resultado é silencioso e cruel: a regra aparece na tela do editor, o navegador joga a linha do @apply fora e o botão fica sem estilo nenhum. Se algum dia uma classe sua “não fizer nada”, confira esse atributo antes de qualquer outra coisa.

Num projeto de verdade, instalado com npm e com o processo de build rodando, não existe esse bloco na página. A classe mora no arquivo CSS de entrada, o mesmo que importa o Tailwind:

@import "tailwindcss";

@layer components {
  .botao {
    @apply rounded-lg bg-amber-500 px-4 py-2;
  }
}

A sintaxe é a mesma; muda o endereço. Na página do guia o bloco é compilado pelo motor que roda no navegador; no projeto, pelo processo de build. As duas rotas existem para você poder praticar aqui e depois repetir em casa sem susto. E, se ficar na dúvida sobre como o build funciona, a aula Instalando com npm mostra a instalação, e O CSS de Entrada explica esse arquivo linha por linha.

seletor de classe
O .botao com ponto na frente. É o nome que você inventou; vale para todo elemento com class="botao".
@apply
Uma ordem para o Tailwind: “pegue as declarações destas utilitárias e copie para dentro desta regra”. Não é herança, não é vínculo; é cópia.
@layer components
A camada onde os estilos de conjunto devem morar. Ela fica antes de utilities na ordem do CSS, então uma utilitária escrita no HTML ainda ganha da sua classe.
@utility
A diretiva que cria uma utilitária nova, com nome e tudo, e que aceita variantes. Diferente da classe de componente, ela entra na camada das utilitárias.
variante
O prefixo que muda quando a classe vale: hover:, md:, dark:, print:. Cada uma delas é uma condição, não uma classe nova.

4. A primeira classe de componente

Hora de escrever. A missão é pequena de propósito: o botão da Ana já está no bloco, mas sem arredondamento — e o arredondamento é justamente o que a deixa insatisfeita. Em vez de copiar a classe para cada botão, ela vai acrescentar rounded-lg na lista do @apply, uma vez, e ver o efeito nos dois botões da prévia.

O componente .botao já está definido, mas sem cantos arredondados. Acrescente rounded-lg à lista do @apply e clique em Rodar: os dois botões (o #alvo e o segundo, com a mesma classe) precisam ficar com cantos de 8 px.

<style type="text/tailwindcss">
@layer components {
  .botao { @apply bg-amber-500 px-4 py-2 font-semibold text-amber-950; }
}
</style>

<button class="botao">Ver a cesta</button>
background-color: oklch(0.769 0.188 70.08)
color: oklch(0.279 0.077 45.635)
font-weight: 600

padding-block: 8px

<style type="text/tailwindcss">
@layer components {
  .botao { @apply rounded-lg bg-amber-500 px-4 py-2 font-semibold text-amber-950; }
}
</style>

<button class="botao">Ver a cesta</button>

Leia o painel depois de rodar: border-radius: 8px. Você não escreveu 8 px em lugar nenhum, escreveu rounded-lg; o Tailwind traduziu. E a segunda linha do painel é a resposta que interessa: o painel descreve só o #alvo, mas o segundo botão tem a mesma classe, então tem o mesmo raio. Uma edição, dois elementos. Numa página com doze botões, uma edição, doze elementos.

Repare também no que não mudou. As classes no HTML continuam sendo só botao. O rounded-lg não apareceu no HTML: ele foi morar dentro da regra, junto com as outras quatro utilitárias. É esse o trato do componente — o HTML fica curto e a decisão fica centralizada. O preço é que, para saber o que o botão tem, agora você precisa olhar dois lugares: o HTML (que diz “é um botao”) e o CSS (que diz como um botao é).

Se você digitar rounded-lg com dois “l” ou esquecer o hífen, o painel continua em branco do lado do raio, e a segunda linha da meta falha. O Tailwind não avisa quando uma classe não existe dentro do @apply... na verdade avisa no build, com um erro de “utilitária desconhecida”. No navegador, o efeito prático é o botão sair sem cantos — e o painel vazio é a sua pista.

5. O que o @apply faz por baixo

Vale desmistificar o @apply, porque ele é o suspeito de muitos mal-entendidos. Ele não cria um atalho, não importa as utilitárias e não deixa nada “vivo”. Ele copia as declarações para dentro da sua regra e pronto. O CSS que sai daquele componente é este:

.botao {
  border-radius: var(--radius-lg);
  background-color: var(--color-amber-500);
  padding-inline: calc(var(--spacing) * 4);
  padding-block: calc(var(--spacing) * 2);
  --tw-font-weight: var(--font-weight-semibold);
  font-weight: var(--font-weight-semibold);
}

É o mesmo CSS que as cinco utilitárias produziriam no HTML, só que com um seletor diferente. Duas consequências práticas saem daí. A primeira: o arquivo não fica menor por causa do componente; o que diminui é o HTML, que troca cinco nomes por um. A segunda: como é cópia, a sua classe é estática. Ela não reage a nada que o Tailwind não tenha colocado ali dentro na hora de escrever.

Agora a parte que mais importa no dia a dia: por que dentro de @layer components? A resposta é ordem. O Tailwind organiza o CSS em camadas e a camada das utilitárias vem depois da camada dos componentes. Quem vem depois ganha quando o peso do seletor é o mesmo. Resultado prático: se num botão específico você precisar de outra cor, basta escrever a utilitária no HTML:

<button class="botao bg-red-600">Cancelar encomenda</button>

O bg-red-600 vence o âmbar que está dentro do componente, e o botão sai vermelho sem que você crie um segundo componente nem mexa no primeiro. Se a mesma regra estivesse fora de camada, o contrário aconteceria: o componente venceria a utilitária e não haveria jeito de ajustar um caso sem !important. É por isso que a camada não é enfeite — é o que mantém a sua classe “sobrescrevível”. Esse mesmo mecanismo, visto do lado do problema, aparece na aula Depurar o CSS.

6. Estados dentro do componente

Um botão não é só a aparência parada: ele muda quando o mouse passa, quando recebe foco pelo teclado, quando está desabilitado. Num componente, esses estados entram como seletor de CSS — :hover, :focus-visible, :disabled — colados no nome da classe:

O botão resolve o estado parado, mas no mouse não escurece. Crie uma regra .botao:hover logo abaixo da existente, com @apply bg-amber-600, para o âmbar ficar um degrau mais escuro quando o mouse passa.

<style type="text/tailwindcss">
@layer components {
  .botao { @apply rounded-lg bg-amber-500 px-4 py-2 font-semibold text-amber-950; }
}
</style>
<button id="alvo" class="botao">Comprar pão</button>
background-color: oklch(0.769 0.188 70.08)
color: oklch(0.279 0.077 45.635)
font-weight: 600
border-radius: 8px
padding-inline: 16px
padding-block: 8px

<style type="text/tailwindcss">
@layer components {
  .botao { @apply rounded-lg bg-amber-500 px-4 py-2 font-semibold text-amber-950; }
  .botao:hover { @apply bg-amber-600; }
}
</style>
<button id="alvo" class="botao">Comprar pão</button>

O painel aqui não mostra valor computado, porque a prévia não está com o mouse em cima. Ele mostra as regras geradas, e é ali que se vê a linha background-color: var(--color-amber-600). Isso não é um detalhe do guia: é assim que você confere estado no navegador de verdade também. No DevTools, o painel Styles tem um botão de forçar estado (:hov no Chrome) que finge o mouse em cima e deixa você ver a regra vencendo.

Os estados que aparecem em quase todo botão são quatro, e cada um tem um seletor próprio. Vale conhecer a lista, porque escrever o seletor errado é o motivo mais comum de “o efeito não pega”:

Quando valeSeletorO que costuma entrar no @apply
mouse em cima:hoverbg-amber-600, shadow-md
foco pelo teclado:focus-visibleoutline-2, outline-offset-2
apertando o botão:activetranslate-y-px, bg-amber-700
campo desligado:disabledbg-neutral-200, text-neutral-500, cursor-not-allowed

Existe um segundo jeito de escrever o mesmo estado, e ele confunde muita gente: a variante hover: dentro do próprio @apply. Também funciona:

.botao {
  @apply rounded-lg bg-amber-500 px-4 py-2;
  @apply hover:bg-amber-600;
}

O resultado no CSS é uma regra aninhada, com a mesma condição que a variante usaria — inclusive o @media (hover: hover) que o Tailwind coloca para não disparar “hover” em tela de toque. Escolha um estilo e mantenha: nesta aula usei .botao:hover, que é mais fácil de ler em voz alta e funciona em qualquer versão. O que não vale é misturar os dois na mesma classe, porque aí duas regras dizem a mesma coisa e você vai passar meia hora perguntando qual está ganhando.

Para o foco de teclado, o padrão é :focus-visible — que só aparece quando a pessoa navega por Tab, e não a cada clique. Um componente bem-feito tem os dois estados:

.botao { @apply rounded-lg bg-amber-500 px-4 py-2 font-semibold text-amber-950; }
.botao:hover { @apply bg-amber-600; }
.botao:focus-visible { @apply outline-2 outline-offset-2 outline-amber-700; }

Repare que os três seletores compartilham a mesma ideia: a base, o mouse, o teclado. Se amanhã o botão virar quadrado, você troca rounded-lg em uma linha e os estados continuam coerentes. Esse é o ganho real do componente: não é digitar menos, é ter um lugar onde a decisão está escrita.

7. O critério: só entra no componente o que se repete

A tentação, depois de aprender @apply, é transformar tudo em classe. Não faça isso. A classe de componente cobra um preço: ela esconde o desenho, e quem lê o HTML passa a precisar de dois arquivos para entender uma tela. Só pague esse preço quando houver repetição de verdade.

Vamos ver o caso em que vale. A Ana tem uma lista de pães, e cada item é um cartão com o mesmo desenho: cantos arredondados, fundo branco, 16 px de respiro. Três cartões, três cópias. A missão é dar um nome a esse conjunto e usá-lo nos três:

Os três cartões repetem as mesmas classes. O componente .cartao já existe no bloco de estilo; use a classe cartao nos três div no lugar das utilitárias. A meta confere que existem 3 elementos com essa classe e que o respiro é de 16 px.

<style type="text/tailwindcss">
@layer components {
  .cartao { @apply rounded-xl bg-white p-4; }
}
</style>
<div id="alvo" class="p-2">Pão francês</div>
<div class="p-2">Pão de queijo</div>
<div class="p-2">Bolo de fubá</div>
padding: 8px

<style type="text/tailwindcss">
@layer components {
  .cartao { @apply rounded-xl bg-white p-4; }
}
</style>
<div id="alvo" class="cartao">Pão francês</div>
<div class="cartao">Pão de queijo</div>
<div class="cartao">Bolo de fubá</div>

Só que existe uma armadilha nesse exemplo, e ela aparece toda semana em projeto de verdade: o cartão do “Bolo de fubá” tem um selo de “últimas unidades” e o do “Pão de queijo” tem preço em destaque. Se você enfiar essas diferenças dentro de .cartao, todo cartão passa a ter selo. A regra é simples: o componente guarda o que é igual; o que é diferente fica no HTML, como utilitária.

<div class="cartao">Bolo de fubá</div>
<div class="cartao mt-4 border-2 border-amber-400">Bolo de fubá</div>

Acrescentar uma utilitária a um elemento que já tem a classe do componente é o gesto mais comum do Tailwind, e funciona justamente porque a camada das utilitárias vem depois. Você não “quebra” o componente; você o ajusta naquele caso. E se o ajuste aparece em cinco lugares, aí sim ele vira parte do componente.

O critério fica assim, em três perguntas: a peça aparece três vezes ou mais? As três cópias deveriam mudar juntas quando o desenho mudar? O nome que eu vou inventar diz algo que a próxima pessoa entende? Se a resposta for “sim, sim, sim”, crie o componente. Se alguma for “não”, fique com as utilitárias e economize um nome.

8. O @utility: quando a peça precisa aceitar variante

Falta uma peça no quebra-cabeça. A classe de componente não aceita variante: md:botao não gera CSS nenhum. Isso é limitação ou recurso? Depende do que você quer. Se a peça tem um comportamento diferente por tamanho de tela, você quer uma utilitária — e para criar uma utilitária própria existe o @utility:

@utility selo {
  @apply rounded-full bg-amber-100 px-2 text-xs font-semibold text-amber-900;
}

Com isso, selo funciona como qualquer utilitária do catálogo, inclusive com prefixo. O CSS gerado quando você usa class="md:selo" mostra o Tailwind repetindo o bloco dentro da condição de largura:

@media (width >= 48rem) {
  .md\:selo {
    border-radius: calc(infinity * 1px);
    background-color: var(--color-amber-100);
    padding-inline: calc(var(--spacing) * 2);
    font-size: var(--text-xs);
    line-height: var(--tw-leading, var(--text-xs--line-height));
  }
}

Três detalhes para não se perder. Primeiro: o nome que vem depois de @utility é um nome novo, e não pode repetir uma utilitária que já existe — flex não é um bom candidato. Segundo: o que você põe dentro é CSS de verdade: @apply, declarações soltas, variáveis, o que precisar. Terceiro: a diferença prática entre os dois é a variante. Componente é para o bloco que aparece igual em todo lugar; utilitária própria é para o valor que se combina com hover:, md:, dark:.

Existe uma variação mais avançada, a utilitária funcional, em que o nome termina em -* e o valor sai de dentro da classe — @utility tab-* faria tab-4 valer quatro espaços de tabulação. É recurso para quem está criando um sistema próprio de valores; para o dia a dia da padaria, um nome fixo resolve tudo.

Na dúvida entre os dois, escolha o caminho mais chato: utilitárias no HTML. Componente é remédio para repetição, não vitamina. Um projeto com trinta classes de componente costuma ter o mesmo problema do CSS antigo, só que com nomes em inglês.

9. Cenários do dia a dia

Cenário 1: o componente que virou um monstro

Seis meses depois, .botao tem dezoito utilitárias dentro do @apply: quatro tamanhos de fonte, três cores de texto, um md: que não funciona, dois !important. Ninguém mexe com medo. O sinal de que o componente passou do ponto é justamente esse: quando ninguém sabe o que ele faz sem abrir o arquivo e ler dezoito linhas. O conserto é dividir: um .botao com o que todo botão tem (raio, respiro, peso da fonte) e as variações no HTML, como utilitárias — class="botao bg-red-600". Componente bom tem cinco, no máximo oito utilitárias dentro.

Cenário 2: .cartao e .cartao-destaque, quase iguais

A Ana criou .cartao e depois .cartao-destaque, que é igual, mas com borda âmbar. Funciona, até a terceira variação (.cartao-destaque-grande) e a quarta. Aí ela tem quatro blocos com 90% do conteúdo repetido — a mesma dor do começo, disfarçada de organização. A alternativa é uma classe só e a diferença no HTML: <div class="cartao border-2 border-amber-400">. Antes de criar a segunda classe, pergunte se a diferença não cabe em uma ou duas utilitárias.

Cenário 3: “mudei o @apply e nada aconteceu”

Três causas, em ordem de frequência. (1) O bloco de estilo está sem type="text/tailwindcss", então o navegador descartou o @apply e a regra inteira ficou pela metade. (2) Você escreveu uma utilitária que não existe, e o build reclamou de “utilitária desconhecida” — no navegador, o efeito é a classe sair sem aquela declaração. (3) A regra está fora de camada e algum CSS antigo da página venceu. Nas três, o caminho de diagnóstico é o mesmo: olhar o CSS gerado e procurar o nome da sua classe ali.

Exercício: o selo de “pão do dia”

A Ana quer um selo com cantos totalmente arredondados, fundo âmbar claro, respiro horizontal de 8 px e texto bem pequeno. Complete o @apply com as três utilitárias que faltam:

.selo { @apply }

Dica: “totalmente arredondado” é rounded-full; o respiro só na horizontal é px-; “bem pequeno” é text-xs. A ordem não importa, mas o nome de cada classe, sim.

11. Resumo

Componente, neste guia, é um conjunto de estilos que se repete e ganha um nome. Você escreve esse nome em um bloco <style type="text/tailwindcss"> (nos exemplos) ou no arquivo de entrada do projeto, dentro de @layer components, e usa @apply para copiar as declarações das utilitárias. O CSS gerado é o mesmo das utilitárias; o que encolhe é o HTML, e o que melhora é a manutenção: um lugar para mudar.

A camada importa. Em components, a utilitária escrita no HTML continua ganhando, e você pode ajustar um caso sem criar um segundo componente. Fora de camada, acontece o contrário — e é aí que a pessoa começa a espalhar !important. Os estados entram como seletor: .botao:hover, .botao:focus-visible. E quando a peça precisa aceitar md: ou hover: no nome, quem resolve é @utility, não @layer components.

Para lembrar

  • Três cópias que mudam juntas: hora de criar a classe. Uma cópia: fique com as utilitárias.
  • @apply copia declarações; não cria vínculo com a utilitária original.
  • Classe de componente mora em @layer components — é a camada que a deixa sobrescrevível.
  • Sem type="text/tailwindcss", o @apply do bloco na página é descartado.
  • Estados: .botao:hover, .botao:focus-visible, .botao:disabled.
  • Dentro do @apply, hover:bg-amber-600 também funciona — escolha um estilo.
  • Diferença entre peças iguais fica no HTML, como utilitária, não dentro do componente.
  • md:botao não gera nada: componente não aceita variante.
  • @utility nome { … } cria uma utilitária própria, e essa aceita variante.
  • Componente com dezoito utilitárias dentro é o CSS antigo com outro nome.

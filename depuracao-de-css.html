Depurar o CSS

A Ana escreveu bg-amber-600 no botão, salvou, recarregou e o botão continuou amarelo claro. Escreveu de novo, agora no cartão, e nada. Foi para o rodapé, tentou de novo, e o rodapé mudou — então a classe funciona, mas naquele botão não. Ela passou vinte minutos trocando classes de lugar antes de perceber que estava lutando contra uma regra que ela mesma tinha escrito seis meses antes, num arquivo de CSS antigo. Depurar CSS é isso: parar de tentar até dar certo e começar a perguntar por que. Nesta aula, a Ana aprende a fazer quatro perguntas na ordem certa e a ler as duas telas do navegador que respondem todas elas.

Você vai aprender
  • As quatro perguntas de toda depuração de CSS, na ordem em que se fazem.
  • Como ler o painel Computed e o painel Styles sem se perder.
  • Por que a ordem das classes no HTML não decide nada.
  • O que fazer quando o valor é outro: duas classes brigando pela mesma propriedade.
  • Como achar uma classe inexistente conferindo o CSS gerado.
  • Por que md: não pega: a variante e o tamanho da tela.
  • O “olho mágico”: contorno e fundo temporários para ver a caixa.
  • Quando o culpado é CSS antigo, !important ou cache.

1. A cena: a classe que funciona em um lugar e não em outro

O caso da Ana é o mais comum de todos. Ela pôs bg-amber-600 em três lugares: no botão, no cartão e no rodapé. O rodapé ficou mais escuro; o botão e o cartão, não. Duas conclusões possíveis: a classe está quebrada (improvável) ou algo nos outros dois elementos está ganhando dela (provável). Como a classe funciona no rodapé, a primeira hipótese já está descartada — e é esse tipo de raciocínio que a aula treina.

Depurar CSS é desconfortável no começo porque o erro é silencioso. O navegador não reclama de classe que não existe, não avisa que duas regras brigaram, não sublinha em vermelho. Ele simplesmente aplica a regra que venceu e segue em frente. A boa notícia é que o navegador guarda todas as evidências: ele sabe qual regra venceu, de qual arquivo ela veio e por que venceu. Você só precisa perguntar no lugar certo.

Uma consequência prática antes de qualquer ferramenta: não conserte no chute. Trocar a classe de lugar, reescrever o bloco, pôr !important “para ver se resolve” — tudo isso às vezes funciona e não ensina nada, então o problema volta na semana seguinte com outra roupa. O que ensina é descobrir quem estava ganhando.

2. As quatro perguntas, na ordem

Toda vez que uma classe “não faz nada”, a causa é uma de quatro. Elas ficam mais fáceis de lembrar em ordem, porque cada resposta descarta a anterior:

PerguntaOnde a resposta estáSinal de que é isso
1. A classe existe?no CSS gerado, procurando o nomenão há regra nenhuma com aquele nome
2. O nome está certo?no CSS gerado, letra por letraexiste uma parecida, com outra grafia
3. Outra regra está ganhando?painel Computed e Styleso valor aplicado é de outra classe
4. A condição da variante vale?a @media em volta da regraa regra existe, mas dentro de uma condição que não vale agora

Um quinto suspeito fica de fora da lista porque não é do Tailwind: CSS antigo da página, com ou sem !important, ou um arquivo que o navegador guardou no cache. Ele entra em cena quando as quatro respostas dão “está tudo certo” e mesmo assim a tela não obedece. A seção 8 cuida dele.

A pergunta 1 e a pergunta 2 são quase a mesma, e valem juntas porque o Tailwind tem um catálogo enorme: bg-amber-100 existe, bg-amber-150 não; p-4 existe, p-44 existe também (é maior do que parece). Digitar text-ambe-600 não gera erro nenhum, e o seu único sinal é o painel vazio.

CSS computado
O valor final que o navegador aplicou, com as contas resolvidas. É a fonte da verdade: se está ali, está valendo.
cascata
A ordem em que o navegador decide entre regras que disputam a mesma propriedade. Quem vem depois ganha, quando o peso é o mesmo.
especificidade
O “peso” de um seletor. .botao pesa menos que #alvo, que pesa menos que um !important.
camada
Um grupo de regras com ordem declarada, criado por @layer. Regra sem camada vence regra com camada, na maioria dos casos.
regra gerada
O CSS que o Tailwind produziu para uma classe. É o que os painéis das caixas mostram quando você pede as regras, em vez dos valores computados.
cache
A cópia do arquivo que o navegador guardou. Se o CSS mudou e a tela não, recarregue ignorando o cache.

3. Duas telas do navegador que respondem tudo

Com o botão direito no elemento e Inspecionar, aparecem dois painéis que você vai usar para sempre. O primeiro é Styles (Estilos): a lista de regras que atingem aquele elemento, na ordem em que o navegador as considerou, cada uma com o arquivo e a linha de onde veio. Regra que perdeu aparece riscada, com o valor antigo ao lado. Quando a Ana olhou ali, viu na primeira linha .botao-antigo { background: #b4532a } e, duas linhas abaixo, riscado, background-color: var(--color-amber-600). Mistério resolvido em três segundos.

O segundo é Computed (Computado): uma lista de propriedades com o valor final. Serve para responder “qual é o valor de verdade?”, sem se preocupar com quem ganhou. É a mesma tela que as caixas deste guia imitam no painel embaixo da prévia. E há um terceiro lugar, mais avançado: a aba Sources mostra o arquivo de CSS gerado inteiro, onde você pode usar Ctrl + F e procurar .bg-amber-600. Se não achar nada, a classe não foi gerada.

.p-2 { padding: calc(var(--spacing) * 2); }
.p-4 { padding: calc(var(--spacing) * 4); }
.p-8 { padding: calc(var(--spacing) * 8); }

Esse trecho é o CSS gerado por um elemento com as três classes juntas. Repare no que ele diz sem falar: as regras das três aparecem, na ordem p-2, p-4, p-8. Ou seja, o arquivo não guarda a ordem em que você escreveu as classes no HTML. Ele guarda a ordem interna do Tailwind, que agrupa por propriedade e ordena por valor. E, como as três disputam padding com o mesmo peso, vence a última do arquivo: p-8. É exatamente por isso que a ordem no HTML não importa.

4. Missão 1: duas classes brigando

Este é o caso que mais aparece em projeto de quem está começando, porque nasce de um hábito inocente: “o respiro está pequeno, vou acrescentar um p-4”. O elemento fica com as três classes, o navegador aplica uma, e a escolhida não é a que você escreveu por último. Na missão, o cartão precisa de 16 px e hoje tem 32:

O cartão carrega p-2, p-8 e p-4. O painel mostra 32 px, e não os 16 px do p-4 que você escreveu por último. Deixe uma única classe de respiro, a de 16 px, e clique em Rodar.

<div id="alvo" class="rounded-lg bg-white p-2 p-8 p-4">Pão quentinho</div>
padding: 32px
background-color: rgb(255, 255, 255)
border-radius: 8px

<div id="alvo" class="rounded-lg bg-white p-4">Pão quentinho</div>

A leitura do painel é o aprendizado: 32 px, mesmo com p-4 escrito por último. Se você tivesse escrito as três classes em outra ordem, o resultado seria o mesmo 32 px. Isso derruba uma intuição que o CSS antigo ensinava — lá, a última regra escrita no arquivo vencia —, e é a razão pela qual o Tailwind pode gerar o CSS na ordem que quiser.

O conserto não é “pôr !important no p-4”. É deixar uma classe só. A regra prática: uma propriedade, uma classe. Quando precisa variar por tela, use a variante (p-4 md:p-6), que é uma condição, não uma segunda declaração competindo. E quando o elemento precisa de ajuste fino em lados diferentes, use longhands que não se sobrepõem: px-6 py-4 diz tudo sem brigar.

5. Missão 2: a classe que não existe

A segunda pergunta é a mais boba e a que mais custa tempo: o nome está certo? O Tailwind tem famílias com nomes parecidos (amber, blue, neutral), degraus que vão de 50 a 950 em saltos, e diferencia maiúsculas de minúsculas. bg-amber-150 não existe — não há 150 na paleta. O navegador não reclama; ele simplesmente não gera a regra.

O fundo do cartão não aparece. Corrija o nome da classe de cor para o tom que existe, o âmbar bem claro (bg-amber-100), e clique em Rodar. A meta confere, no CSS gerado, a variável do fundo.

<div id="alvo" class="rounded-lg bg-amber-150 p-4 text-amber-950">Pão quentinho</div>
padding: 16px
color: oklch(0.279 0.077 45.635)
border-radius: 8px

<div id="alvo" class="rounded-lg bg-amber-100 p-4 text-amber-950">Pão quentinho</div>

Antes de rodar, o painel mostra tudo menos o fundo: o respiro está lá, o raio está lá, o texto está lá — e background-color não aparece, porque a classe não existe. Esse é o padrão que vale memorizar: quando só uma propriedade falta no painel, o suspeito é o nome da classe daquela propriedade. Não é o navegador, não é o build; é o nome.

Existe um jeito de conferir sem o painel: peça as regras geradas (nas caixas, o botão que mostra o CSS; no navegador, a busca na aba Sources) e procure o nome que você escreveu. Se a busca não achar, a classe não foi gerada. Se achar uma parecida, você acabou de encontrar o erro de digitação. Vale fazer isso com calma, letra por letra, porque o olho tende a “consertar” o que lê.

E fica o aviso que a aula Otimização detalha: classe montada por pedaços ("bg-" + cor + "-100") nunca existe, porque o Tailwind varre texto, não executa código. O sintoma é idêntico ao do erro de digitação — a propriedade simplesmente não aparece — mas a causa é outra, e o conserto também: escrever o nome inteiro.

6. Missão 3: a variante que não casa

A terceira pergunta é a que mais engana quem já entendeu as duas primeiras: a regra existe, está escrita certo e ninguém está ganhando dela — só que ela mora dentro de uma condição que não vale naquele momento. O exemplo clássico é md:, que o Tailwind traduz para “a partir de 48 rem”, ou 768 px:

.p-4 { padding: calc(var(--spacing) * 4); }
@media (width >= 48rem) {
  .md\:p-8 { padding: calc(var(--spacing) * 8); }
}

Na prévia abaixo, a janela tem 640 px — então o md: não vale, e o cartão fica com os 16 px do p-4. A Ana queria 32 px nessa tela e escreveu a variante de tela grande sem querer. O conserto é usar a variante que vale a partir de 640 px, que é sm::

A prévia tem 640 px de largura. O respiro grande está em md:p-8, que só vale a partir de 768 px — por isso o painel mostra 16 px. Troque a variante por uma que valha em 640 px (sm:) e clique em Rodar.

<div id="alvo" class="rounded-lg bg-white p-4 md:p-8">Pão quentinho</div>
padding: 16px
background-color: rgb(255, 255, 255)
border-radius: 8px

<div id="alvo" class="rounded-lg bg-white p-4 sm:p-8">Pão quentinho</div>

O mesmo raciocínio vale para todas as variantes condicionais. hover: só age com o mouse em cima — no celular, quase nunca. dark: só age quando a classe dark está no html; se o seu tema escuro é feito por data-theme, a variante não vai casar. print: só age na impressão, e por isso o painel de uma caixa nunca mostra o efeito dela. focus-visible: só age com foco vindo do teclado.

O jeito de conferir isso no navegador é o mesmo das emulações da aula Acessibilidade: force a condição. Em Styles, clique em :hov para fingir o mouse; na aba Rendering, emule prefers-reduced-motion ou o tema escuro; no DevTools do Chrome, dá para redimensionar a janela e ver a @media passar a valer. O CSS gerado mostra a condição escrita na cara — basta ler.

7. O olho mágico: ver a caixa antes de julgar

Metade das dúvidas de CSS não é sobre a propriedade, é sobre o elemento. A pessoa acha que está mexendo no cartão e está mexendo no texto dentro dele; acha que o espaço é margem e é respiro; acha que a caixa tem 200 px e ela tem 320. Para isso existe um truque de dez segundos: dar um contorno temporário e um fundo berrante.

<div class="cartao outline-2 outline-red-500 bg-red-100">…</div>

O contorno desenha a borda externa exata do elemento, e o fundo mostra a área que ele ocupa. Compare com o que você imaginava e a dúvida acaba. Depois, apague as duas classes — elas são ferramenta, não estilo. O mesmo vale para o “olho mágico” de espaçamento: pôr bg-amber-100 em todos os filhos de uma lista mostra, de uma olhada, quem tem respiro e quem não tem.

A variante desse truque é o inspetor do navegador: passar o mouse sobre o elemento na aba Elements desenha a caixa na tela. O contorno no código serve para quando você não pode abrir o DevTools (num celular emprestado, numa apresentação) ou para mostrar o problema para outra pessoa sem pedir que ela abra nada.

8. Quando o culpado é CSS antigo, !important ou cache

As quatro perguntas deram “está tudo certo” e a tela continua teimando. Agora o suspeito é o que está em volta. Três casos, em ordem de frequência:

CSS antigo sem camada. O Tailwind coloca as utilitárias numa camada (@layer utilities). Regra que está fora de qualquer camada vence regra que está dentro de uma — é assim que o CSS funciona, e é o que faz o site da Ana ter um .botao-antigo mandando no fundo do botão. No painel Styles, a regra vencedora aparece sem o rótulo da camada. Conserto: apagar a regra velha ou colocá-la dentro de @layer base, para ela perder para as utilitárias. A aula Migrando de CSS Antigo trata disso como processo; aqui basta o diagnóstico.

!important. Uma declaração com !important ganha de qualquer coisa que não tenha !important, inclusive de utilitária. Se o CSS antigo tem color: #6b7280 !important, o text-amber-900 não tem chance nenhuma. O Tailwind permite escrever text-amber-900! (no v4 o ponto de exclamação vai no fim da classe; na frente também funciona), mas isso é remédio para emergência: cada !important novo aumenta a confusão do próximo, e você acaba com uma guerra de prioridades. Prefira tirar o !important do CSS antigo.

Cache. Você mudou o CSS, o build rodou, e a página continua igual. Antes de duvidar do Tailwind, recarregue ignorando o cache (Ctrl + Shift + R, ou Cmd + Shift + R no Mac). Se a mudança aparece, era cache. Em projeto com build, o segundo suspeito é o processo que gera o CSS: se ele não está rodando, o arquivo fica velho e nenhuma classe nova entra. A pista é sempre a mesma: classes antigas funcionam, as novas não.

9. Cenários do dia a dia

Cenário 1: o painel vazio

O painel que mostra o CSS computado fica em branco e a pessoa entra em pânico: “quebrei tudo”. Na maioria das vezes ele está dizendo a verdade — nada mudou naquele elemento. Três causas comuns: a classe não existe (nome errado), o elemento descrito é outro (o painel olha o id="alvo" ou o primeiro filho da prévia, e você mexeu no neto), ou o valor aplicado é igual ao que o elemento já tinha. Antes de reescrever o HTML, confira de quem o painel está falando.

Cenário 2: “funciona no meu computador e não no celular da cliente”

Quase sempre é variante de breakpoint. A Ana testou no monitor de 1440 px, onde lg: vale; no celular de 390 px, só o que está sem prefixo vale. O caminho de diagnóstico é abrir o DevTools com o modo responsivo na largura da cliente e ler o CSS gerado: qual @media está em volta da regra que você quer? Se a condição pede 1024 px e a tela tem 390, não há bug — há engano de variante. A aula Breakpoints tem a tabela das larguras.

Cenário 3: o elemento certo, a propriedade errada

A pessoa põe text-amber-900 no div e o texto continua cinza, porque quem tem a cor definida é o <p> dentro dele, com a própria classe. Cor e fonte herdam, mas uma classe no filho ganha da herança do pai. O sintoma é o mesmo de sempre: o painel do pai mostra a cor certa e a tela não muda. A pergunta que resolve: quem é o elemento que realmente desenha aquele texto? Muitas vezes não é onde você está olhando.

2. O painel mostra respiro, raio e texto, mas não mostra o fundo. Qual é o suspeito?

3. Por que md:p-8 não pega numa janela de 640 px?

Exercício: o cartão com três respiros

Este cartão precisa de 24 px de respiro e hoje tem três classes de respiro brigando. Escreva a classe única que resolve:

<div class="rounded-lg bg-white ">Pão quentinho</div>

Dica: 24 px é o sexto degrau da escala. As classes p-2 e p-8 precisam sair — não basta acrescentar mais uma.

11. Resumo

Depurar CSS é fazer quatro perguntas na ordem: a classe existe? o nome está certo? outra regra está ganhando? a condição da variante vale agora? O CSS gerado responde as duas primeiras (procure o nome no arquivo), o painel Computed responde “qual valor ficou” e o painel Styles responde “quem ganhou”, com a regra perdedora riscada e o nome do arquivo de origem.

A ordem das classes no HTML não decide nada: o Tailwind ordena as regras por conta própria, e duas classes da mesma propriedade são sempre um erro de escrita, não uma escolha. Variantes moram dentro de condições (@media (width >= 48rem), :hover, tema escuro), e por isso podem existir sem valer. Quando tudo parece certo e a tela não obedece, o culpado costuma ser CSS antigo sem camada, um !important herdado ou o cache — nessa ordem.

Para lembrar

  • Classe que não existe não avisa: procure o nome no CSS gerado.
  • Ordem no HTML não importa; vale a última regra que o Tailwind gerou.
  • Uma propriedade, uma classe. Para variar por tela, use variante.
  • Falta só uma propriedade no painel? O nome daquela classe está errado.
  • md: vale de 768 px para cima; sm:, de 640 px.
  • print:, hover: e focus-visible: não aparecem no painel porque dependem de condição.
  • Computed mostra o valor final; Styles mostra quem ganhou, com o perdedor riscado.
  • Contorno e fundo temporários mostram a caixa exata — e depois se apagam.
  • CSS sem camada vence utilitária; !important vence tudo que não é !important.
  • Recarregue sem cache antes de duvidar do Tailwind.

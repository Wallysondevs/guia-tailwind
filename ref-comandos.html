Comandos e build

Até aqui, a Ana usou o Tailwind sem instalar nada: as caixas deste guia compilam o HTML no próprio navegador. Mas o site da padaria precisa de um arquivo CSS de verdade, que funcione sem internet e sem compilador na máquina de quem visita. É aí que entram dois comandos: um instala, o outro gera. Ela abriu o terminal em /home/ana/padaria, digitou a primeira linha e ficou olhando a tela — sem saber se tinha dado certo. Esta página é a consulta dos comandos: o que instalar, o que rodar, o que cada arquivo faz e por que o CSS gerado é diferente do que ela escreveu.

1. O que é "build" e por que ele existe

Build é a etapa em que um programa lê os seus arquivos e escreve outros, prontos para o navegador. No caso do Tailwind, o programa lê o seu HTML e o seu CSS de entrada, descobre quais classes aparecem e escreve um CSS final que contém só as regras dessas classes. O navegador não sabe o que é p-4: ele só entende CSS. Alguém precisa fazer essa tradução antes de a página abrir, e esse alguém é o build.

É por isso que uma classe nova não aparece na tela até você recompilar. O arquivo final foi escrito num momento do passado, com a lista de classes daquele momento. Quando você acrescenta md:grid-cols-2 no HTML e a grade não muda, o culpado quase sempre é o build que não rodou — e não o Tailwind. A exceção é justamente o que este guia usa nas caixas: o compilador de navegador, que lê o HTML a cada clique e compila na hora.

Existem três jeitos de rodar esse build, e vale saber o nome dos três. O primeiro é a CLI (@tailwindcss/cli): um comando que você dá no terminal. O segundo é o plugin do Vite (@tailwindcss/vite), que compila junto com o resto do projeto. O terceiro é o compilador de navegador (@tailwindcss/browser), que é o deste guia e serve para estudar e prototipar, não para produção. Todos usam o mesmo motor e produzem o mesmo CSS; o que muda é quem aperta o botão. A aula Sem Build cobre o terceiro caminho, que é o desta página.

build
A etapa que transforma os seus arquivos-fonte no arquivo que o navegador lê. Roda no seu computador, não no do visitante.
entrada
O CSS que você escreve, com @import "tailwindcss"; e as suas diretivas. É pequeno: três linhas já bastam.
saída
O CSS gerado, com todas as regras. É esse arquivo que o HTML deve carregar no <link>.
CLI
Command line interface: o programa que você chama pelo terminal, com flags como -i e -o.
watch
O modo que fica rodando e recompila a cada arquivo salvo. Evita o "esqueci de gerar de novo".

2. Instalando as duas peças

São dois pacotes, e a divisão ajuda a entender. tailwindcss é o motor: a parte que lê classes e escreve CSS. @tailwindcss/cli é a interface de terminal em volta dele. Instalar o motor sozinho não dá comando nenhum; instalar a CLI sozinha não tem motor para chamar. Os dois vão como dependência de desenvolvimento (-D), porque o build roda na sua máquina e não precisa viajar para o servidor. Se for a primeira vez que você abre um terminal, a aula Instalando faz esse passo com calma.

$ cd /home/ana/padaria
$ npm install -D tailwindcss @tailwindcss/cli

added 2 packages, and audited 3 packages in 2s

found 0 vulnerabilities

Duas coisas acabaram de acontecer. O npm criou (ou atualizou) o arquivo package.json, que é a lista de dependências do projeto, e a pasta node_modules, onde o código dos pacotes fica. O package.json é o que você versiona; node_modules não, porque é reconstruível com npm install. Se você clonar o projeto em outra máquina, roda npm install sem argumentos e o npm lê a lista do package.json.

Uma pegadinha de versão: a partir do Tailwind v4, o pacote da CLI é @tailwindcss/cli, e não mais tailwindcss com comando embutido. Tutoriais antigos mandam rodar npx tailwindcss init -p, que era o v3 e não existe mais. Se um comando do tutorial não for reconhecido, a primeira suspeita é a versão. Este guia usa a v4.3.5 — a mesma que aparece no cabeçalho do CSS gerado.

3. O CSS de entrada e a saída

O arquivo de entrada é seu, e pode ter três linhas. O nome é escolha sua: entrada.css, app.css, tailwind.css. O que importa é a primeira linha, que manda o motor trazer o tema, a base e as utilitárias. O assunto tem aula inteira em O CSS de Entrada.

@import "tailwindcss";

/* as suas personalizações vêm depois, se houver */

A saída é o arquivo que o HTML carrega. Ela não deve ser editada à mão — o próximo build apaga tudo o que você escrever ali. Guarde-a numa pasta separada, como dist/, e trate como produto: quem edita o produto em vez da receita perde a mudança na próxima fornada. O <link> no HTML aponta para ela, e não para o arquivo de entrada.

<link rel="stylesheet" href="dist/estilo.css">

Se você abrir a saída no editor, vai encontrar um cabeçalho de licença, uma camada de tema com variáveis, uma camada de base com a normalização do navegador e, no fim, só as utilitárias que você usou. Nada de 300 classes de cor que ninguém pediu: no v4 o build gera apenas o que encontra nos arquivos. Por isso um site pequeno costuma sair com poucos quilobytes, e a página do guia que você está lendo cabe folgada num arquivo só.

E onde o motor procura as classes? A partir da pasta do arquivo de entrada, seguindo as regras de inclusão do projeto — e respeitando o .gitignore. Se o seu HTML está em outra pasta, ou se as classes vêm de um arquivo que ele não enxerga, existe a diretiva @source para apontar o caminho. É o primeiro lugar para olhar quando "o build roda, mas o CSS não tem a classe nova".

4. Os comandos do dia a dia

Não são muitos. A tabela abaixo é a lista completa do que você vai digitar nesta fase, com o efeito de cada um. Os caminhos são os da Ana: entrada em src/entrada.css, saída em dist/estilo.css.

ComandoO que fazQuando usar
npm install -D tailwindcss @tailwindcss/cliinstala o motor e a CLI no projetouma vez, no começo
npx @tailwindcss/cli -i src/entrada.css -o dist/estilo.csscompila uma vez e encerrapara conferir e antes de publicar
npx @tailwindcss/cli -i src/entrada.css -o dist/estilo.css --watchcompila e fica observando os arquivosdurante o desenvolvimento
npx @tailwindcss/cli -i src/entrada.css -o dist/estilo.css --minifycompila comprimido, sem espaçosno build de produção
npx @tailwindcss/cli --helpmostra as opções disponíveisquando esquecer uma flag
npm run devroda o script dev do package.jsono atalho do dia a dia
npm run buildroda o script build, geralmente com --minifyantes de subir para o servidor

O npx merece uma explicação, porque assusta. Ele executa um programa que está dentro de node_modules sem você precisar instalar nada globalmente. É por isso que o comando começa com npx @tailwindcss/cli e não com tailwindcss: o nome do pacote é @tailwindcss/cli, e o npx sabe achar o executável dentro dele. Quando você criar os scripts no package.json, o mesmo comando pode ficar ainda mais curto.

Cuidado com um detalhe de ordem: o --watch não termina sozinho. Ele fica no terminal até você apertar Ctrl e C. Se você abrir outra aba e rodar o build de produção enquanto o watch está ligado, os dois escrevem no mesmo arquivo e o resultado pode ficar pela metade por um instante. Pare o watch antes de gerar a versão final — ou, melhor, aponte os dois para arquivos diferentes.

A cor da marca da padaria é #7c2d12 e não existe na paleta: a classe bg-marca não gera nada. Declare a variável no @theme para essa classe passar a existir.

<button id="alvo" class="rounded-lg bg-marca px-4 py-2 text-white">Encomendar</button>
color: rgb(255, 255, 255)
border-radius: 8px
padding-inline: 16px
padding-block: 8px

<style type="text/tailwindcss">
@theme {
  --color-marca: #7c2d12;
}
</style>
<button id="alvo" class="rounded-lg bg-marca px-4 py-2 text-white">Encomendar</button>

Esta caixa é o build em miniatura: o bloco @theme é o que você escreveria em src/entrada.css, e a classe bg-marca só passa a existir porque a variável existe. Repare que a variável vira uma classe com o nome da cor: --color-marca produz bg-marca, text-marca, border-marca e ring-marca de uma vez. O prefixo --color- não é enfeite: é ele que diz ao motor em que família a variável entra.

5. As flags: o que cada uma muda

Flag é a palavra que começa com dois traços e ajusta o comportamento do comando. São poucas na CLI do Tailwind, e todas cabem numa tabela. A regra de ouro é escrever por extenso quando estiver em dúvida — --watch e --minify se explicam sozinhos, e nenhuma versão confunde as duas.

FlagForma curtaO que muda
--input-iqual arquivo é o CSS de entrada
--output-oonde o CSS gerado é escrito
--watch—fica rodando e recompila a cada gravação
--minify—remove espaços e comentários da saída
--help-himprime a lista de opções e encerra

Sobre o --minify, vale entender o que ele faz e o que não faz. Ele remove espaços, quebras de linha e comentários: o arquivo fica menor para baixar, e ilegível para humanos — o que é esperado, porque ninguém edita a saída. Ele não remove classes não usadas, porque elas já não estão lá: o motor só gera o que encontrou. Se o seu CSS final está grande, o problema é a quantidade de classes diferentes espalhadas pelo projeto, não a formatação.

E há uma flag que não existe mais: --content, do v3, usada para listar os arquivos onde procurar classes. No v4 esse trabalho passou para o CSS, com @source, e a detecção é automática a partir da pasta do arquivo de entrada. Quem cola um comando antigo e recebe "unknown option" está batendo nessa mudança.

6. O projeto por dentro

Depois do primeiro build, a pasta da Ana tem cinco vizinhos. Saber quem é quem evita 80% da confusão: metade dos problemas de "não atualizou" é um arquivo certo sendo gerado no lugar errado, ou um <link> apontando para o arquivo antigo.

Arquivo ou pastaQuem escrevePara que serve
index.htmlvocêo conteúdo; carrega a saída no <link>
src/entrada.cssvocêo @import "tailwindcss" e as suas diretivas
dist/estilo.csso buildo CSS final; não editar à mão
package.jsonnpm e vocêas dependências e os scripts
node_modules/npmo código dos pacotes; nunca versionar
package-lock.jsonnpmas versões exatas; versionar sempre

Os scripts são a parte que economiza digitação todos os dias. Em vez de decorar o comando com dois caminhos e uma flag, você escreve uma vez no package.json e chama por um nome curto. O npm já coloca node_modules/.bin no caminho quando roda um script, então dentro dele o npx é dispensável — mas deixá-lo não faz mal e ajuda quem lê.

{
  "name": "padaria",
  "private": true,
  "scripts": {
    "dev": "npx @tailwindcss/cli -i src/entrada.css -o dist/estilo.css --watch",
    "build": "npx @tailwindcss/cli -i src/entrada.css -o dist/estilo.css --minify"
  },
  "devDependencies": {
    "tailwindcss": "^4.3.5",
    "@tailwindcss/cli": "^4.3.5"
  }
}

Com isso, o dia de trabalho começa com npm run dev e o terminal fica mostrando cada recompilação. Antes de publicar, Ctrl e C para parar, npm run build e pronto. Um cuidado: o ^ antes da versão permite atualizações dentro da mesma major — ^4.3.5 aceita 4.4, 4.9, mas não 5.0. É uma forma de receber correções sem quebrar o projeto de um dia para o outro.

$ npm run dev

> padaria@ dev
> npx @tailwindcss/cli -i src/entrada.css -o dist/estilo.css --watch

≈ tailwindcss v4.3.5

Done in 128ms
Rebuilding...
Done in 41ms

Esse > no começo é o próprio npm repetindo o comando que vai rodar — não é erro. E o ≈ tailwindcss v4.3.5 é a única confirmação de versão que você vai ver no caminho. Se ele mostrar v3, o projeto tem o pacote errado instalado, e todas as diretivas novas vão falhar.

7. As diretivas do CSS de entrada

Diretiva é a linha que começa com arroba. No v3 quase tudo se configurava num tailwind.config.js; no v4 quase tudo se escreve no CSS, com diretivas. A tabela é o mapa completo do que existe e do que cada uma resolve.

DiretivaPara que serveExemplo
@import "tailwindcss"traz tema, base e utilitárias@import "tailwindcss";
@themedefine ou troca valores do tema--color-marca: #7c2d12;
@sourceaponta arquivos que o motor deve ler@source "../paginas";
@applyusa utilitárias dentro de uma regra sua@apply rounded-lg p-4;
@layercoloca a regra na camada certa@layer components { … }
@utilitycria uma utilitária própria, com variante@utility tab-4 { … }
@custom-variantdefine uma variante nova@custom-variant aberto (&[open]);
@variantusa uma variante dentro do CSS seu@variant dark { … }
@plugincarrega um plugin@plugin "@tailwindcss/typography";
@referencedá contexto ao @apply em arquivo separado@reference "../entrada.css";
@configlê um tailwind.config.js antigo@config "../tailwind.config.js";

As três que você usa numa tarde normal são @theme (cor, fonte, espaçamento próprio), @layer components com @apply (quando um componente se repete) e @source (quando o motor não enxerga uma pasta). As outras existem para casos específicos, e vale saber que estão lá antes de inventar gambiarra.

O componente .botao só tem a cor e o texto branco. Complete com @apply para ele ganhar raio de 8 px e respiro de 16 px por 12 px, e o botão sair do tamanho do texto.

<style type="text/tailwindcss">
@layer components {
  .botao {
    @apply bg-amber-600 text-white;
  }
}
</style>
<button id="alvo" class="botao">Encomendar</button>
background-color: oklch(0.666 0.179 58.318)
color: rgb(255, 255, 255)

<style type="text/tailwindcss">
@layer components {
  .botao {
    @apply rounded-lg bg-amber-600 px-4 py-3 text-white;
  }
}
</style>
<button id="alvo" class="botao">Encomendar</button>

O painel mostra o resultado como se as classes estivessem no HTML, porque é isso que o @apply faz: copia as declarações para dentro da sua regra. E repare no verde da missão: ela também confere que existe exatamente um elemento com a classe .botao. Esse tipo de conferência pega o erro mais comum de quem mexe em CSS de componente — editar a regra e não salvar o arquivo, ou salvar num lugar que o build não lê.

8. Quando dá errado

Os problemas de build são poucos e repetitivos. O primeiro é o arquivo de saída que ninguém carrega: o CSS é gerado em dist/estilo.css, mas o <link> do HTML aponta para src/entrada.css. Abra a aba Network do navegador e confira se o arquivo pedido é o mesmo que o build escreveu, com o mesmo tamanho. Um 404 ali explica tudo.

O segundo é o caminho errado na flag. -i e -o são relativos à pasta em que você está quando digita o comando, e não à pasta do projeto. Rodar o comando de dentro de src/ faz src/entrada.css virar src/src/entrada.css. Se a mensagem de erro falar de arquivo inexistente, confira o pwd antes de duvidar da flag.

O terceiro é a classe que não existe. O build roda, o CSS é gerado, e a classe não está lá porque o nome está errado — bg-amber-600 escrito bg-amber600. O motor não avisa: ele lê texto. O jeito de descobrir é procurar o nome da classe no arquivo final; se não estiver, o problema é de digitação ou de variante inválida, não de build.

O quarto é o build antigo rodando junto com o novo. Dois terminais com --watch abertos, ou um watch de ontem que você esqueceu, escrevem no mesmo arquivo e o resultado alterna entre versões. Feche todos e rode um só. Um sintoma clássico: você muda o HTML, salva, e o CSS "volta" depois de alguns segundos com a versão anterior.

O quinto é o node_modules corrompido por uma instalação interrompida. A saída é sempre a mesma: apague node_modules e rode npm install de novo. Não apague o package-lock.json — ele é o que garante que você receba exatamente as mesmas versões. Se o erro persistir, vale conferir a versão do Node: a v4 pede uma versão recente, e um Node antigo reclama de sintaxe antes mesmo de chegar ao Tailwind.

O sexto é o mais chato e o mais raro: o build não enxerga o arquivo onde estão as classes. Isso acontece quando o HTML está numa pasta fora da árvore do CSS, quando o arquivo está no .gitignore ou quando as classes são montadas por concatenação em JavaScript. A resposta é @source "../outra-pasta"; para o primeiro caso e classes completas para o último.

Como alternativa a toda essa configuração, vale conhecer o caminho que dispensa a flag de entrada e saída. Se o projeto usa Vite, instale @tailwindcss/vite junto com o motor, registre o plugin no vite.config.js e mantenha o @import "tailwindcss"; no CSS. Quem compila passa a ser o próprio servidor de desenvolvimento: você salva o arquivo e a página atualiza, sem terminal extra e sem caminho para errar. É o que a maioria dos projetos novos escolhe hoje.

import { defineConfig } from "vite";
import tailwindcss from "@tailwindcss/vite";

export default defineConfig({
  plugins: [tailwindcss()],
});

Um erro de sintaxe que aparece uma vez e nunca mais: a linha @import precisa ser a primeira do arquivo. CSS exige que todo @import venha antes de qualquer regra, e um @theme colocado acima dela faz o navegador descartar o import inteiro. Se o build passa e a página fica sem estilo nenhum, olhe as primeiras linhas do CSS de entrada antes de qualquer outra coisa.

9. Resumo

Instale tailwindcss e @tailwindcss/cli como dependência de desenvolvimento; escreva @import "tailwindcss"; num CSS de entrada; rode npx @tailwindcss/cli -i src/entrada.css -o dist/estilo.css. Aponte o <link> do HTML para a saída, nunca para a entrada. E não edite a saída: ela é descartável e o próximo build escreve por cima.

  • --watch durante o desenvolvimento, --minify na versão final.
  • Os scripts do package.json transformam o comando comprido em npm run dev e npm run build.
  • O v4 configura no CSS: @theme para valores, @source para caminhos, @apply para componentes, @plugin para plugins.
  • tailwind.config.js só entra por compatibilidade, via @config.
  • Classe que não aparece na tela é quase sempre build não rodado, caminho errado ou nome digitado errado.
  • O compilador de navegador é para estudar e prototipar; o site publicado usa o CSS gerado.

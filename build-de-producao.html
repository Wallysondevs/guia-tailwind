Build de Produção

A padaria vai ganhar endereço na internet na segunda-feira, e a Ana percebeu que nunca pensou no assunto "publicar". A folha que ela gera no dia a dia é confortável de ler, com espaços e comentários, e não é essa que o visitante deve baixar. Nesta aula ela separa os dois momentos — o build de desenvolvimento e o build de produção —, aprende o que a opção --minify faz de verdade, monta o checklist que evita publicar besteira e entende por que o navegador de quem já visitou o site insiste em mostrar a versão velha.

Você vai aprender
  • O que diferencia o build de desenvolvimento do build de produção.
  • O que --minify faz e o que ele não faz.
  • Por que a aparência não muda quando o arquivo encolhe.
  • O checklist de conferência antes de publicar.
  • Como o cache do navegador atrapalha e como o nome do arquivo resolve.
  • Como montar o build automático num servidor, com npm ci.
  • O que fazer quando o site publicado fica sem estilo.

1. A cena: segunda-feira é a publicação

O site da Ana tem três páginas, uma folha gerada e um problema novo: publicar não é copiar a pasta inteira. Se ela copiar tudo, vão junto o node_modules, os arquivos de origem e a folha cheia de espaços. Se copiar só o HTML, a página chega sem estilo. No meio disso, existe uma decisão que ela nunca teve de tomar: qual versão do CSS é a que o visitante recebe.

A resposta é que existem dois builds, com objetivos diferentes, e os dois usam o mesmo comando. Durante o desenvolvimento, o objetivo é você conseguir ler o que foi gerado e entender o que aconteceu. Na produção, o objetivo é o visitante baixar o menor arquivo possível, o mais rápido possível. São prioridades opostas — legibilidade contra tamanho — e é por isso que existe uma opção para virar a chave.

Nada disso muda o que você escreve. O HTML continua com as mesmas classes, o CSS de entrada continua igual, e o resultado na tela tem de ser idêntico. O build de produção é uma etapa de acabamento: pega o mesmo conteúdo e o entrega no formato mais econômico. Se a aparência mudar, alguma coisa saiu do esperado.

2. Duas folhas, dois trabalhos

Vale colocar os dois builds lado a lado, porque a diferença é pequena na lista e grande na prática:

AssuntoBuild de desenvolvimentoBuild de produção

arquivogrande, indentado, com comentáriosuma linha por regra, sem espaço sobrando
quando rodaa cada salvamento, o dia inteirouma vez, antes de cada publicação

Escrever o mesmo CSS com o mínimo de caracteres: sem espaços, sem comentários, com valores na forma mais curta.
artefato
O arquivo que a publicação entrega ao navegador: a folha gerada, as páginas, as imagens. O que fica no seu computador e nunca vai ao ar não é artefato.
cache
A cópia que o navegador guarda de um arquivo já baixado. Enquanto ela vale, o servidor nem é consultado.
nome versionado
Um pedaço do conteúdo no nome do arquivo, como estilo.3f2a.css. Conteúdo novo, nome novo, download garantido.
ambiente
Onde o projeto está rodando: desenvolvimento, na sua máquina, ou produção, no servidor que o público acessa.

O mais comum é ter as duas coisas no package.json, cada uma com seu script. O dev fica rodando enquanto você trabalha; o build é chamado na hora de publicar. Como os dois escrevem no mesmo arquivo de saída, o último que roda manda — e é aí que nasce um erro clássico: publicar sem perceber que a última geração foi a de desenvolvimento, cheia de espaços.

Se preferir separar de vez, use dois arquivos de saída: dist/estilo.css para o dia a dia e dist/estilo.min.css para a produção. O custo é ter dois link diferentes no HTML, o que é chato de manter. Para o site da padaria, o caminho mais simples é um arquivo só, gerado de novo com --minify imediatamente antes de publicar.

3. O que --minify faz de verdade

A opção --minify (ou -m) pede ao gerador que escreva o CSS em formato compacto. Na prática, ela faz quatro coisas: tira os espaços e as quebras de linha que só servem para leitura humana, remove os comentários que não são de licença, encurta valores quando há uma forma mais curta de escrever o mesmo (0.5rem pode virar .5rem) e junta regras que podem ser declaradas de uma vez.

$ npx @tailwindcss/cli -i src/entrada.css -o dist/estilo.css --minify
$ ls -lh dist/estilo.css
-rw-r--r-- 1 ana ana 3,6K nov 27 09:14 estilo.css

No projeto da Ana, a folha de desenvolvimento tem cerca de 14 KB; com --minify, fica em torno de 3,6 KB. A diferença parece pequena em números absolutos, e é — para um site de três páginas com vinte visitantes por dia. Mas o hábito importa: em um site com cinquenta páginas e muitos acessos, os mesmos 70% de economia aparecem na conta do servidor e no tempo de carregamento de quem está no 4G.

O que --minify não faz: não remove classes que você não usa (isso já acontece sempre, por desenho), não troca o nome das classes, não mexe nas variáveis do tema e não "otimiza" a sua lógica. Ele só escreve o mesmo CSS de forma mais curta. Se alguém prometer que minificar resolve um problema de seletor, desconfie: são assuntos diferentes.

4. O que não muda: a aparência

Esta é a parte tranquilizadora. Minificar é uma transformação de texto, não de regra: as mesmas classes, os mesmos valores, a mesma ordem de camadas. O navegador não sabe se o arquivo foi escrito com espaços ou sem; ele lê a mesma estrutura. Se a tela mudou depois de minificar, o problema não é a minificação — é outra folha, um arquivo velho ou um erro de caminho.

Por isso, a conferência de produção é sempre a mesma: abrir as três páginas, olhar o resultado e comparar o CSS computado de dois ou três elementos que você conhece bem. Quando os valores batem, o build está certo. Quando não batem, o painel diz qual propriedade ficou de fora — e o culpado costuma ser uma classe que não foi encontrada na varredura.

Vale treinar essa comparação na caixa abaixo. A missão é escrever a folha com menos regras possíveis, sem mudar o resultado: em vez de duas classes de respiro (horizontal e vertical), uma só classe que cuida dos quatro lados.

O cartão usa px-4 py-4, que gera duas regras para o mesmo resultado. Troque por uma única classe de respiro que dê 16 px nos quatro lados — menos CSS, mesma aparência.

<div id="alvo" class="px-4 py-4 bg-amber-100">Pão quentinho</div>
background-color: oklch(0.962 0.059 95.617)
padding-inline: 16px
padding-block: 16px

<div id="alvo" class="p-4 bg-amber-100">Pão quentinho</div>

Antes, o painel trazia as duas propriedades separadas, padding-inline e padding-block; depois da missão, ele resume tudo em padding: 16px, vindo de uma regra só. Esse é o tipo de economia que não exige ferramenta nenhuma: vem de conhecer as classes e preferir a que resolve tudo de uma vez. Em um site grande, escolhas como essa valem mais que qualquer opção de build.

5. O fluxo de publicação, em ordem

Publicar tem uma sequência, e a ordem evita metade dos problemas. Primeiro, pare o modo de desenvolvimento: um --watch ligado pode sobrescrever a folha de produção segundos depois de você gerá-la. Segundo, rode o build de produção e confira o tamanho do arquivo. Terceiro, abra as páginas no navegador em modo local, inclusive na largura de um celular. Quarto, copie para o servidor apenas o que o visitante precisa: as páginas, a folha gerada e as imagens.

O que nunca vai para o servidor: node_modules, o CSS de entrada, o package.json, os arquivos de exemplo e a pasta de rascunhos. Nada disso é usado pelo navegador, e alguns desses arquivos contam detalhes do seu projeto que não interessam ao público. A regra prática é pensar no servidor como uma vitrine: entra o que o cliente vê.

Uma atenção especial ao caminho do link. No seu computador, o HTML e a pasta dist estão lado a lado, e href="dist/estilo.css" funciona. No servidor, a estrutura pode ser outra: se você copiou só o conteúdo de dist, o caminho vira href="estilo.css". Caminho errado é a causa número um de "subi o site e ficou sem estilo" — e o sintoma é uma página cinza e sem espaçamento, igual à de quando falta o @import.

6. O checklist antes de publicar

A lista é curta de propósito, para ser usada de verdade. Cinco conferências resolvem quase tudo:

A quinta conferência merece um exemplo, porque é a mais esquecida. Durante o desenvolvimento é comum pintar um bloco de vermelho para achar onde ele está, ou deixar um texto de teste. Nada disso pode ir para a produção — não porque quebre o site, mas porque o visitante vê. A caixa abaixo faz essa limpeza de um jeito que você pode conferir: a meta conta os elementos com a classe de teste e exige zero.

Existe um caso em que a classe nunca vai aparecer no arquivo, e ele engana muita gente: quando o nome não existe no catálogo do Tailwind. O gerador não tenta adivinhar o parente mais próximo e não avisa — ele simplesmente não escreve regra nenhuma para um nome que não conhece. Uma classe inventada, como texto-ambar, atravessa o build inteira sem deixar rastro e chega ao ar sem efeito.

A etiqueta foi publicada com texto-ambar, um nome que não existe: a folha saiu sem regra de cor e o texto ficou preto. Troque pela utilitária que pinta a letra em âmbar escuro.

<span id="alvo" class="bg-amber-100 texto-ambar px-2 py-1">Pão do dia</span>
.bg-amber-100 {
  background-color: var(--color-amber-100);
}
.px-2 {
  padding-inline: calc(var(--spacing) * 2);
}
.py-1 {
  padding-block: var(--spacing);
}

<span id="alvo" class="bg-amber-100 text-amber-900 px-2 py-1">Pão do dia</span>

A vitrine foi publicada com uma marcação de teste: um bloco com fundo vermelho, que existe só para achar a seção. Tire esse bloco e deixe as duas etiquetas de verdade com o fundo da marca.

<div id="alvo">
  <p class="bg-red-500 px-2 py-1">teste</p>
  <span class="bg-amber-100 px-2 py-1">Pão francês</span>
  <span class="bg-amber-100 px-2 py-1">Broa</span>
</div>
.bg-amber-100 {
  background-color: var(--color-amber-100);
}
.bg-red-500 {
  background-color: var(--color-red-500);
}
.px-2 {
  padding-inline: calc(var(--spacing) * 2);
}
.py-1 {
  padding-block: var(--spacing);
}

<div id="alvo">
  <span class="bg-amber-100 px-2 py-1">Pão francês</span>

Repare que o data-goal conta elementos, não regras: conta:.bg-red-500=0 quer dizer "nenhum elemento com essa classe". É um jeito de conferir ausência — o que, no CSS, é a coisa mais difícil de verificar a olho nu. Na sua página, o equivalente é usar a busca do editor e procurar a palavra que você sabe que é de teste.

7. Cache: por que o visitante insiste na versão velha

O navegador guarda arquivos para não baixar tudo de novo. Isso é ótimo para o visitante e péssimo no dia da publicação: quem já entrou no site continua com o CSS antigo por horas, e o seu conserto parece não ter funcionado. Recarregar com Ctrl + Shift + R resolve no seu computador; o visitante não vai fazer isso.

A solução usada no mundo inteiro é trocar o nome do arquivo a cada publicação: em vez de estilo.css, um estilo.3f2a.css, em que o pedaço do meio muda quando o conteúdo muda. Como o endereço é novo, o navegador é obrigado a baixar. Com isso, você pode dizer ao servidor para guardar o CSS "para sempre" e o HTML "por cinco minutos" — o HTML muda mais e precisa ser fresco.

Para um site estático e pequeno, o caminho manual é esse: renomeie a folha com a data ou um número curto, atualize o link nas três páginas e publique. É chato, e é a versão honesta do processo para quem ainda não usa uma ferramenta de build. Quando o projeto crescer, um passo de automação faz o renomeio sozinho — e o conceito continua o mesmo.

Quem manda nessa história é o cabeçalho de cache que o servidor envia junto com o arquivo. Ele diz, em segundos, por quanto tempo o navegador pode reaproveitar a cópia. Duas políticas convivem bem: arquivos com nome versionado podem ser guardados por um ano, porque o nome muda quando o conteúdo muda; o HTML, que aponta para os nomes novos, vale poucos minutos. Assim o visitante baixa o HTML fresquinho, descobre o nome novo do CSS e baixa só o que mudou.

Se você publica num serviço que não deixa mexer nesses cabeçalhos, não se preocupe: o nome versionado já resolve o pior caso. O que não dá para fazer é confiar só no bom senso do navegador. Ele faz o que o servidor mandou, e o padrão costuma ser guardar por mais tempo do que você gostaria.

8. Build automático, no servidor

Quem publica com frequência para de rodar o build na mão. O servidor (ou um serviço de publicação) recebe os arquivos-fonte, roda dois comandos e publica o resultado. O primeiro é npm ci, que instala exatamente as versões do package-lock.json — releia a aula Instalando com npm se esse comando ainda não estiver claro. O segundo é o script de build que você já usa.

$ npm ci
added 12 packages in 2s
$ npm run build
$ ls dist
estilo.css

Para que isso funcione, o que vai para o servidor é o projeto, não o resultado: HTML, CSS de entrada, package.json e package-lock.json. A pasta node_modules é recriada pelo npm ci, e a pasta dist é recriada pelo build. Copiar qualquer uma das duas é trazer lixo e risco de versão diferente.

Um cuidado que vale ouro: o build automático tem de rodar com --minify e tem de falhar alto quando algo der errado. É para isso que serve o código de saída que você viu na aula da CLI: se o comando terminar com zero, o servidor publica; se terminar com outro número, a publicação para e alguém olha. Build silencioso que falha é pior que build nenhum.

Vale uma palavra sobre reprodutibilidade, que assusta pelo nome e é simples: o mesmo código de entrada tem de produzir o mesmo arquivo de saída, em qualquer máquina, em qualquer dia. O package-lock.json cuida da parte das versões; a varredura cuidada dos arquivos cuida do resto. Quando o build automático gera um arquivo com tamanho muito diferente do seu, é sinal de que ele está vendo outros arquivos — quase sempre porque roda numa pasta mais acima e varre o que não devia.

9. Cenários do dia a dia

Cenário 1: "o site no ar está sem estilo"

O sintoma é uma página cinza, com tudo colado. Confira primeiro o link da página publicada: ele aponta para um caminho que existe no servidor? Abra o endereço da folha no navegador — se der erro, é caminho; se aparecer o CSS, o problema é a página estar guardada em cache. Depois, confira se a folha publicada é a de produção, e não uma cópia antiga de src.

Cenário 2: "publiquei a correção e o cliente não vê"

Cache. O navegador do cliente guardou a folha com o nome antigo. A cura definitiva é o nome versionado: mude o arquivo de nome, atualize o link e o download é inevitável. Enquanto isso não acontece, o paliativo é pedir para recarregar sem cache — o que funciona para você e não para quem está na fila comprando pão.

Cenário 3: "a folha de produção ficou maior que a de desenvolvimento"

Acontece quando o build de produção roda em outro lugar, com outros arquivos por perto. Suspeite de um @source apontando para uma pasta enorme, de um build rodado na pasta do usuário (que varre tudo) ou de duas folhas ligadas na mesma página. Compare o número de blocos dentro de @layer utilities com o número de classes do seu site: a diferença mostra de onde vem o excesso.

Exercício: completar o build

É hora de publicar. Complete o comando com a opção que escreve a folha em formato compacto:

$ npx @tailwindcss/cli -i src/entrada.css -o dist/estilo.css

Dica: são duas opções no repertório da CLI, uma com quatro letras e uma com duas. A mesma ideia de "deixar menor" que a gente usa na cozinha para a porção que vai na vitrine.

11. Resumo

O build de produção é o mesmo gerador com outra prioridade: em vez de legibilidade, tamanho. A opção --minify tira espaços, comentários e valores redundantes, e o resultado é indistinguível na tela. O fluxo é parar o --watch, rodar o build compacto, conferir tamanho e caminho, abrir as páginas no computador e no tamanho de celular e copiar para o servidor só o que o visitante usa.

Duas ideias sustentam a publicação sem sustos. A primeira é que o servidor recebe fonte, não resultado: npm ci e o build recriam node_modules e dist. A segunda é que o nome do arquivo é a chave do cache: mudou o conteúdo, muda o nome, e o navegador de quem já visitou o site é obrigado a buscar o novo. Com essas duas, "publiquei e não apareceu" deixa de ser mistério.

Para lembrar

  • Desenvolvimento quer legibilidade; produção quer tamanho.
  • --minify compacta o texto; não remove classe nem muda valor.
  • Mesma aparência é o teste: se mudou, o problema é outro.
  • Pare o --watch antes de gerar a folha de produção.
  • Menos regras com o mesmo resultado também é otimização: prefira p-4 a px-4 py-4.
  • Ao servidor vão páginas, folha gerada e imagens; nada de fonte nem node_modules.
  • Renomear a folha a cada publicação vence o cache do visitante.
  • Build automático: npm ci, depois o script, e falhar alto se der erro.
  • Site sem estilo no ar quase sempre é caminho errado no link.
  • Cliente que não vê a correção quase sempre é cache.

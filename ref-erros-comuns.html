Erros Comuns

A Ana já publicou três páginas da padaria e nesta altura do campeonato o CSS dela já falhou de todos os jeitos possíveis: a classe que ela jurava ter escrito não aparecia, o cartão ficava com o respiro errado, a imagem estourava a coluna e um tutorial mandava rodar um comando que o terminal não reconhecia. Nenhuma dessas falhas veio com mensagem de erro — e é isso que torna o Tailwind tranquilo de aprender e chato de depurar. Esta página é a lista dos tropeços em ordem de frequência, com o sintoma, a causa e o conserto.

1. Por que o erro é silencioso

O Tailwind não valida o seu HTML. Ele lê o texto, encontra nomes de classe que reconhece e escreve CSS para eles; o que ele não reconhece, ele ignora. Não existe aviso de "essa classe não existe", porque tecnicamente ela pode ser sua — definida num <style>, vinda de um plugin, escrita com @utility. O motor não tem como saber se o nome era para ser uma utilitária ou se é só uma palavra qualquer no atributo.

Esse silêncio é uma escolha de projeto, e tem um lado bom: você nunca recebe um erro por causa de uma classe de terceiro. O lado ruim é que o diagnóstico fica com você, e a única testemunha confiável é o CSS computado no navegador. Todo o resto — achar que o arquivo salvou, achar que o build rodou, achar que a classe está certa — é palpite. O painel das caixas deste guia e a aba Computed do DevTools existem para trocar palpite por leitura.

Vale combinar uma rotina de três perguntas, na ordem, e nunca fora dela. A classe está escrita exatamente como o catálogo pede? Então ela existe. O CSS gerado tem a regra? Se não tem, o build não rodou ou o arquivo não foi lido. A regra existe e mesmo assim a tela não mudou? Então há algo vencendo ela — style inline, CSS sem camada ou !important. Cada uma das seções seguintes cobre uma dessas três perguntas.

classe inexistente
Um nome que o motor não reconhece. Não gera CSS, não gera erro, não aparece em lugar nenhum.
conflito
Duas classes que mexem na mesma propriedade. Vence a que estiver depois no CSS compilado, e não a que você escreveu depois no HTML.
camada
O agrupamento de regras que decide prioridade sem olhar especificidade: theme, base, components, utilities.
cache
A cópia do CSS que o navegador guardou. Um arquivo antigo em cache faz a página parecer que não atualizou.
escape
A barra invertida que protege dois-pontos e colchetes no nome da classe dentro do CSS: .md\:flex.

Esta é a categoria mais numerosa, e a mais fácil de resolver: quase sempre é um hífen no lugar errado, um número que não está na escala ou um sinônimo em inglês que o Tailwind não usa. A tabela reúne os tropeços que aparecem em toda turma, com o que o motor faz e o nome correto.

Há um caso especial que não é erro de digitação: a classe existe, mas o valor que você quer não está na escala. w-277 funciona (é degrau de espaço, 1108 px), w-[277px] é o que você quer. E há o caso oposto: a classe existe e faz algo diferente do que o nome sugere. shadow-sm no v4 é a sombra que no v3 se chamava shadow — a escala toda desceu um degrau, como mostra a seção 7.

O cartão deveria ter 16 px de respiro interno, mas a classe foi digitada com um "x" sobrando no fim. Corrija o nome e clique em Verificar: a missão lê o respiro computado.

<div id="alvo" class="rounded-lg bg-amber-50 p-4x">
  <p>Pão quentinho</p>
</div>
background-color: oklch(0.987 0.022 95.277)
border-radius: 8px

<div id="alvo" class="rounded-lg bg-amber-50 p-4">
  <p>Pão quentinho</p>
</div>

Depois de rodar o HTML inicial, o painel mostra border-radius e background-color, e nenhuma linha de padding. Essa ausência é o diagnóstico: a propriedade não foi tocada porque a classe não existe. Não é que o valor esteja errado — é que ninguém mandou o navegador mudá-lo. Guarde esse raciocínio: propriedade ausente do painel significa classe que não pegou, e quase sempre é nome.

3. O build que não rodou (ou rodou no lugar errado)

Se a classe está correta e mesmo assim não aparece, o problema saiu do HTML e foi para o processo. Três suspeitos, nesta ordem. Primeiro, o build não rodou depois da última mudança: o CSS gerado é uma fotografia do momento em que foi escrito, e classe nova não entra sozinha. Rode o comando de novo ou deixe o --watch ligado.

Segundo, o build rodou e escreveu num arquivo que a página não carrega. Acontece muito em projeto copiado: o HTML aponta para src/entrada.css e a saída foi para dist/estilo.css. A aba Network do navegador mostra qual arquivo foi pedido e qual foi devolvido; um 404 ou um tamanho muito pequeno denuncia o problema em dois segundos.

Terceiro, o navegador guardou a versão antiga em cache. O sintoma típico é a mudança aparecer em uma aba e não na outra. Recarregue com Ctrl e Shift e R (ou Cmd e Shift e R), e no DevTools desligue o cache enquanto trabalha. Em produção, o jeito de evitar é o servidor mandar um nome de arquivo com versão, como estilo.3f2a.css.

Existe ainda um quarto caso, mais raro: o motor não enxerga o arquivo onde as classes estão. Ele procura a partir da pasta do CSS de entrada, respeitando o .gitignore. Uma página gerada por script numa pasta ignorada, ou um HTML guardado fora do projeto, fica invisível — e a resposta é @source "../caminho"; no CSS de entrada. Se você usa classes montadas por concatenação em JavaScript, nenhum @source resolve: o nome precisa estar inteiro em algum lugar.

4. Conflito entre classes

Aqui o erro deixa de ser de digitação e passa a ser de expectativa. Duas classes que mexem na mesma propriedade não somam: uma vence. E quem decide não é a ordem em que você as escreveu no atributo class, e sim a ordem em que o Tailwind escreveu as regras no CSS. O caso clássico é class="p-8 p-2" num cartão que devia ficar apertado: a pessoa escreveu p-2 por último e achou que tinha vencido.

.p-2 {
  padding: calc(var(--spacing) * 2);
}
.p-8 {
  padding: calc(var(--spacing) * 8);
}

O Tailwind ordena as utilitárias por família e por valor, então p-8 sai depois de p-2 e ganha. O resultado do exemplo é 32 px, e não 8 px. Não há nada de errado nisso: é a mesma cascata de sempre, só que sem um arquivo visível para conferir. A saída prática é não escrever duas classes da mesma família no mesmo elemento — e, quando precisar, saber que a resposta é p-2!, com o ! no fim, que gera !important.

O segundo tipo de conflito não é entre utilitárias, e sim entre a utilitária e outra coisa. Estilo inline ganha de tudo; CSS escrito à mão sem @layer ganha das camadas; e um !important antigo ganha de quem não tem. Quando a regra existe no CSS e a tela não muda, inspecione o elemento e olhe na aba Styles qual declaração está riscada — o risco se chama "sendo sobrescrito", e o motivo aparece ao lado.

5. Variantes que não pegam

Variante inválida é silenciosa do mesmo jeito que classe inválida. Os tropeços têm causas bem distintas, e vale reconhecer cada uma. O primeiro: hover: no celular. Como visto em Estados e Variantes, o v4 embrulha o hover em @media (hover: hover), então num aparelho de toque a regra nem existe. O efeito não está quebrado; ele está desligado por desenho.

O segundo: disabled: num div. A pseudo-classe :disabled só existe em elementos de formulário, e um div com atributo disabled não é desabilitado para o navegador. Para um bloco, use aria-disabled="true" com aria-disabled:opacity-50, ou um data-* seu.

O terceiro: group-hover: sem nenhum ancestral com group. O seletor gerado procura um .group acima; sem ele, a regra nunca casa. O quarto é o par peer-* com o campo depois do aviso no HTML: o combinador só olha para frente, e nada acontece. O quinto é dark: sem o tema configurado: se o seu projeto usa tema por classe, é preciso declarar a variante com @custom-variant; sem isso, dark: segue a preferência do sistema.

O sexto é mais sutil e vale para qualquer variante: ela só existe se a classe inteira estiver no texto. "hover:" + "bg-amber-600" montado em JavaScript não gera nada, porque o compilador lê strings literais. Se você precisa alternar por código, alterne classes completas — ou, melhor, alterne um atributo e deixe a variante fazer o trabalho.

6. Os clássicos de layout

Estes não são erros do Tailwind: são comportamentos do CSS que aparecem no primeiro projeto e voltam sempre. Reconhecer pelo sintoma economiza meia hora de tentativa. A tabela é o resumo; os parágrafos abaixo explicam os três mais teimosos.

O primeiro é o mais frequente: dentro de um flex, todo item tem min-width: auto, o que significa "nunca fique menor que o seu conteúdo". Um parágrafo com uma palavra comprida, ou um pre, define uma largura mínima grande e empurra tudo. min-w-0 no item devolve o direito de encolher, e aí truncate ou break-words funcionam. É o mesmo motivo pelo qual uma tabela dentro de grid precisa de min-w-0 no contêiner.

O segundo é a altura em porcentagem. h-full é height: 100%, e porcentagem de altura só resolve quando o pai tem altura definida. Numa cadeia de div sem altura, o valor volta a auto e nada acontece. Se o objetivo é ocupar a tela, use h-dvh (a altura visível do navegador) ou min-h-screen no invólucro. Se o objetivo é herdar a altura de um pai que já tem, aí sim h-full.

O terceiro é o z-index sem posição. z-index só vale em elemento posicionado (ou flex/grid item). z-10 num div estático é ignorado, e a pessoa conclui que o Tailwind não gera a classe — quando gera. O mesmo raciocínio vale para absolute: ele se posiciona em relação ao ancestral posicionado mais próximo; sem nenhum, é o bloco da página, e o elemento "foge" para o canto.

A caixa de aviso sumiu em todas as telas: ficou só com hidden. Esta prévia tem 768 px, então o md: vale — acrescente o par que a mostra a partir daí.

<div id="alvo" class="hidden rounded-lg bg-amber-100 p-3 text-sm">
  Encomendas para o dia seguinte até as 17h.
</div>
display: none
padding: 12px
background-color: oklch(0.962 0.059 95.617)
font-size: 14px
line-height: 20px
border-radius: 8px

<div id="alvo" class="hidden rounded-lg bg-amber-100 p-3 text-sm md:block">
  Encomendas para o dia seguinte até as 17h.
</div>

Aqui o painel é a prova: antes, display: none; depois, display: block. Note que md:block não "desesconde" por mágica — ele escreve display: block dentro de uma consulta de largura, e essa regra vem depois da regra de hidden no CSS. É o mesmo princípio da seção 4, agora a favor do desenho.

7. Nomes que mudaram do v3 para o v4

Boa parte dos "erros" que aparecem em projeto novo é código de 2023 copiado para 2025. O v4 renomeou a escala de sombra e de raio, mudou a forma de declarar opacidade de cor, tirou as classes de opacidade separadas e mudou a posição do !. A tabela é a lista que mais aparece; todas as linhas foram conferidas no motor — quem está migrando de verdade encontra o roteiro em Migrando de CSS Antigo.

O caso da opacidade de cor merece ver o CSS, porque explica a mudança de sintaxe. No v4 a cor com opacidade não usa mais uma variável separada: ela é misturada na hora, com color-mix, e há um fallback para navegador antigo:

.bg-black\/50 {
  background-color: color-mix(in srgb, #000 50%, transparent);
  @supports (color: color-mix(in lab, red, red)) {
    background-color: color-mix(in oklab, var(--color-black) 50%, transparent);
  }
}

Repare no \/ no seletor: a barra também precisa de escape, como os dois-pontos. E repare que a cor vem de --color-black, então trocar a cor da marca no tema continua valendo. Quem tenta bg-black bg-opacity-50 no v4 não recebe erro nenhum: recebe preto opaco, porque a segunda classe não existe.

Sobre o ring, vale a explicação porque dói ver o layout: no v3 o anel padrão tinha 3 px e no v4 tem 1 px. Muita gente não percebe que o anel ficou fino, ou pior, escreve ring-3 esperando o valor antigo e recebe 3 px de verdade — que agora é o dobro do padrão. Anel não ocupa espaço, então o desenho não quebra; mas o foco fica menos visível, e acessibilidade não é lugar para aproximação.

8. O roteiro de investigação em cinco minutos

Quando nada funciona, a tentação é trocar classes ao acaso. Um roteiro fixo é mais rápido. Primeiro minuto: abra o DevTools, selecione o elemento e olhe a aba Computed. Se a propriedade tem o valor que você quer, o problema é outro — talvez o elemento errado esteja selecionado, ou o estilo esteja sendo aplicado num filho. Se não tem, vá para o segundo minuto.

Segundo minuto: procure o nome da classe no CSS gerado. No navegador, a aba Sources abre o arquivo; no terminal, um grep resolve. Se a classe não está lá, o build não a viu: rode de novo, confira o caminho da saída, confira o @source. Se está lá, o problema é de prioridade.

Terceiro minuto: na aba Styles, veja qual regra ganhou. Declaração riscada é regra derrotada. O motivo aparece ao lado — outra regra, !important, estilo inline. A partir daí a decisão é simples: remova o que vence, ou escreva a sua regra com força suficiente.

Quarto minuto: confira o elemento na tela, não no código. Um div a mais, um class colado no lugar errado, um fechamento de tag faltando — o HTML inválido faz o navegador reorganizar a árvore, e o seu estilo vai parar num elemento que você não tinha em mente. O testador de navegador deste guia verifica exatamente isso: tag escrita como exemplo na prosa, sem escape, abre um elemento de verdade e engole o resto da página.

Quinto minuto: reduza. Apague metade das classes e veja o que acontece; se voltar a funcionar, o conflito está na metade apagada. É chato e é rápido. Depurar CSS é uma busca binária, não uma discussão com o computador — e o computador sempre tem razão sobre o que aplicou. Quando o CSS gerado for o suspeito, Depurar o CSS mostra como ler o arquivo por dentro.

9. Resumo

O Tailwind não valida nomes: classe que não existe é ignorada em silêncio. A rotina de diagnóstico é sempre a mesma — a classe está escrita certo, o CSS gerado tem a regra, e a regra ganhou a disputa? Cada pergunta elimina uma família de causas.

  • Sem hífen, sem dois-pontos ou com sufixo inventado, a classe não existe: p4, text-bold, p-4x, md: block.
  • Classe que não aparece na tela: build parado, saída no arquivo errado, cache do navegador ou arquivo fora do alcance do @source.
  • Duas classes da mesma propriedade: vence a última no CSS compilado, não a última no HTML. Force com p-2!.
  • style="" vence tudo; CSS sem @layer vence as camadas do Tailwind.
  • Variante que não pega: hover: no toque, disabled: em div, group ausente, peer depois do alvo.
  • Layout: min-w-0 para encolher no flex, altura definida para h-full, relative para absolute e z-index.
  • v3 no v4: shadow virou shadow-sm, bg-opacity-* virou bg-black/50, ring agora é 1 px e o ! vai no fim.

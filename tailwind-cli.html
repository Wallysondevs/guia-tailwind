A CLI do Tailwind

A Ana já instalou os pacotes e já conseguiu gerar a folha de CSS uma vez — copiando o comando de um tutorial. O problema é que ela não sabe o que está copiando: se o caminho do arquivo mudar, se a pasta de saída não existir, se o terminal ficar horas sem responder, ela não tem para onde olhar. Nesta aula ela vira o jogo: entende o comando peça por peça, aprende as três formas de chamá-lo, descobre o que as poucas opções fazem e como saber, sem adivinhar, se o trabalho terminou bem.

Você vai aprender
  • O que é uma CLI e por que o Tailwind tem uma.
  • As três formas de chamar o comando: npx, o binário da pasta e o script do npm.
  • O que -i, -o, --watch, --minify e --help fazem.
  • O que a CLI lê, o que ela escreve e de que pasta rodar.
  • O que significa um comando terminar em silêncio e o que é código de saída.
  • Como ler a folha que a CLI escreveu, bloco por bloco.
  • O que fazer quando o comando reclama, trava ou não escreve nada.

1. A cena: o comando copiado

Na aula anterior a Ana instalou o Tailwind e rodou uma linha que encontrou num tutorial. Funcionou de primeira, e é justamente por isso que ela ficou incomodada. Ela quer mudar a saída de dist/estilo.css para dist/padaria.css e não sabe quais partes da linha mexer. Quer gerar uma segunda folha para a página de contato e não sabe se pode rodar o comando duas vezes. Quer entender por que o terminal às vezes devolve o cursor na hora e às vezes fica parado.

Esse é o momento certo para aprender a ferramenta. Um comando de terminal tem uma anatomia simples: o nome do programa, os argumentos (aquilo sobre o que ele age) e as opções (os ajustes, que começam com um ou dois hífens). Quem entende a anatomia consegue ler qualquer comando da documentação — e, mais importante, consegue perceber quando uma linha copiada não faz sentido para o seu projeto.

A CLI do Tailwind é pequena de propósito. Ela não compila JavaScript, não inicia servidor, não vigia pastas por conta própria, não tem arquivo de configuração próprio. Ela faz uma coisa: pega o CSS de entrada, pergunta ao motor quais classes o projeto usa e escreve o CSS final. Todo o resto — minificar, vigiar, otimizar — são variações dessa mesma tarefa.

2. O que é uma CLI, sem mistério

CLI é a sigla de command line interface, interface de linha de comando. É um programa sem janela própria: você o chama escrevendo o nome dele no terminal, ele faz o trabalho, imprime o que tem para imprimir e termina. Programas assim são ideais para tarefas repetitivas, porque podem ser chamados por scripts e por outras ferramentas, sem ninguém clicando em nada.

A conversa tem três canais. A entrada são os argumentos que você digita. A saída padrão é o texto que aparece na tela — normalmente mensagens curtas de progresso. A saída de erro é o canal das mensagens ruins, que também aparece na tela, mas por outro caminho. E existe ainda um número silencioso, o código de saída: zero quando deu certo, diferente de zero quando falhou. Programas que automatizam o build olham esse número, não o texto.

Guarde essa última ideia, porque ela resolve a dúvida mais comum de quem começa: "o terminal não mostrou nada, funcionou?". Se o código de saída é zero, sim. Ferramentas de linha de comando são econômicas por cultura: elas só falam quando têm algo a dizer. Silêncio, depois de um comando que deveria gerar um arquivo, é o som do sucesso.

argumento
O alvo do comando. Em npx @tailwindcss/cli, o argumento é o nome do pacote; o resto são opções com os valores delas.
opção
Um ajuste, escrito com hífen: -i (curta) ou --input (longa). As duas formas fazem a mesma coisa; a curta economiza digitação.
caminho
O endereço de um arquivo ou pasta. Pode ser absoluto (/home/ana/padaria/src) ou relativo à pasta em que o terminal está.
binário
O arquivo executável de um pacote. O npm cria um atalho dele em node_modules/.bin para que você não precise escrever o caminho inteiro.
código de saída
O número que o programa devolve ao terminar. Zero é sucesso; qualquer outro valor é falha, e é por ele que os scripts decidem parar ou continuar.

Uma nota sobre a palavra binário: ela não quer dizer que o arquivo seja ilegível. O atalho do Tailwind é um pequeno arquivo de script que chama o JavaScript do pacote. No Windows ele ganha a extensão .cmd; no Linux e no macOS, não tem extensão e é executável. Quando o terminal diz "comando não encontrado", ele está reclamando justamente de não achar esse atalho.

3. As três formas de chamar o mesmo comando

O mesmo programa pode ser chamado de três jeitos, e os três chegam no mesmo lugar. Saber a diferença evita o erro de colar uma linha de um contexto no outro.

A primeira é npx, que procura o comando dentro de node_modules e o executa. Se não achar, baixa o pacote numa pasta temporária e roda — útil para experimentar, arriscado para o dia a dia, porque você pode acabar usando uma versão diferente da que está no projeto. A segunda é o caminho completo do atalho, ./node_modules/.bin/tailwindcss, que é o que o npx faz por baixo. A terceira é dentro de um script do package.json, escrevendo só tailwindcss: o npm coloca a pasta .bin no caminho de busca antes de executar o script, então o nome curto basta.

Como chamarO que aconteceQuando usar
npx @tailwindcss/cli -i … -o …usa o pacote do projeto; se faltar, baixa um temporárioprimeiros testes, comandos avulsos
./node_modules/.bin/tailwindcss …executa exatamente o que está instaladoquando precisa ter certeza da versão
npm run buildroda o script build do package.jsondia a dia, e tudo que for automatizado

Para o trabalho de todo dia, a terceira forma ganha. Ela é curta, fica documentada no projeto e esconde os caminhos compridos. Se amanhã a Ana mudar a saída de dist/estilo.css para dist/padaria.css, mexe em um lugar só — no script — e todos os comandos que chamam npm run build continuam funcionando.

4. O comando mínimo: entrada e saída

Sem opção nenhuma, a CLI não sabe o que fazer: ela precisa de um arquivo para ler e de um lugar para escrever. Essas são as duas únicas opções obrigatórias. Tudo o mais é ajuste.

$ npx @tailwindcss/cli -i src/entrada.css -o dist/estilo.css
$ echo $?
0

-i vem de input, entrada: é o CSS que você escreveu, com o @import "tailwindcss"; e o que mais você quiser declarar. -o vem de output, saída: é o arquivo que a CLI cria ou sobrescreve, e é ele que a página carrega. Repare no echo $? logo depois: ele imprime o código de saída do último comando, e o 0 confirma que deu certo. No Windows, o equivalente é echo %ERRORLEVEL%.

Se a pasta de saída não existir, crie antes: mkdir -p dist faz isso e não reclama se a pasta já existir. É um comando idempotente, ou seja, pode ser repetido sem efeito colateral. Vale a pena rodá-lo uma vez na vida do projeto e esquecer o assunto.

5. O que a CLI lê, o que ela escreve e de que pasta

Vale ser preciso sobre o trabalho dela, porque metade dos problemas de "a classe não funciona" nasce de uma expectativa errada aqui. A CLI lê dois tipos de coisa. Primeiro, o arquivo de entrada, que é o único caminho que você informa. Segundo, todos os arquivos de texto do projeto — HTML, JavaScript, componentes, Markdown —, porque é neles que os nomes de classe aparecem.

A varredura começa na pasta em que o comando foi chamado e desce pelas subpastas. Ela pula o que não é texto e pula a própria node_modules, que tem milhares de arquivos e nenhuma classe sua. Se as páginas da Ana estão em public/ ou se algum componente mora fora da pasta do projeto, a CLI precisa saber: é para isso que existe o @source, uma linha no CSS de entrada que acrescenta caminhos à varredura. A aula O CSS de Entrada mostra como escrever essa linha.

Por isso a pasta de onde você roda o comando não é detalhe. O terminal tem uma pasta atual, e todo caminho relativo é resolvido a partir dela. Se a Ana está em /home/ana e digita -i src/entrada.css, o programa vai procurar /home/ana/src/entrada.css e não vai achar. O caminho mais previsível é rodar sempre da raiz do projeto, a pasta que tem o package.json — e é de lá que os scripts do npm rodam por definição:

$ cd /home/ana/padaria
$ pwd
/home/ana/padaria
$ ls
dist  index.html  package.json  src

Três comandos que você vai usar mais do que qualquer opção do Tailwind: pwd mostra onde você está, ls mostra o que tem ali, cd leva para outra pasta. Caminho errado é a causa de boa parte dos erros de iniciante, e esses três comandos custam menos que o erro.

Na saída, a CLI escreve um arquivo de CSS comum. Não escreve JavaScript, não escreve HTML, não injeta nada na página. Ela sobrescreve o arquivo inteiro a cada execução: não há atualização incremental no arquivo, e é por isso que a data de modificação dele muda toda vez. Se você editar a saída à mão, a próxima execução apaga a sua edição — é sempre assim, e é uma proteção: a fonte da verdade é a entrada mais o HTML.

6. As opções que importam

São poucas, o que é uma vantagem. Estas cinco resolvem praticamente tudo, e cada uma tem forma curta e forma longa:

OpçãoForma longaO que faz
-i--inputo arquivo de CSS a ser lido como entrada
-o--outputo arquivo de CSS a ser escrito como saída
-w--watchfica rodando e refaz o build a cada salvamento
-m--minifyescreve o CSS sem espaços nem comentários, para ir ao ar
-h--helpmostra o resumo das opções e a versão

A ordem das opções não importa: -i antes ou depois de -o dá o mesmo resultado. O que importa é que cada opção venha seguida do seu valor, separados por espaço. Um hífen sozinho também é informação: -i é opção, -input é erro de digitação, e a CLI reclama de opção desconhecida em vez de adivinhar.

Quando estiver em dúvida sobre uma opção nova, o primeiro reflexo deve ser npx @tailwindcss/cli --help. A resposta vem do programa que está instalado no seu projeto, não de um blog de dois anos atrás — e essa é a diferença entre uma resposta certa e uma resposta quase certa. As opções --watch e --minify têm aulas próprias, porque mudam o jeito de trabalhar: O Modo watch e Build de Produção.

A CLI escreveu a regra errada para a coluna da padaria: ela está com 128 px. Deixe a coluna com 16 rem de largura — e note, no painel de CSS, que a regra gerada não tem número: ela tem uma conta com variável.

<div id="alvo" class="w-32 bg-amber-100 p-2">Encomendas</div>
width: 128px
padding: 8px
background-color: oklch(0.962 0.059 95.617)

<div id="alvo" class="w-64 bg-amber-100 p-2">Encomendas</div>

Repare no painel: width: 256px, e a regra por trás é width: calc(var(--spacing) * 64). A CLI não escreveu "256px" em lugar nenhum: ela escreveu a multiplicação, e o navegador resolve. Entender isso ajuda quando um valor parece estranho — a resposta costuma estar na variável, não na conta.

7. Silêncio, erro e código de saída

O comando termina de três maneiras. Termina em silêncio, com código zero: deu certo, o arquivo foi escrito. Termina com uma mensagem curta e código diferente de zero: alguma coisa está errada e a mensagem aponta o caminho. Ou não termina: nesse caso, quase sempre é porque o --watch está ligado e ele não termina por desenho — fica esperando o próximo salvamento.

Essa distinção é a chave para não entrar em pânico. Um terminal parado depois de --watch não está travado: está trabalhando. Para sair, o atalho universal é Ctrl + C; ele interrompe o processo e devolve o cursor. Se você fechar a janela do terminal no meio, o processo morre junto, e a próxima alteração no HTML não vai gerar CSS nenhum — motivo de metade dos "parou de funcionar" de quem usa watch.

Quando o assunto é automatizar, o código de saída vira o personagem principal. Um script de publicação roda o build e só continua se o código for zero. Nada de ler mensagens à mão: o número decide. É por isso que a CLI é silenciosa, e é por isso que vale conferir o echo $? pelo menos uma vez, para ver o zero com os próprios olhos.

Vale conhecer também o caminho de erro mais instrutivo: rodar o comando sem o arquivo de entrada. A CLI responde dizendo que falta a entrada e mostra um exemplo de uso correto. Ler essa resposta com calma ensina mais do que qualquer aula — e é de graça. Repare que ela não tenta adivinhar qual arquivo você queria: ferramenta boa falha rápido e diz onde.

8. Lendo o que a CLI escreveu

O arquivo gerado é a prova do trabalho da CLI, e vale aprender a lê-lo. Ele começa com um comentário de versão, depois declara as variáveis do tema e, no fim, escreve as classes na ordem em que o motor as organiza. Cada classe vira um bloco pequeno, com o seletor da classe e as propriedades que ela muda. Duas classes que produzem a mesma regra não se repetem: uma regra serve a todos os elementos que usam o nome.

Um detalhe que confunde quem compara o arquivo com o resultado na tela: a CLI escreve algumas classes com nomes de propriedade lógicos, como padding-inline e padding-block, em vez de padding-left e padding-right. O navegador entende os dois, e o painel de CSS computado resume tudo numa linha só. Não é bug: é o mesmo recurso que permite ao Tailwind funcionar em idiomas escritos da direita para a esquerda.

Quando a classe tem uma condição, a CLI escreve um bloco em volta. Uma classe de breakpoint vira um @media com largura mínima; uma classe de estado vira um seletor com dois-pontos. É a mesma sintaxe de CSS que você já viu, só que gerada. Pedir que a caixa mostre as regras geradas é a maneira mais direta de ver isso acontecendo sem abrir o arquivo:

Na tela larga, o cartão precisa de 32 px de respiro; na estreita, 16 px bastam. Deixe o respiro grande valendo a partir do breakpoint médio e observe o bloco @media que aparece na saída.

<div id="alvo" class="p-4 md:p-4 bg-amber-100">Pão quentinho</div>
.bg-amber-100 {
  background-color: var(--color-amber-100);
}
.p-4 {
  padding: calc(var(--spacing) * 4);
}
@media (width >= 48rem) {
  .md\:p-4 {
    padding: calc(var(--spacing) * 4);
  }
}

<div id="alvo" class="p-4 md:p-8 bg-amber-100">Pão quentinho</div>

A saída traz o bloco da classe sem condição e o bloco dentro do @media — além do fundo âmbar, que já estava lá. A largura de 48rem é o breakpoint médio do Tailwind, equivalente a 768 px. A prévia desta caixa está com 768 px justamente para que o breakpoint valha: em 640 px, o bloco sairia com o valor de antes.

A vitrine dos pães precisa de três colunas iguais, com 16 px entre elas. A classe grid já está no cartão; faltam as colunas e o espaço.

<div id="alvo" class="grid gap-2">
  <p>Pão francês</p>
  <p>Broa</p>
  <p>Sonho</p>
</div>
.grid {
  display: grid;
}
.gap-2 {
  gap: calc(var(--spacing) * 2);
}

<div id="alvo" class="grid grid-cols-3 gap-4">
  <p>Pão francês</p>
  <p>Broa</p>
  <p>Sonho</p>
</div>

Duas classes, dois blocos, e a grade aparece. A regra de grid-cols-3 é repeat(3, minmax(0, 1fr)) — três colunas de largura igual que nunca estouram o container. Você não precisa decorar esse texto; precisa reconhecer que ele é o resultado de um nome curto. O caminho mental é sempre o mesmo: a classe no HTML, a regra na saída, o valor na tela.

9. Cenários do dia a dia

Cenário 1: "não achei o arquivo de entrada"

A mensagem fala de um caminho comprido que você não digitou. É sinal de que o caminho relativo foi resolvido a partir de outra pasta. Rode pwd e confira: se não estiver na raiz do projeto, volte com cd e repita o comando. Também vale olhar se o arquivo de entrada existe mesmo, com ls src — nome trocado, extensão trocada e pasta que nunca foi criada produzem a mesma mensagem.

Cenário 2: "a folha saiu, mas sem as minhas classes"

O arquivo existe e está quase vazio. Quase sempre a varredura não passou por onde o HTML está: ou o comando rodou numa pasta acima do projeto, ou as páginas moram fora da pasta do comando, ou a classe está montada em pedaços no JavaScript e nunca aparece escrita por inteiro. A cura é apontar o caminho com @source e rodar de novo da raiz. O Tailwind não avisa sobre classe que não encontrou: folha pequena é o aviso.

Cenário 3: "o terminal parou e não aceita mais nada"

Provavelmente o comando está em modo de espera, com --watch ligado. Não está travado: ele fica ouvindo alterações e só escreve quando você salva. Se você quer o cursor de volta, aperte Ctrl + C. Se quer continuar gerando CSS a cada salvamento, deixe esse terminal em paz e abra outro para os demais comandos — é o que a aula O Modo watch ensina a fazer.

11. Resumo

A CLI do Tailwind é um programa de terminal pequeno: lê um CSS de entrada, percorre os arquivos do projeto em busca de nomes de classe e escreve um CSS de saída. Ela tem duas opções obrigatórias, -i e -o, e umas poucas opcionais — --watch para refazer o build a cada salvamento, --minify para compactar a saída, --help para lembrar do resto. Pode ser chamada por npx, pelo atalho em node_modules/.bin ou por um script do npm, que é a forma recomendada no dia a dia.

O comportamento dela é discreto por desenho: não fala quando dá certo, e o código de saída zero é o atestado. A pasta de onde você roda o comando importa duas vezes — pelos caminhos relativos e pelo ponto de partida da varredura. E o arquivo que ela escreve é CSS comum, que vale a pena abrir e ler: cada classe vira um bloco, condições viram @media, e nada do que está lá foi escrito por você.

Para lembrar

  • CLI é programa de terminal: argumentos entram, texto e código de saída saem.
  • Só duas opções são obrigatórias: -i (entrada) e -o (saída).
  • --watch fica rodando; Ctrl + C interrompe.
  • --minify compacta a saída; serve para publicar, não para estudar.
  • Na dúvida sobre uma opção, rode --help e leia a resposta do próprio programa.
  • No script do npm, o nome curto tailwindcss funciona; no terminal, use npx.
  • Rode da raiz do projeto: caminhos e varredura dependem da pasta atual.
  • Silêncio mais código zero é sucesso; mensagem mais código diferente de zero é falha.
  • A CLI sobrescreve a saída inteira: não edite o arquivo gerado à mão.
  • Ela escreve CSS comum, com @media e variáveis — e você pode ler tudo.

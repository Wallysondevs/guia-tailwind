O CSS de Entrada

A Ana abriu o arquivo src/entrada.css da padaria e encontrou uma linha só: @import "tailwindcss";. Ficou desconfiada. Um arquivo com uma linha não pode ser o lugar onde se configura um site inteiro — ou pode? Nesta aula ela descobre que esse arquivo pequeno é o painel de controle do projeto: é nele que se diz de onde vêm as classes, quais valores a marca usa e quais estilos entram junto com as utilitárias. E descobre também o que não deve ir para lá.

Você vai aprender
  • O que é o CSS de entrada e por que ele não é o arquivo que a página carrega.
  • O que a linha @import "tailwindcss"; traz para dentro do projeto.
  • Por que ela precisa ser a primeira linha do arquivo.
  • O que mais pode morar no arquivo: @source, @theme, @apply e CSS comum.
  • Como usar @apply para criar uma classe sua com utilitárias por dentro.
  • A ordem das regras e o que acontece quando um valor entra em conflito.
  • O que fazer quando a folha sai vazia ou o estilo esperado não aparece.

1. A cena: um arquivo com uma linha

Depois de instalar e de rodar o build algumas vezes, a Ana resolveu abrir os dois arquivos de CSS do projeto, um ao lado do outro. O de dist/ tinha centenas de linhas, cheio de blocos e variáveis. O de src/ tinha uma linha. Um é o resultado do trabalho; o outro é o pedido. E é aí que vem a pergunta que esta aula responde: se o pedido é tão pequeno, onde é que se configura o resto?

A resposta é que o pedido é pequeno porque o Tailwind já sabe o que fazer com quase tudo. Ele tem um catálogo de nomes prontos e um conjunto de valores padrão — cores, espaços, tamanhos de fonte, raios de borda. O arquivo de entrada serve para dizer o que é específico do seu projeto: de onde ler os arquivos, quais valores são da marca, quais combinações viram uma classe só. É a diferença entre um caderno impresso e as suas anotações nas margens.

Antes de qualquer coisa, um ponto que confunde muita gente: esse arquivo nunca é ligado na página. O link do HTML aponta para o arquivo de dist. O de src é fonte, como o HTML: existe para ser lido pela ferramenta. Se você ligar o de src na página, o navegador recebe uma linha de @import e nenhuma classe — e o site fica sem estilo, sem nenhum erro visível.

2. O que é o CSS de entrada

O arquivo de entrada é um CSS comum, com uma diferença: ele passa pelo compilador do Tailwind antes de virar o arquivo final. Tudo o que o compilador entende — as diretivas dele e o CSS normal — sai do outro lado; o que ele não entende, ele reclama. Por isso o arquivo é, ao mesmo tempo, configuração e folha de estilo.

Pense nele como a receita que você entrega ao padeiro. A receita não é o pão: é a instrução. O pão é o que sai do forno, e é ele que o cliente leva. Se você mudar a receita, o próximo pão muda; o que já saiu não muda. Essa imagem vale para o fluxo inteiro: mexa na entrada, rode o build, o arquivo de dist é reescrito do zero.

entrada
O arquivo que você escreve, em src/entrada.css ou nome parecido. Aponta no -i da CLI. Nunca é ligado na página.
saída
O arquivo que a CLI escreve, em dist/estilo.css. É o que o navegador carrega. Nunca é editado à mão.
diretiva
Uma instrução que começa com @, como @import, @theme ou @apply. São ordens para o compilador, não para o navegador.
camada
Um grupo de regras com prioridade definida. O Tailwind usa camadas para que a utilitária vença o reset sem precisar de !important.
utilitária
Uma classe que faz uma coisa só, como p-4. É o que o Tailwind gera em série a partir do que encontra no projeto.

O nome do arquivo é escolha sua: entrada.css, app.css, tailwind.css, estilos/fonte.css. O que importa é que ele exista, que esteja apontado no -i e que ninguém o confunda com a saída. Projetos maiores às vezes têm mais de um, um por área do site.

3. A linha que faz tudo: @import "tailwindcss"

Essa linha pede ao compilador que traga o Tailwind inteiro para o arquivo: as variáveis do tema, o reset de base e a capacidade de gerar utilitárias. Sem ela, o arquivo é só CSS comum — as classes do Tailwind no HTML não produzem regra nenhuma, e a página fica sem estilo.

Ela precisa ser a primeira coisa do arquivo, antes de qualquer regra sua. Não é capricho do Tailwind: a regra de CSS para @import exige que ele venha antes de todas as outras regras, senão o navegador ignora. Se você escrever sua classe primeiro e o @import depois, o compilador avisa — e, se não avisasse, o resultado seria uma folha sem o tema.

Quem vem de tutoriais antigos vai estranhar: a versão 3 pedia três linhas, @tailwind base, @tailwind components e @tailwind utilities. A versão 4 trocou as três por um @import só. Se você colar as linhas antigas num projeto novo, elas não fazem nada — não há erro, só uma folha sem o Tailwind. Quando um tutorial parecer certo e não funcionar, confira a versão antes de conferir o resto.

Um detalhe prático: o @import também aceita a forma @import "tailwindcss/preflight" e outras fatias separadas, para quem quer só uma parte. É recurso de projeto grande, que prefere controlar cada pedaço. Para o site da padaria, a linha inteira é o que basta.

4. O que mais pode morar no arquivo

Aqui está a parte que responde à desconfiança da Ana: o arquivo pequeno pode crescer quando o projeto precisa. Estas são as diretivas que aparecem com mais frequência, com o que cada uma faz:

DiretivaPara que serveExemplo
@importtraz o Tailwind para o arquivo@import "tailwindcss";
@sourceacrescenta pastas à varredura de classes@source "../public";
@themedeclara valores do projeto: cores, espaços, fontes@theme { --color-marca: #b4532a; }
@applyusa utilitárias dentro de uma regra sua.botao { @apply px-4 py-2; }
@custom-variantcria uma variação própria, como um tema@custom-variant destaque (&:where([data-destaque]));

Além das diretivas, cabe CSS comum: seletores de elemento, classes suas, regras de impressão, o que você quiser. O compilador deixa passar. É ali, por exemplo, que se ajusta a cor de fundo do body ou se define um estilo para links que não têm classe. A regra de bom senso é não duplicar: se existe uma utilitária que faz o serviço, use a utilitária no HTML.

Duas diretivas ficaram de fora da tabela de propósito, porque são assunto de aulas próprias: @config, que carrega um arquivo de configuração no formato antigo, e @plugin, que carrega plugins da comunidade. Você não precisa delas para começar, e a documentação avisa que são caminhos de compatibilidade.

A @source merece um parágrafo, porque resolve um problema real. Por padrão, a CLI percorre a pasta em que foi chamada. Se as páginas do site ficam em public/ e o CSS em src/, a varredura já passa por ali, porque public/ está dentro do projeto. Mas se algum arquivo mora fora — um componente compartilhado, uma pasta irmã —, a classe dele não entra no build. A linha @source "../compartilhado"; conserta isso sem precisar mover arquivo nenhum.

5. A ordem importa, e as camadas explicam por quê

Dentro do arquivo de entrada, a ordem das suas regras conta. CSS é uma lista: quando duas regras atingem o mesmo elemento com a mesma prioridade, a última vence. O Tailwind organiza o próprio conteúdo em camadas — tema, base, componentes, utilitárias —, e as utilitárias ficam por último justamente para vencer o reset do navegador.

Aqui vem a parte contraintuitiva, e ela vale ouro. Suas regras escritas depois do @import vencem as utilitárias, mesmo que a utilitária esteja no HTML. O motivo são as camadas: o Tailwind coloca as utilitárias dentro de @layer utilities, e a regra do CSS diz que o que está fora de camada ganha do que está dentro. Sua regra comum, escrita solta no arquivo, está fora de camada. Portanto ela manda.

Isso explica o susto mais comum de quem começa: o cartão tem class="cartao p-4", a regra .cartao fixa 40 px de padding, e o p-4 parece não funcionar. Não é bug: a regra fora de camada está ganhando. As saídas são duas — tirar a propriedade da regra e deixar a utilitária cuidar dela, ou escrever a regra dentro de @layer components, que fica antes das utilitárias e perde a disputa de propósito.

A recomendação prática é a primeira: cada propriedade tem um dono. Se o espaçamento é assunto da utilitária, a regra .cartao cuida de outra coisa. Quando você quiser mesmo que a utilitária vença, envolva a regra em @layer components e o conflito desaparece. Não é preciso decorar a ordem das camadas; é preciso saber que ela existe e que decide as brigas silenciosas.

A regra .cartao fixa 40 px de padding e está vencendo o p-2, que deveria dar 8 px. Deixe o espaçamento com a utilitária e a regra cuidando do arredondamento de 8 px.

<style type="text/tailwindcss">
.cartao { padding: 40px; }
</style>
<div id="alvo" class="cartao p-2">Pão quentinho</div>
padding: 40px

<style type="text/tailwindcss">
.cartao { border-radius: 8px; }
</style>
<div id="alvo" class="cartao p-2">Pão quentinho</div>

Depois da missão, o painel mostra 8 px de respiro e 8 px de raio: um valor de cada dono, sem briga. Se você tivesse deixado os dois paddings, o resultado dependeria de quem foi escrito por último — e esse tipo de dúvida não aparece no código, só no resultado.

6. @apply: a classe sua que usa utilitárias

Existe uma situação em que repetir a mesma lista de classes em vinte botões cansa: quando o botão aparece em toda parte e sempre igual. O @apply existe para isso. Você escreve uma regra normal, com um seletor seu, e dentro dela pede as utilitárias que quiser. O compilador copia as propriedades para dentro da sua regra e o HTML fica com uma classe só.

.botao {
  border-radius: var(--radius-lg);
  padding-inline: calc(var(--spacing) * 4);
  padding-block: calc(var(--spacing) * 2);
}

É literalmente isso que sai no arquivo final: a classe .botao com as propriedades das utilitárias copiadas para dentro. Nada de @apply chega ao navegador — a diretiva é uma instrução de montagem, não um recurso de CSS.

O botão da padaria usa a classe botao, definida no CSS de entrada. Falta arredondar os cantos e dar respiro: acrescente ao @apply o raio de 8 px e o respiro horizontal de 16 px.

<style type="text/tailwindcss">
.botao { @apply py-2; }
</style>
<button id="alvo" class="botao">Encomendar</button>
.botao {
  padding-block: calc(var(--spacing) * 2);
}

<style type="text/tailwindcss">
.botao { @apply rounded-lg px-4 py-2; }
</style>
<button id="alvo" class="botao">Encomendar</button>

O painel de regras mostra o resultado: um bloco .botao com as propriedades das utilitárias escolhidas, e mais nada. O HTML não sabe que existe Tailwind ali. Isso tem um custo e um benefício. O custo é que a regra .botao deixa de responder a variações: não existe botao:hover nem md:botao, a não ser que você escreva outra regra. O benefício é que o HTML fica curto e o estilo do botão mora em um lugar só.

O uso saudável do @apply é para peças realmente repetidas e realmente estáveis — o botão principal, o selo, o campo de formulário. Usar @apply em tudo devolve o problema que o Tailwind veio resolver: um CSS cheio de classes inventadas, longe do HTML, em que ninguém sabe de onde vem cada valor. Quando estiver em dúvida, repita as utilitárias no HTML; é mais fácil de ler.

7. @theme: os valores da casa

O @theme é onde se declaram os valores que o projeto usa e o Tailwind não tem. Uma cor de marca, por exemplo. A sintaxe é a de variáveis CSS, com um prefixo que diz ao Tailwind que tipo de valor é aquilo: --color- para cores, --spacing para a escala de espaço, --font- para famílias de fonte.

A padaria tem uma cor de marca, o terracota #b4532a, já declarado no CSS de entrada. Pinte o selo com essa cor e deixe o texto branco — usando só classes.

<style type="text/tailwindcss">
@theme { --color-marca: #b4532a; }
</style>
<span id="alvo" class="px-2 py-1">Pão do dia</span>
.px-2 {
  padding-inline: calc(var(--spacing) * 2);
}
.py-1 {
  padding-block: var(--spacing);
}

<style type="text/tailwindcss">
@theme { --color-marca: #b4532a; }
</style>
<span id="alvo" class="px-2 py-1 bg-marca text-white">Pão do dia</span>

Repare no que aconteceu: a variável --color-marca virou uma família de utilitárias. bg-marca pinta o fundo, text-marca pinta a letra, border-marca pinta a borda — todas de graça, sem você escrever regra nenhuma. É esse o poder do @theme: declarar uma vez e ganhar o catálogo inteiro.

.bg-marca {
  background-color: var(--color-marca);
}

O bloco não tem o valor em hexadecimal: tem a variável. O hexadecimal fica declarado uma vez, no arquivo de entrada, e todas as regras apontam para ele. Trocar a cor da marca passa a ser uma edição de uma linha, seguida do build.

Como o @theme gera variáveis CSS, o valor final aparece como var(--color-marca) na folha gerada. Você pode até usar a variável direto numa regra sua. O assunto tem aula própria, com todos os tipos de valor e as armadilhas de nome: quando o site crescer, vale ler Cores da Marca e, mais adiante, o @theme completo.

8. O que não vai no arquivo de entrada

Três coisas não pertencem a ele, e todas aparecem no começo. A primeira é @tailwind no lugar do @import: sintaxe da versão 3, que na 4 não faz nada. A segunda é o CSS de uma página específica — o ajuste de uma tela, o espaçamento de um cartão. Isso mora no HTML, como classe. O arquivo de entrada é para o que vale no site inteiro.

A terceira é o próprio arquivo de saída: não copie pedaços de dist/estilo.css para dentro da entrada. A saída é descartável e reescrita a cada build; o que você precisa dela é gerado automaticamente. Copiar é criar uma segunda fonte de verdade, que envelhece sem avisar.

Existe um caso legítimo de CSS solto no arquivo de entrada: o reset fino e os estilos de base. Um body com fundo claro, uma fonte padrão, o scroll-behavior suave, a seleção de texto com a cor da marca. São regras globais, que valem para o site todo e não têm classe. A aula Variáveis de Tema mostra como amarrar esses valores às variáveis, para que mudem junto com o resto.

9. Cenários do dia a dia

Cenário 1: "a folha saiu com uma linha só"

Você abriu a entrada no navegador achando que era a saída, ou ligou o arquivo errado no HTML. A folha de src/ tem o @import e mais nada — é fonte. Confira o href do link: ele tem de apontar para dist/. Se o caminho estiver certo e a página continuar sem estilo, rode o build e recarregue sem cache.

Cenário 2: "minha classe do entrada não pega no HTML"

Duas causas comuns. A primeira é ordem: sua regra está antes do @import, então o Tailwind veio depois e o navegador aplicou outra coisa — ou o compilador recusou o arquivo. A segunda é especificidade: a utilitária está na camada de utilitárias e vence a sua regra comum. Se precisar mesmo que a sua regra vença, escreva-a depois e com o mesmo peso; se puder, resolva com utilitária e esqueça a classe própria.

Cenário 3: "o @apply não faz nada"

O @apply só funciona em arquivo que tem o @import "tailwindcss" no topo, ou que é importado por ele. Se você criou um CSS separado só com @apply e ligou esse arquivo direto na página, o navegador não conhece a diretiva e a ignora em silêncio. A cura é incluir o arquivo dentro da entrada, com @import "./botoes.css";, na ordem certa.

11. Resumo

O CSS de entrada é o arquivo que você escreve e o compilador lê: pequeno por fora, poderoso por dentro. Sua primeira linha, @import "tailwindcss";, traz tema, base e a capacidade de gerar utilitárias. Depois dela cabem diretivas — @source para ampliar a varredura, @theme para declarar valores da casa, @apply para criar classes compostas — e também CSS comum, para o que é global e não tem classe.

O que nunca vai para lá é o resultado do build: dist é saída, reescrita a cada execução. E o que nunca sai de lá é o link da página: o HTML carrega a saída, sempre. Uma vez entendida essa separação, os dois arquivos param de parecer duplicados e passam a ser o que são — a receita e o pão.

Para lembrar

  • Entrada é fonte, escrita por você; saída é resultado, escrita pela CLI.
  • O link da página aponta sempre para a saída.
  • @import "tailwindcss"; vem antes de qualquer regra sua.
  • Na versão 4 não existe @tailwind base: quem manda é o @import.
  • @source acrescenta pastas que a varredura não veria.
  • @theme transforma uma variável em família de utilitárias.
  • @apply é para peça repetida e estável, não para tudo.
  • Suas regras comuns valem mais que as utilitárias: estão fora de camada.
  • Para a utilitária vencer, escreva a regra em @layer components.
  • CSS global sem classe cabe aqui; CSS de uma tela específica mora no HTML.
